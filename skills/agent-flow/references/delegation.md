# Назначения исполнителей

Делегируйте независимую работу, когда результат оправдывает стоимость передачи контекста и интеграции. Не создавайте роли под отдельный файл или задачу. Используйте существующую роль и отдельное назначение.

Для документной задачи обязателен отдельный реальный `orchestrator` по [правилам Doc Flow](flows.md#маршрутизация-doc-flow); это не зависит от масштаба или способности root выполнить работу самостоятельно. Оркестратор определяет роли, пакеты, последовательность и повторные проверки. В задаче с журналом фактический root технически запускает и продолжает каждого участника как своего прямого ребёнка и регистрирует назначения по указаниям оркестратора. Сам оркестратор также прямой ребёнок root и не запускает авторов, reviewer или QA как внуков. Root identity и единственный журнал сохраняются; технический запуск не даёт root параллельного права выбирать маршрут. Недоступность обязательного оркестратора оставляет этап невыполненным.

## До запуска

Прочитайте `agents/<role>.md`. Выберите минимальные профильные skills из доступных; отсутствие необязательного skill не разрешает установку и не должно превращаться в фиктивное подтверждение проверки.

Если документ передаётся как задание или источник согласованных решений для реализации, до назначения исполнителя проверьте его текущую редакцию по [правилу утверждения](flows.md#утверждение-документов): статус `approved` и отсутствие открытых вопросов обязательны. Передайте исполнителю ссылку на эту редакцию и её статус. Обнаруженный открытый вопрос возвращается владельцу документа; зависимая реализация ждёт исправления и утверждения. Обычное чтение справочных материалов не является такой передачей.

Идентичности и отображаемые имена находятся в `agents/agent-identities.json`. Параметры запуска получает существующий resolver:

```sh
python3 "$AF_PACKAGE/scripts/agent_config.py" --role qa-verifier
```

Передавайте полученные `model`, `reasoning_effort` и ненулевой `service_tier`. Существенный риск можно передать существующим `--trigger`. Не подменяйте модель для обхода ошибки регистрации. Используйте фактический canonical `agent_type`; для обязательного QA/reviewer другая роль не подходит.

Настройка ролей выполняется при установке или обновлении, а не перед каждым назначением:

```sh
python3 "$AF_PACKAGE/scripts/sync-codex-agent-config.py" --output-dir .codex/agents
```

Для `arch-simplicity-guard` экспорт переносит инструкцию вызова селектора. Модельное дополнение не выбирается при экспорте или в пакете задания: архитектор и reviewer получают его внутри собственной текущей сессии по правилам скилла. Это применение в назначенной роли, без дополнительного guard-субагента.

## Пакет задания

Передайте исполнителю:

- цель, источник критериев и относящиеся к нему ограничения;
- ID назначения, роль и ответственность за файлы;
- актуальные исходники, нужный контекст и ссылки на зависимые отчёты;
- разрешённые команды, запреты и доступные доказательства;
- ожидаемый результат и условие остановки.

Не копируйте полный каталог правил в каждое задание. Предупредите, что исполнитель не один в репозитории и не должен откатывать чужие изменения.

После реального запуска зарегистрируйте `assignment` с UUID агента либо его canonical task path, ролью, `kind`, абсолютными `allowed_paths` и `depends_on`. Writer разрешает task path по native-метаданным и сохраняет UUID. Для собственного авторства root допустим `/root`. Регистрация не подменяет запуск агента.

## Владение и интеграция

Назначайте непересекающиеся области записи. На одном пути одновременно работает один исполнитель. Перед последовательной передачей прочитайте текущий файл и сообщите новому владельцу принятый результат предыдущего.

При смене worktree сначала проверьте выбранную базу и объявите новый root в scope. Незавершённое назначение продолжайте через `record --kind transfer` после native-подтверждения остановки прежнего исполнителя. Перенос сопоставляет один репозиторий и относительные области ответственности, не требует старого продуктового отчёта и сохраняет историю. Не регистрируйте временную проверку как нового продуктового автора: используйте check/analysis. Контракт исключения уже ошибочно назначенного временного автора находится в [traceable-runs.md](traceable-runs.md#transfer).

Назначение хранит разрешённую область, отчёт автора — пути его работы; writer проверяет их по native-действиям и границам назначения. Список не строится по изменениям всего репозитория. Не сохраняйте эти сведения в дополнительных представлениях.

Выход за область задачи требует явного изменения назначения или scope до зависимой работы. Архитектурное решение согласуется с его владельцем; исполнитель не добавляет запасные режимы, зависимости и новые контракты ради обхода затруднения.

## Один отчёт

Перед итоговым ответом субагент получает ссылки на свои фактически завершённые действия через `journal.py --run-dir "$RUN_DIR" read native/ASSIGNMENT_ID`. Он берёт `ref` нужного наблюдения, а не UI-маркер `exec-*` из `read_thread`. Затем завершает свой turn одним структурированным JSON-отчётом по [traceable-runs.md](traceable-runs.md). Не создавайте перед этим handoff-файл и не просите агента повторять сгенерированное заключение.

После остановки субагента оркестратор читает то же `native/ASSIGNMENT_ID`, проверяет `completed: true` и использует возвращённый `turn_id` как `completion_turn_id`. Writer проверяет реального исполнителя и принимает его собственный ответ. Зависимости связывают назначения по ID. Для собственного отчёта root получает текущий `turn_id` и refs после правок через это же представление; завершать turn искусственно не нужно.

Представление `native/ID` вычисляется при чтении и не хранит копию сессии, reasoning или raw output. Получение ссылки не заменяет проверку доказательства при принятии отчёта.

Принятые назначения и отчёты неизменяемы. Исправление создаёт новое назначение с новым ID и `previous_assignment_id`, затем новый отчёт. После содержательного исправления результата новые reviewer и QA проверяют затронутую часть. Отклонённое до записи оформление можно исправить без повторения продуктовых действий.

## Независимость и закрытие

Для изменения файлов нужны два отдельных реальных назначения: `reviewer` и `qa-verifier`. Они не являются авторами результата. Reviewer проверяет реализацию и подлинные завершённые авторские отчёты из `depends_on` независимо от их `outcome`; QA начинает после принятого `status: completed, outcome: passed` review и указывает его `assignment_id`. Невыполненные обязательные проверки не получают положительный результат QA.

Если роль или native-доказательства недоступны, не выдавайте положительный итог. Укажите причину и неподтверждённую часть с `outcome: unverified`; выполненное исследование имеет `status: completed`, прерванное — `interrupted`. Оркестратор выбирает дальнейшую работу или запрашивает необходимые сведения, решение либо ручное действие человека по [правилам продолжения](orchestrator.md). Отрицательный результат назначения сам по себе не завершает поручение. При внешнем blocker не организуйте цепочку новых агентов, повторяющих недоступную команду.

Итог оркестратора — вывод по текущим отчётам и критериям. Он не копирует их evidence в новые summary, lane-map или timeline.
