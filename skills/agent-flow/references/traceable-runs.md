# Текущая задача, отчёты и доказательства

Этот документ описывает полный штатный порядок Agent Flow. Команды выполняются установленным пакетом; `AF_PACKAGE` — его абсолютный путь. Примеры используют `~/.agents/skills/agent-flow`. Для плагина возьмите фактический путь выбранного пакета. Не смешивайте две установки.

## Что хранится

Run — текущая задача с одной базой `.journal/state.sqlite3`. SQLite хранит состояние, документы и операции. Отдельные Markdown-отчёты, timeline, копии summary и памяти не поддерживаются; Markdown получается через `read --format markdown`.

Логические записи:

| Путь | Содержание |
| --- | --- |
| `task.json` | Задача и ссылка на раздел требований |
| `scope.json` | Реальные roots, context inputs и начальная опись |
| `assignments/ID.json` | Исполнитель, ответственность, разрешённые пути и зависимости |
| `reports/ID.json` | Один текущий отчёт назначения |
| `checks/ID.json` | Фактическая команда, cwd, exit, отпечаток и ссылка на вывод |
| `generations/OPERATION_ID.json` | Фактический запуск генератора и отпечатки его объявленных изменений |
| `artifacts/...` | Один экземпляр необходимого лога или другого доказательства |
| `final.json` | Только итог завершённой задачи |

`read summary` выводит сводку из текущих записей. `read result` возвращает текущие `fingerprint` и `changed_paths`; `read requirements` — `digest` и критерии `{id,text}`. Это вычисляемые представления, а не дополнительные сохранённые документы.

`read native/ASSIGNMENT_ID` читает native-действия зарегистрированного исполнителя. Для автора доступны действия с начала назначения, включая предыдущие завершённые turn; для QA/reviewer — текущий turn. Представление не сохраняет копию сессии и не принимает доказательства: оно помогает получить точные ссылки для отчёта.

Путь к актуальному native-журналу берётся из `threads.rollout_path` в базе Codex `$CODEX_HOME/state_5.sqlite` (по умолчанию `~/.codex/state_5.sqlite`). База открывается только для чтения. UUID, родитель и роль проверяются по native-метаданным; имя файла не определяет исполнителя. Если источник недоступен или не соответствует назначению, Agent Flow возвращает `execution unconfirmed`, не подставляя старый журнал.

Поддерживается один текущий контракт без миграции старых баз и восстановления поколений. После обновления пакета и синхронизации ролей откройте новый чат. Пользовательские архивы и память проекта автоматически не удаляются.

## Источники и инициализация

Выберите существующую задачу или план с уникальным заголовком задачи и подразделом «Критерии приёмки». В нём должен быть непустой плоский Markdown-список. Например:

```md
## Безопасный запуск CLI

### Критерии приёмки
- Пустой ввод даёт понятную ошибку без traceback.
- Валидный ввод сохраняет прежний результат.
```

Пункты получают `ac-1`, `ac-2` по порядку. Текст и порядок значимы; состояние checkbox не меняет критерий. Изменение других задач и обычных записей прогресса не делает QA неактуальным. Не создавайте отдельный DoD-файл или копию требований в базе.

До инициализации разделите локальную разработку и внешнюю настройку с live-проверками по [implementation-plan-authoring.md](implementation-plan-authoring.md). Выбирайте отдельный `--task-heading` с собственными критериями для каждой части. Локальный прогон не зависит от реальных внешних credentials, доступности сервиса или удалённого CI; внешний прогон сохраняет свои требования и запускается после подготовки окружения. Успешный локальный final не завершает внешнюю часть плана.

Критерии описывают результат и необходимые проверки, например обработку пустого ввода. Порядок приёмки проверяется отдельно: код → review → QA → final. Не включайте успешное прохождение самого QA или последующего final в критерии QA. Содержательные требования пользователя сохраняйте; если они противоречат этому порядку, уточните их до зависимой работы. Writer не удаляет такие пункты автоматически.

```sh
AF_PACKAGE="$HOME/.agents/skills/agent-flow"
python3 -B "$AF_PACKAGE/scripts/init-run.py" \
  --repo "$PWD" --slug cli-input --summary "Проверка пустого ввода CLI" \
  --root-agent-id "$CODEX_THREAD_ID" \
  --requirements .agent-work/tasks/todo.md \
  --task-heading "Безопасный запуск CLI" \
  --memory "$PWD/.agent-work/tasks/lessons.md" \
  --memory "$PWD/.agent-work/tasks/implementation-notes.md" \
  --operation-id cli-input-init
```

Пути памяти в примере должны существовать; ненужные `--memory` опустите. Команда возвращает `run_dir`; сохраните этот путь в `RUN_DIR`. По умолчанию каталог находится в `REPO/.agent-work/runs/YYYY-MM-DD-SLUG`. `--criteria-heading` меняет имя подраздела, если проект использует другое.

`--root-agent-id` берётся из `CODEX_THREAD_ID`, если явно не указан. Это фактический UUID root-сессии, а не произвольное имя. Инициализация проверяет native-сессию.

Основной root — Git checkout. Дополнительные `--root PATH` и `--context PATH` указывают реальные продуктовые каталоги/файлы и нужные контекстные входы. Начальная опись хранит пути, типы, отпечатки, права обычных файлов и строки target симлинков. Содержимое исходников и Git objects не копируется.

Git-опись учитывает tracked и неигнорируемые untracked. Нужные ignored-файлы включаются явно через scope. Зависимости и результаты сборок не становятся входами только потому, что лежат на диске. Вложенный Git root объявляется отдельно. Вне Git учитывайте только явно выбранные дополнительные файлы или область.

`--memory PATH` перечисляет существующие файлы постоянной памяти. Источник требований включается автоматически. Они не входят целиком в продуктовый отпечаток: хешируются выбранные критерии, а не вся история To Do. Другие изменения памяти не инвалидируют QA.

Опись не содержит исходных dirty bytes. Agent Flow не умеет автоматически восстановить старые незакоммиченные строки и не доказывает сохранность каждого старого фрагмента. Редактируйте точечно и проверяйте сохранность пользовательской работы при ревью.

## Регистрация и чтение

У изменяющей команды обязателен известный `--operation-id`. Для точного технического повтора сохраните ID и аргументы. JSON можно передать через stdin; дополнительные request-файлы не требуются.

`journal.py contract` — справка по текущим полям, а не обязательный шаг перед каждой записью:

```sh
python3 -B "$AF_PACKAGE/scripts/journal.py" contract
python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" read summary
python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" read result
python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" read requirements
python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" read native/author
```

`record` принимает `assignment`, `scope`, `report`, `check` и `generation`.

### Получение native-ссылок

После нужного действия прочитайте `native/ID` своего назначения. Ответ имеет форму:

```json
{
  "assignment_id": "author",
  "thread_id": "ACTUAL_AGENT_UUID",
  "turn_id": "ACTUAL_CURRENT_TURN_UUID",
  "completed": false,
  "observations": [
    {
      "ref": {"thread_id": "ACTUAL_AGENT_UUID", "turn_id": "ACTUAL_CURRENT_TURN_UUID", "call_id": "ACTUAL_NATIVE_CALL_ID"},
      "name": "apply_patch",
      "success": true,
      "authored_paths": ["/absolute/repo/cli.py"]
    }
  ]
}
```

В `observations` входят завершённые пары call/output и поддерживаемые native items. Для автора список охватывает turn от сохранённого `start_turn_id` назначения до последнего turn включительно; предыдущие turn должны быть завершены. Каждая ссылка сохраняет исходный `turn_id` действия. Верхние `turn_id` и `completed` всегда описывают последний turn. Поле `success` отражает доступное подтверждение действия; применимость к критерию проверяет QA. Содержимое reasoning и raw output сюда не копируется.

Редактирование может быть представлено native item `FileChange`. Его готовый `ref` содержит `thread_id`, `turn_id`, `item_id` вместо `call_id`; `authored_paths` перечисляет подтверждённые пути. Берите этот ref из списка целиком, не преобразуйте item ID в call ID и не указывайте оба поля одновременно.

Вывод инструмента, содержащий только изображение либо смесь текста с изображением, остаётся в списке с `success: false` и `reason`: он недоступен для прямой текстовой проверки. Такая ссылка не принимается как непосредственное доказательство. Это не удаляет остальные наблюдения и не обязательно означает сбой самого действия. Используйте другое фактическое доказательство нужного результата, не пересказ изображения.

Берите `ref` целиком из нужного наблюдения. UI-маркер действия вида `exec-*` из `read_thread` не является native `call_id`. Не вычисляйте ID и не ищите session-файлы вручную.

Автор читает представление после `apply_patch`. QA и reviewer читают свои наблюдения после исследования результата. Субагент получает эти ссылки до собственного итогового JSON-ответа. После завершения субагента оркестратор снова читает `native/ID`: при `completed: true` его `turn_id` используется как `completion_turn_id` при регистрации единственного отчёта.

### assignment

```json
{
  "id": "author",
  "role": "python-worker",
  "agent_id": "ACTUAL_AGENT_UUID",
  "kind": "author",
  "allowed_paths": ["/absolute/repo/cli.py", "/absolute/repo/tests/test_cli.py"],
  "depends_on": []
}
```

`kind`: `author`, `qa`, `reviewer` либо `analysis`. Автору нужны разрешённые абсолютные пути. Для analysis/QA/reviewer область записи обычно пуста. Для QA используется роль `qa-verifier`, для reviewer — `reviewer`. Зависимости ссылаются на уже зарегистрированные назначения. У QA в `depends_on` обязательно указан reviewer с актуальным принятым `completed`-отчётом; без него регистрация QA отклоняется.

Запускайте субагента реальным инструментом среды, с инструкциями роли и параметрами существующего `agent_config.py`. Затем передайте фактический UUID либо canonical task path провайдера, например `/root/worker`. Writer разрешает путь по native-метаданным и сохраняет UUID; искать session-файлы вручную не нужно. `/root` обозначает зарегистрированный root. Для собственного авторства используйте его идентичность и соответствующую роль автора.

Регистрируйте авторское назначение в turn начала его работы, до правок. При первой регистрации writer сам сохраняет `start_turn_id` из последнего собственного `task_started` исполнителя. Повтор не сдвигает эту границу; перед новым заданием тому же исполнителю начните новый turn. Отчёт может использовать подтверждённые действия с этой границы, но не произвольную историю автора.

Один путь одновременно имеет одного автора. Последовательная передача требует принятого отчёта предшественника и явной зависимости нового назначения.

### scope

```json
{
  "roots": [{"path": "/absolute/repo", "include": ["ignored-input.json"]}],
  "context": ["/absolute/spec/contract.md"]
}
```

Добавляет область, не заменяя начальную опись уже известных путей. `include` — явные относительные пути внутри root. Новый продуктовый root можно указать без `include`. Изменение scope требует актуальных зависимых проверок и заключений.

### report

Субагент получает evidence refs через `read native/ID` и завершает turn собственным JSON-отчётом. Оркестратор после остановки читает то же представление, проверяет `completed: true` и регистрирует только источник отчёта:

```json
{"assignment_id": "author", "completion_turn_id": "ACTUAL_COMPLETED_TURN_UUID"}
```

Writer читает фактический ответ, проверяет исполнителя, ancestry, роль и последний завершённый turn. После начала продолжения старый completion не принимается. Не передавайте заранее созданный handoff или поддельный completion.

Основной агент ещё не завершил свой turn. Для его собственного отчёта используется другая форма:

```json
{
  "assignment_id": "author",
  "turn_id": "ACTUAL_CURRENT_TURN_UUID",
  "report": {
    "status": "completed",
    "summary": "Обработан пустой ввод, добавлена проверка причины ошибки.",
    "evidence": [
      {"thread_id": "ACTUAL_ROOT_UUID", "turn_id": "ACTUAL_CURRENT_TURN_UUID", "call_id": "ACTUAL_EDIT_CALL_ID"}
    ],
    "authored_paths": ["/absolute/repo/cli.py", "/absolute/repo/tests/test_cli.py"]
  }
}
```

Для root значения `turn_id` и evidence refs берутся из `read native/author` после фактических правок. Writer проверяет реальные уже выполненные native-действия. Дополнительный worker ради завершённого turn не нужен. Для собственного анализа root используется `kind: analysis` и та же форма запроса с `turn_id` и отчётом; нужны собственные native-доказательства исследования, а `authored_paths` не требуется.

Если отчёт автора отклонён из-за оформления, продолжите то же назначение. Субагент возвращает исправленный JSON в новом завершённом native-ответе; root регистрирует исправленный отчёт из своего текущего turn. Передайте новый operation ID и сохраните действительные ссылки на прежние действия с начала назначения. Например, после отказа из-за `summary`-объекта верните в следующем turn непустую строку `summary`, не меняя исходники и не запуская генератор повторно. Writer проверяет исходные события, допустимые пути и актуальность outputs; исправление отчёта не создаёт авторство. Для нового отчёта QA/reviewer требуется собственное исследование в его turn.

### check

```json
{
  "id": "cli-tests",
  "assignment_id": "qa",
  "command": ["python3", "-m", "unittest", "discover", "-s", "tests"],
  "cwd": "/absolute/repo",
  "timeout": 300
}
```

Writer сам выполняет команду один раз и сохраняет фактические cwd, exit и stdout/stderr. `timeout` необязателен, по умолчанию 300 секунд. Не передавайте свой exit code и не запускайте ту же команду отдельно перед регистрацией.

Команда должна быть разрешена пользователем. Проверка выполняется в выбранном checkout; её временные игнорируемые outputs допустимы, изменение продуктовых входов требует разбирательства и новой актуальной проверки.

Результат хранится в `checks/cli-tests.json`, полный вывод — один раз в `artifacts/checks/cli-tests.log`. Повторная реальная проверка получает новый check ID и operation ID. Точный повтор записи завершённой операции возвращает сохранённый результат.

### generation

Для разрешённого генератора или форматтера, который меняет продуктовые файлы, используйте `record --kind generation`. Запускает его сам назначенный автор, пока никто другой не меняет продуктовые входы. В request передаются `assignment_id`, `command` как argv, абсолютный `cwd`, непустой список `outputs` с точными абсолютными путями файлов и необязательный `timeout` в секундах, по умолчанию 300. Outputs должны входить в scope и разрешённую область автора; каталог вместо списка файлов не подходит.

Writer выполняет команду один раз внутри `BEGIN IMMEDIATE`. Он сравнивает исходные и итоговые отпечатки, сохраняет фактический exit и полный вывод. Изменение неуказанного продуктового файла, context input или выбранных критериев отклоняет запись. Это не sandbox: при отказе, timeout или прерывании изменённые файлы остаются на месте. Сохранённых исходных bytes и автоматического rollback файлов нет.

Чтобы связать реальный запуск с автором, используйте каноническую команду writer. Получите абсолютные `python` и `journal` из `journal.py contract`, раздел `generation_invocation`. В инструменте выполнения задайте `shell: /bin/zsh`, `login: true`. Подставьте реальные абсолютные пути вместо путей примера до запуска; порядок аргументов и literal delimiter оставьте как показано. JSON допускает другое форматирование пробелами и сравнивается с фактическим request.

```sh
/absolute/runtime/bin/python3 -B /absolute/package/scripts/journal.py --run-dir /absolute/repo/.agent-work/runs/TASK record --kind generation --request-file - --operation-id generate-client <<'AF_GENERATION_REQUEST'
{"assignment_id":"author","command":["/absolute/runtime/bin/python3","tools/generate_client.py"],"cwd":"/absolute/repo","outputs":["/absolute/repo/generated/client.py"]}
AF_GENERATION_REQUEST
```

Не добавляйте к этой команде shell-префиксы, перестановку flags или оболочку-скрипт. `--run-dir` должен быть каноническим абсолютным путём. Для обычной работы импортировать внутренние Python helpers не требуется.

При фактическом выполнении stdout содержит `{"executed":true,"receipt":...}`. Повтор завершённой операции возвращает `executed: false` и прежний receipt; он не подтверждает новый запуск или авторство. Сама запись находится в `generations/OPERATION_ID.json`, вывод — в `artifacts/generations/OPERATION_ID.log`. В записи хранится фактический exit, а наличие receipt не означает exit 0.

После выполнения автор читает `native/ID` своего назначения. Готовый `observations[].ref` для generation содержит путь и SHA записи вместе с `native`-ссылкой на фактический `CommandExecution` item. Авторство подтверждается только для фактически изменившихся outputs успешной команды; пустая разница авторства не создаёт. Если файл изменён после генерации, для его текущего состояния нужно новое доказательство; подтверждение остальных outputs сохраняется. Этот ref не заменяет тест или успешную QA-проверку. Не используйте повтор `executed: false` как новое доказательство.

Если команда могла выполниться до сбоя публикации, сначала проверьте native-выполнение и файлы. Отсутствие receipt не даёт гарантии, что команда не запускалась, и не разрешает слепой повтор. Для обычного `check` правило прежнее: продуктовые входы изменять нельзя.

## Один отчёт исполнителя

Обязательные поля всех отчётов: `status`, `summary`, `evidence`. `summary` — непустая строка, не объект и не массив. Допустимые статусы — `completed` и `failed`; при `failed` нужна содержательная `reason`. Анализ, архитектурный вывод и полезные ограничения помещаются в summary без обязательного набора секций.

Доказательство имеет одну из форм:

```json
{"path": "checks/cli-tests.json", "sha256": "SHA_FROM_ACCEPTED_RECORD"}
```

```json
{"thread_id": "ACTUAL_UUID", "turn_id": "ACTUAL_TURN_UUID", "call_id": "ACTUAL_CALL_ID"}
```

Для native FileChange item:

```json
{"thread_id": "ACTUAL_UUID", "turn_id": "ACTUAL_TURN_UUID", "item_id": "ACTUAL_FILE_CHANGE_ITEM_ID"}
```

Для фактически выполненного generation writer возвращает через `read native/ID` готовую составную ссылку:

```json
{"path": "generations/generate-client.json", "sha256": "GENERATION_RECORD_SHA", "native": {"thread_id": "ACTUAL_UUID", "turn_id": "ACTUAL_TURN_UUID", "item_id": "ACTUAL_COMMAND_ITEM_ID"}}
```

Ссылки на записи берите из результатов writer, native-ссылки — из `read native/ID`. Writer проверяет содержимое и источник. Разрешение выполнить команду и её пересказ не являются доказательством выполнения. QA и reviewer включают собственное успешное native-действие проверки из turn нового отчёта: это подтверждает, что каждый действительно исследовал результат. Одного опубликованного пересказа недостаточно.

Автор добавляет `authored_paths` с фактически изменёнными абсолютными путями и ссылается на собственные действия редактирования: `apply_patch`, native FileChange либо штатный `generation`. Произвольный shell-скрипт записи сам по себе не подтверждает затронутые пути.

После остановки правок reviewer проверяет текущий код и принятые `completed`-отчёты авторов. Он возвращает fingerprint и свои доказательства; writer сам привязывает review к точным SHA авторских отчётов. Поля `qa` в отчёте reviewer нет:

```json
{
  "status": "completed",
  "summary": "Проверены реализация, сохранность пользовательских изменений и простота решения.",
  "evidence": [
    {"thread_id": "ACTUAL_REVIEWER_UUID", "turn_id": "ACTUAL_REVIEWER_TURN_UUID", "call_id": "ACTUAL_REVIEWER_INSPECTION_CALL_ID"}
  ],
  "fingerprint": "CURRENT_RESULT_FINGERPRINT"
}
```

После исправления замечаний продолжите того же reviewer в том же `assignment_id`. Он заново исследует результат в новом turn и возвращает отчёт с собственными свежими доказательствами. Зарегистрируйте его с новым operation ID: writer заменит прежний отчёт и привяжет review к актуальным SHA всех авторских отчётов. Не меняйте `depends_on` существующего назначения ради новых авторских отчётов и не создавайте второе назначение для повторной проверки той же ответственности. Новое назначение требуется при смене исполнителя или ответственности.

Только после актуального `completed` review запускается QA. В отчёт QA входят тот же `fingerprint`, точная ссылка `reviewer` и исходы каждого критерия. При повторной проверке QA указывает SHA обновлённого review. SHA review берётся из результата регистрации либо `read summary`; вручную вычислять и переписывать служебные поля не нужно.

```json
{
  "status": "completed",
  "summary": "Пустой и валидный ввод проверены штатными тестами.",
  "evidence": [
    {"path": "checks/cli-tests.json", "sha256": "CHECK_RECORD_SHA"},
    {"thread_id": "ACTUAL_QA_UUID", "turn_id": "ACTUAL_QA_TURN_UUID", "call_id": "ACTUAL_QA_INSPECTION_CALL_ID"}
  ],
  "fingerprint": "CURRENT_RESULT_FINGERPRINT",
  "reviewer": {"assignment_id": "reviewer", "sha256": "ACCEPTED_REVIEWER_REPORT_SHA"},
  "criteria": {
    "ac-1": {"status": "passed", "evidence": [{"path": "checks/cli-tests.json", "sha256": "CHECK_RECORD_SHA"}]},
    "ac-2": {"status": "passed", "evidence": [{"path": "checks/cli-tests.json", "sha256": "CHECK_RECORD_SHA"}]}
  }
}
```

Исход критерия — `passed`, `failed` или `unverified`. Для `unverified` обязательна непустая `reason`; поле `evidence` можно опустить или передать пустым массивом. Переданные ссылки проверяются, но не меняют исход на `passed`. Общие `evidence` самого QA-отчёта остаются обязательными и подтверждают его фактическое исследование задачи. Для `passed` нужна успешная фактическая проверка: writer check либо native inspection, относящаяся к критерию. Один текстовый artifact этого не доказывает. Пример выше ссылается на один check без копирования его вывода.

Пример исхода критерия, для которого проверка запрещена:

```json
{
  "ac-3": {
    "status": "unverified",
    "reason": "Пользователь запретил запуск необходимого интеграционного теста."
  }
}
```

Регистрация отчёта сохраняет его результат, включая `failed`, и не означает успешную приёмку. Для `final: completed` нужны актуальный успешный review и QA со всеми критериями `passed`. QA и reviewer независимы друг от друга и от всех авторов.

До final исправленный отчёт заменяет текущий отчёт назначения. Предыдущее тело не архивируется. Изменение результата или авторского отчёта делает review неактуальным; замена review делает связанный QA неактуальным. Обновите только затронутые доказательства, затем повторно примите review и QA.

## Нормальный порядок на примере

1. Выберите раздел задачи из примера выше. Инициализируйте её и сохраните выданный `RUN_DIR`.
2. Зарегистрируйте author: это реально запущенный worker либо root, который сам пишет код. Передайте корректный request через:

   ```sh
   python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" \
     record --kind assignment --request-file - --operation-id cli-author-assignment
   ```

   В stdin подайте JSON assignment из раздела выше с фактическими UUID и путями.
3. Выполните правку. При необходимости автор запускает writer check под своим зарегистрированным назначением один раз в пределах разрешений; повтор ради отчёта не нужен. QA выполняет свои проверки после review на шагах 5–6. Прочитайте `native/author` после правки и возьмите её `ref`. Для root это также источник текущего `turn_id`. Для worker после его JSON-ответа дождитесь `completed: true` в том же представлении. Зарегистрируйте один отчёт автора:

   ```sh
   python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" \
     record --kind report --request-file - --operation-id cli-author-report
   ```

4. Остановите авторские правки и убедитесь, что отчёт автора принят как `completed`. Реально запустите независимого `reviewer`, передайте критерии, scope, текущие файлы и отчёт автора. Зарегистрируйте assignment `reviewer`, `kind: reviewer`, с зависимостью `["author"]`. Reviewer проверяет код и отчёт автора, получает свои refs через `read native/reviewer` и возвращает JSON с fingerprint. После его остановки возьмите `turn_id` при `completed: true` из этого представления и примите отчёт через `record --kind report` с новым operation ID. При замечаниях автор исправляет код и заменяет отчёт, затем reviewer проверяет исправление.
5. Только после актуального `completed` review запустите независимого `qa-verifier`. Зарегистрируйте assignment `qa`, `kind: qa`, с зависимостью `["reviewer"]`. Передайте критерии, scope, текущие файлы, авторский отчёт и точные SHA review и fingerprint. Не оформляйте review или QA как `analysis` для обхода этого порядка.
6. QA читает `result`, `requirements`, принятый review и доказательства. Если автор уже выполнил нужный check на том же текущем fingerprint, QA проверяет его применимость и использует существующую запись. Только недостающую или затронутую изменением проверку выполняйте через writer:

   ```sh
   python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" \
     record --kind check --request-file - --operation-id cli-tests-execution
   ```

   В stdin подаётся check request, а SHA берётся из результата записи. Собственное native-исследование QA обязательно, но им может быть чтение кода, результата и доказательств, а не повтор теста. QA получает свои refs через `read native/qa`, затем возвращает единственный native JSON-отчёт со ссылкой `reviewer`. Оркестратор после его остановки читает `native/qa`, проверяет `completed: true` и регистрирует выданный `turn_id` через `record --kind report` с новым operation ID.
7. Проверьте результат зарегистрированного QA. При обнаруженном дефекте верните его тому же исполнителю: он исправляет код и заменяет свой отчёт, reviewer проверяет исправление, затем QA повторяет затронутые проверки и заменяет своё заключение со ссылкой на новое review. Если обязательная проверка запрещена или недоступна, QA сообщает `failed`, а её критерии — `unverified` с причиной. Не отправляйте код на переделку без найденного дефекта. Запросите только недостающее решение; установленный запрет соблюдайте. Во время ожидания не создавайте final. При завершении без необходимой проверки используйте `finalize --status failed`, как показано ниже.
8. После актуальных `completed` review и QA со всеми критериями `passed` проверьте сводку и завершите. Дополнительный reviewer после QA не нужен:

   ```sh
   python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" read summary --format markdown
   python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" \
     finalize --status completed --summary "Критерии CLI выполнены; review и QA приняты." \
     --operation-id cli-final
   ```

Значения UUID, call IDs, fingerprints и SHA в примерах — места для фактических значений инструментов. Не сохраняйте их буквальными placeholders. Команды демонстрируют контракт, но не утверждают, что конкретный тест был выполнен.

Если критерии не подтверждены:

```sh
python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" \
  finalize --status failed --summary "Результат не принят." \
  --reason "Обязательный сценарий нельзя проверить в разрешённой среде." \
  --unverified "Поведение CLI на целевой платформе" --operation-id cli-final-failed
```

## Артефакты, свежесть и прерывания

Для необходимого готового файла используйте:

```sh
python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" \
  publish --file artifacts/screenshot.png /absolute/screenshot.png --operation-id cli-screenshot
```

`publish` не записывает отчёты, назначения и final. Не публикуйте копию уже сохранённого check log. Читайте записи через `read`, а не ручное редактирование базы или экспорта.

Отпечаток включает текущие продуктовые входы, scope и выбранные критерии. QA и reviewer проверяют одно состояние; перед final код сверяет его снова. SQLite lock защищает запись в базе, но не запрещает внешнему редактору изменить исходник.

Операции используют существующие SQLite-транзакции, rollback и durability. Отчёт и результат операции сохраняются согласованно. Точный повтор с тем же ID возвращает сохранённый результат; другие аргументы с тем же ID отклоняются. После `BUSY` выясните исход первой попытки, затем повторите явную операцию со свежими входами, если она не завершилась. Автоматического цикла повторов нет.

Команда могла завершиться до сбоя публикации. Отсутствие receipt не разрешает повторять её вслепую: сначала прочитайте native-вывод и проверьте фактическое состояние. Если результат восстановить нельзя, укажите неподтверждённую часть.

Final отсутствует до завершения. После его принятия задача закрыта: доступны чтение и точный повтор завершённых операций, но не новые изменения или повторное открытие.
