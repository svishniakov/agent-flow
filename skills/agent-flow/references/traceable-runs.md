# Текущая задача, отчёты и доказательства

Этот документ описывает полный штатный порядок Agent Flow. Команды выполняются установленным пакетом; `AF_PACKAGE` — его абсолютный путь. Примеры используют `~/.agents/skills/agent-flow`. Для плагина возьмите фактический путь выбранного пакета. Не смешивайте две установки.

## Что хранится

Run — текущая задача с одной базой `.journal/state.sqlite3`. SQLite хранит состояние, документы и операции. Отдельные Markdown-отчёты, timeline, копии summary и памяти не поддерживаются; Markdown получается через `read --format markdown`.

Логические записи:

| Путь | Содержание |
| --- | --- |
| `task.json` | Версия контракта, задача и ссылка на раздел требований |
| `scope.json` | Пути рабочих roots, контекста и памяти |
| `assignments/ID.json` | Исполнитель, ответственность, разрешённые пути и зависимости |
| `reports/ID.json` | Неизменяемый принятый отчёт назначения |
| `checks/ID.json` | Фактическая команда, cwd, exit и ссылка на вывод |
| `generations/OPERATION_ID.json` | Запрос генератора, команда, заявленные outputs, exit и ссылка на вывод |
| `transfers/OPERATION_ID.json` | Неизменяемый перенос назначения или подтверждённое исключение временного автора |
| `artifacts/...` | Один экземпляр необходимого лога или другого доказательства |
| `final.json` | Только итог завершённой задачи |

`read summary` выводит сводку из текущих записей, включая переносы. `read result` возвращает `authored_paths` текущего продуктового результата с учётом переносов; `read requirements` читает критерии `{id,text}` из выбранного раздела документа. Это вычисляемые представления, а не дополнительные сохранённые документы. Список результата не строится по diff всего репозитория. Отдельную transfer-запись можно прочитать по её логическому пути.

`read native/ASSIGNMENT_ID` читает native-действия зарегистрированного исполнителя. Для автора доступны действия с начала назначения, включая предыдущие завершённые turn; для QA/reviewer — текущий turn. Представление не сохраняет копию сессии и не принимает доказательства: оно помогает получить точные ссылки для отчёта.

Путь к актуальному native-журналу берётся из `threads.rollout_path` в базе Codex `$CODEX_HOME/state_5.sqlite` (по умолчанию `~/.codex/state_5.sqlite`). База открывается только для чтения. UUID, родитель и роль проверяются по native-метаданным; имя файла не определяет исполнителя. Если источник недоступен или не соответствует назначению, Agent Flow возвращает `execution unconfirmed`, не подставляя старый журнал.

Новые задачи используют `contract_version: 2` в `task.json`. Старые журналы доступны только для чтения без преобразования; запись отклоняется. После обновления пакета и синхронизации ролей откройте новый чат. Пользовательские архивы и память проекта автоматически не удаляются.

## Источники и инициализация

Выберите существующую задачу или план с уникальным заголовком задачи и подразделом «Критерии приёмки». В нём должен быть непустой плоский Markdown-список. Например:

```md
## Безопасный запуск CLI

### Критерии приёмки
- Пустой ввод даёт понятную ошибку без traceback.
- Валидный ввод сохраняет прежний результат.
```

Пункты получают `ac-1`, `ac-2` по порядку; состояние checkbox не меняет критерий. Источник требований определяется путём документа и названием выбранного раздела. Критерии читаются из него без отслеживания изменений содержимого. Не создавайте отдельный DoD-файл или копию требований в базе.

До инициализации разделите локальную разработку и внешнюю настройку с live-проверками по [implementation-plan-authoring.md](implementation-plan-authoring.md). Выбирайте отдельный `--task-heading` с собственными критериями для каждой части. Локальный прогон не зависит от реальных внешних credentials, доступности сервиса или удалённого CI; внешний прогон сохраняет свои требования и запускается после подготовки окружения. Успешный локальный final не завершает внешнюю часть плана.

Критерии описывают результат и необходимые проверки, например обработку пустого ввода. Порядок приёмки проверяется отдельно: код → review → QA → final. Не включайте успешное прохождение самого QA или последующего final в критерии QA. Содержательные требования пользователя сохраняйте; если они противоречат этому порядку, уточните их до зависимой работы. Writer не удаляет такие пункты автоматически.

```sh
AF_PACKAGE="$HOME/.agents/skills/agent-flow"
python3 -B "$AF_PACKAGE/scripts/init-run.py" \
  --repo "$PWD" --slug cli-input --summary "Проверка пустого ввода CLI" \
  --root-agent-id "$CODEX_THREAD_ID" \
  --requirements .agent-work/tasks/todo.md \
  --task-heading "Безопасный запуск CLI" \
  --memory "$PWD/.agent-work/tasks/lessons.md" \
  --memory "$PWD/.agent-work/tasks/implementation-notes.md" \
  --operation-id cli-input-init
```

Пути памяти в примере должны существовать; ненужные `--memory` опустите. Команда возвращает `run_dir`; сохраните этот путь в `RUN_DIR`. По умолчанию каталог находится в `REPO/.agent-work/runs/YYYY-MM-DD-SLUG`. `--criteria-heading` меняет имя подраздела, если проект использует другое.

`--root-agent-id` берётся из `CODEX_THREAD_ID`, если явно не указан. Это фактический UUID root-сессии, а не произвольное имя. Инициализация проверяет native-сессию.

Основной root — Git checkout. Дополнительные `--root PATH` и `--context PATH` указывают реальные продуктовые каталоги/файлы и нужный контекст. `--memory PATH` перечисляет существующие файлы постоянной памяти. Источник требований включается автоматически. Это обычные пути: Agent Flow не создаёт опись репозитория, не копирует исходники и не отслеживает их содержимое, время изменения, размеры или версии.

Каждый автор указывает собственные пути в отчёте. Изменения соседних задач не включаются в его результат и не отменяют его проверки. Редактируйте точечно и проверяйте сохранность пользовательской работы при ревью.

## Регистрация и чтение

У изменяющей команды обязателен известный `--operation-id`. Для точного технического повтора сохраните ID и аргументы. JSON можно передать через stdin; дополнительные request-файлы не требуются.

`journal.py contract` — справка по текущим полям, а не обязательный шаг перед каждой записью:

```sh
python3 -B "$AF_PACKAGE/scripts/journal.py" contract
python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" read summary
python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" read result
python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" read requirements
python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" read native/author
```

`record` принимает `assignment`, `scope`, `report`, `check`, `generation` и `transfer`.

### Получение native-ссылок

После нужного действия прочитайте `native/ID` своего назначения. Ответ имеет форму:

```json
{
  "assignment_id": "author",
  "thread_id": "ACTUAL_AGENT_UUID",
  "turn_id": "ACTUAL_CURRENT_TURN_UUID",
  "completed": false,
  "observations": [
    {
      "ref": {"thread_id": "ACTUAL_AGENT_UUID", "turn_id": "ACTUAL_CURRENT_TURN_UUID", "call_id": "ACTUAL_NATIVE_CALL_ID"},
      "name": "apply_patch",
      "success": true,
      "authored_paths": ["/absolute/repo/cli.py"]
    }
  ]
}
```

В `observations` входят завершённые пары call/output и поддерживаемые native items. Для автора список охватывает turn от сохранённого `start_turn_id` назначения до последнего turn включительно; предыдущие turn должны быть завершены. Каждая ссылка сохраняет исходный `turn_id` действия. Верхние `turn_id` и `completed` всегда описывают последний turn. Поле `success` отражает доступное подтверждение действия; применимость к критерию проверяет QA. Содержимое reasoning и raw output сюда не копируется.

Редактирование может быть представлено native item `FileChange` или распознанным `CommandExecution`: добавление, изменение, перемещение и удаление, включая бинарные файлы и отдельный вызов `apply_patch` через shell с повышенными правами. Принимаются точные пути, поддерживаемая форма команды и подтверждённое исполнение. Произвольный shell, напечатанное сообщение об успехе или один `exit 0` авторство не доказывают. Готовый `ref` содержит `thread_id`, `turn_id`, `item_id` вместо `call_id`; `authored_paths` перечисляет подтверждённые пути. Берите ref из списка целиком, не преобразуйте item ID в call ID и не указывайте оба поля одновременно. Прежнее действие проверяется по native-записи без повторного исполнения; неподдерживаемое доказательство остаётся неподтверждённым.

Вывод инструмента, содержащий только изображение либо смесь текста с изображением, остаётся в списке с `success: false` и `reason`: он недоступен для прямой текстовой проверки. Такая ссылка не принимается как непосредственное доказательство. Это не удаляет остальные наблюдения и не обязательно означает сбой самого действия. Используйте другое фактическое доказательство нужного результата, не пересказ изображения.

Берите `ref` целиком из нужного наблюдения. UI-маркер действия вида `exec-*` из `read_thread` не является native `call_id`. Не вычисляйте ID и не ищите session-файлы вручную.

Автор читает представление после `apply_patch`. QA и reviewer читают свои наблюдения после исследования результата. Субагент получает эти ссылки до собственного итогового JSON-ответа. После завершения субагента оркестратор снова читает `native/ID`: при `completed: true` его `turn_id` используется как `completion_turn_id` при регистрации единственного отчёта.

### assignment

```json
{
  "id": "author",
  "role": "python-worker",
  "agent_id": "ACTUAL_AGENT_UUID",
  "kind": "author",
  "allowed_paths": ["/absolute/repo/cli.py", "/absolute/repo/tests/test_cli.py"],
  "depends_on": []
}
```

`kind`: `author`, `qa`, `reviewer` либо `analysis`. Автору нужны разрешённые абсолютные пути. Для analysis/QA/reviewer область записи обычно пуста. Для QA используется роль `qa-verifier`, для reviewer — `reviewer`. Зависимости ссылаются на уже зарегистрированные назначения. Reviewer перечисляет проверяемые авторские назначения в `depends_on`. У QA в `depends_on` обязательно указан reviewer с принятым `status: completed, outcome: passed`; без него регистрация QA отклоняется.

Принятое назначение не изменяется. Новая попытка получает новый `id` и необязательный `previous_assignment_id` со ссылкой на предыдущее назначение с принятым отчётом. Эта ссылка сохраняет историю итераций и не заменяет `depends_on`.

У автора-преемника `allowed_paths` должны покрывать всю область предшественника теми же путями или содержащими их каталогами; ссылка не позволяет отбросить прежнюю ответственность.

Запускайте субагента реальным инструментом среды, с инструкциями роли и параметрами существующего `agent_config.py`. Затем передайте фактический UUID либо canonical task path провайдера, например `/root/worker`. Writer разрешает путь по native-метаданным и сохраняет UUID; искать session-файлы вручную не нужно. `/root` обозначает зарегистрированный root. Для собственного авторства используйте его идентичность и соответствующую роль автора.

Регистрируйте авторское назначение в turn начала его работы, до правок. При первой регистрации writer сам сохраняет `start_turn_id` из последнего собственного `task_started` исполнителя. Повтор не сдвигает эту границу; перед новым заданием тому же исполнителю начните новый turn. Отчёт может использовать подтверждённые действия с этой границы, но не произвольную историю автора.

Один путь одновременно имеет одного автора. После завершённого назначения передача требует принятого отчёта предшественника и явной зависимости. Для продолжения незавершённого назначения в другом worktree используйте `transfer`.

### transfer

Перенос сохраняет старое назначение и атомарно создаёт новое вместе с `transfers/OPERATION_ID.json`. Он не копирует файлы. Новый root сначала объявляется через `scope`.

```json
{
  "from_assignment_id": "author-old",
  "purpose": "continue",
  "new_assignment": {
    "id": "author-new",
    "role": "python-worker",
    "agent_id": "/root/worker_new",
    "kind": "author",
    "allowed_paths": ["/absolute/new-worktree/cli.py"],
    "depends_on": []
  },
  "root_map": [{"from": "/absolute/old-worktree", "to": "/absolute/new-worktree"}]
}
```

`purpose: continue` используется по умолчанию. Карта roots должна связывать worktree одного репозитория по каноническому Git common-dir и сохранять относительные пути всей ответственности автора. Несвязанный репозиторий, потеря пути или root вне scope отклоняются. При смене исполнителя его последний собственный native-turn должен завершиться `task_complete` либо `turn_aborted` без более нового `task_started`. При продолжении тем же исполнителем прежний turn должен завершиться до начала turn преемника. Writer сохраняет подтверждение остановки в `stopped`. Принятый отчёт прежнего назначения не требуется. После переноса новые report/check/generation от него запрещены; чтение истории и точные повторы операций доступны. `finalize` проверяет преемника, сохраняя прежние замечания и их разрешение через QA.

Для временных проверок используйте check/analysis без продуктового авторства. Если временная работа уже ошибочно зарегистрирована автором, исключение требует отдельного переноса:

```json
{
  "from_assignment_id": "temporary-author",
  "purpose": "verification_only",
  "reason": "Назначение выполняло только проверку во временном каталоге.",
  "evidence": [{"path": "checks/temporary-scope-inspection.json"}],
  "reviewer_assignment_id": "temporary-scope-review"
}
```

Здесь `new_assignment` и `root_map` не передаются. Независимый reviewer должен иметь принятый `status: completed, outcome: passed` отчёт с `verification_only: ["temporary-author"]` и собственным успешным native-исследованием, подтверждающим отсутствие потери продуктового результата. Writer проверяет остановку прежнего исполнителя, доказательства и заключение reviewer; исключение сохраняется неизменяемой записью и не удаляет историю. Повтор с тем же `operation-id` и payload возвращает прежний receipt; другой payload или конфликт `revision` отклоняется.

### scope

```json
{
  "roots": [{"path": "/absolute/additional-inputs", "include": ["contract.json"]}],
  "context": ["/absolute/spec/contract.md"]
}
```

Добавляет пути в область задачи. Для Git root область охватывает весь root. В root вне Git `include` ограничивает область перечисленными относительными путями; без `include` доступен весь root. Содержимое этих путей не сканируется. Если работа расширяется, передайте новые границы исполнителям и проверьте добавленную часть результата.

### report

Субагент получает evidence refs через `read native/ID` и завершает turn собственным JSON-отчётом. Оркестратор после остановки читает то же представление, проверяет `completed: true` и регистрирует только источник отчёта:

```json
{"assignment_id": "author", "completion_turn_id": "ACTUAL_COMPLETED_TURN_UUID"}
```

Writer читает фактический ответ, проверяет исполнителя, ancestry, роль и последний завершённый turn. После начала продолжения старый completion не принимается. Не передавайте заранее созданный handoff или поддельный completion.

Основной агент ещё не завершил свой turn. Для его собственного отчёта используется другая форма:

```json
{
  "assignment_id": "author",
  "turn_id": "ACTUAL_CURRENT_TURN_UUID",
  "report": {
    "status": "completed",
    "outcome": "passed",
    "summary": "Обработан пустой ввод, добавлена проверка причины ошибки.",
    "evidence": [
      {"thread_id": "ACTUAL_ROOT_UUID", "turn_id": "ACTUAL_CURRENT_TURN_UUID", "call_id": "ACTUAL_EDIT_CALL_ID"}
    ],
    "authored_paths": ["/absolute/repo/cli.py", "/absolute/repo/tests/test_cli.py"]
  }
}
```

Для root значения `turn_id` и evidence refs берутся из `read native/author` после фактических правок. Writer проверяет реальные уже выполненные native-действия. Дополнительный worker ради завершённого turn не нужен. Для собственного анализа root используется `kind: analysis` и та же форма запроса с `turn_id` и отчётом; нужны собственные native-доказательства исследования, а `authored_paths` не требуется.

Отклонённый до записи JSON можно исправить без повторения продуктовых действий. Принятый отчёт не исправляется: создайте новое назначение с новым ID и `previous_assignment_id`, затем новый отчёт. Writer проверяет исходные события и допустимые пути; исправление оформления не создаёт авторство. Для нового отчёта QA/reviewer требуется собственное исследование в его turn.

При исправлении только оформления принятого авторского отчёта новый автор исследует результат и может вернуть `authored_paths: []`. Первоначальные правки остаются доказательствами исходного назначения; не выдавайте их за новую работу. Reviewer проверяет актуальные конечные авторские назначения; предшественник, заменённый через `previous_assignment_id`, остаётся историей.

### check

```json
{
  "id": "cli-tests",
  "assignment_id": "qa",
  "command": ["python3", "-m", "unittest", "discover", "-s", "tests"],
  "cwd": "/absolute/repo",
  "timeout": 300
}
```

Writer сам выполняет команду один раз и сохраняет фактические cwd, exit и stdout/stderr. `timeout` необязателен, по умолчанию 300 секунд. Не передавайте свой exit code и не запускайте ту же команду отдельно перед регистрацией.

Команда должна быть разрешена пользователем. Проверка выполняется в выбранном checkout; её временные outputs допустимы. Для намеренного изменения продуктовых файлов используйте `generation`. Writer не сравнивает файлы до и после команды.

Результат записи возвращает `path` и фактический `exit_code`. Запись хранится в `checks/cli-tests.json`, полный вывод — один раз в `artifacts/checks/cli-tests.log`. Повторная реальная проверка получает новый check ID и operation ID. Точный повтор записи завершённой операции возвращает сохранённый результат.

### generation

Для разрешённого генератора или форматтера, который меняет продуктовые файлы, используйте `record --kind generation`. Запускает его сам назначенный автор, пока никто другой не пишет в его outputs. В request передаются `assignment_id`, `command` как argv, абсолютный `cwd`, непустой список `outputs` с точными абсолютными путями файлов и необязательный `timeout` в секундах, по умолчанию 300. Outputs должны входить в scope и разрешённую область автора; каталог вместо списка файлов не подходит.

Writer выполняет команду один раз внутри `BEGIN IMMEDIATE` и сохраняет запрос, команду, заявленные outputs, фактический exit и полный вывод. Он не сравнивает файлы до и после запуска и не проверяет изменения файлов соседних задач. Автор отвечает за границы команды и проверяет её результат. При timeout или прерывании изменённые файлы остаются на месте; автоматического rollback файлов нет.

Чтобы связать реальный запуск с автором, используйте каноническую команду writer. Получите абсолютные `python` и `journal` из `journal.py contract`, раздел `generation_invocation`. В инструменте выполнения задайте `shell: /bin/zsh`, `login: true`. Подставьте реальные абсолютные пути вместо путей примера до запуска; порядок аргументов и literal delimiter оставьте как показано. JSON допускает другое форматирование пробелами и сравнивается с фактическим request.

```sh
/absolute/runtime/bin/python3 -B /absolute/package/scripts/journal.py --run-dir /absolute/repo/.agent-work/runs/TASK record --kind generation --request-file - --operation-id generate-client <<'AF_GENERATION_REQUEST'
{"assignment_id":"author","command":["/absolute/runtime/bin/python3","tools/generate_client.py"],"cwd":"/absolute/repo","outputs":["/absolute/repo/generated/client.py"]}
AF_GENERATION_REQUEST
```

Не добавляйте к этой команде shell-префиксы, перестановку flags или оболочку-скрипт. `--run-dir` должен быть каноническим абсолютным путём. Для обычной работы импортировать внутренние Python helpers не требуется.

При фактическом выполнении stdout содержит `{"executed":true,"receipt":...}`. В результате записи находятся `path` и фактический `exit_code`. Повтор завершённой операции возвращает `executed: false` и прежний receipt; он не подтверждает новый запуск или авторство. Сама запись находится в `generations/OPERATION_ID.json`, вывод — в `artifacts/generations/OPERATION_ID.log`. Наличие receipt не означает exit 0.

После выполнения автор читает `native/ID` своего назначения. Готовый `observations[].ref` для generation содержит путь записи вместе с `native`-ссылкой на фактический `CommandExecution` item. Ссылка подтверждает запуск команды с заявленными outputs, но не доказывает, что каждый из них изменился побайтово. В `authored_paths` автор указывает файлы своей работы; QA проверяет результат по требованиям. Этот ref не заменяет тест или успешную QA-проверку. Не используйте повтор `executed: false` как новое доказательство.

Если команда могла выполниться до сбоя публикации, сначала проверьте native-выполнение и файлы. Отсутствие receipt не даёт гарантии, что команда не запускалась, и не разрешает слепой повтор. Для обычного `check` правило прежнее: продуктовые входы изменять нельзя.

## Неизменяемый отчёт назначения

Обязательные поля всех отчётов: `status`, `outcome`, `summary`, `evidence`. `summary` — непустая строка. Статус `completed` или `interrupted` описывает выполнение, результат `passed`, `failed` или `unverified` — исход. Завершённая проверка может иметь `status: completed, outcome: failed`; прерванная работа не получает `passed`. Для отрицательного или неподтверждённого результата укажите содержательную `reason`. Анализ и ограничения помещаются в summary без обязательного набора секций.

Доказательство имеет одну из форм:

```json
{"path": "checks/cli-tests.json"}
```

```json
{"thread_id": "ACTUAL_UUID", "turn_id": "ACTUAL_TURN_UUID", "call_id": "ACTUAL_CALL_ID"}
```

Для native FileChange item:

```json
{"thread_id": "ACTUAL_UUID", "turn_id": "ACTUAL_TURN_UUID", "item_id": "ACTUAL_FILE_CHANGE_ITEM_ID"}
```

Для фактически выполненного generation writer возвращает через `read native/ID` готовую составную ссылку:

```json
{"path": "generations/generate-client.json", "native": {"thread_id": "ACTUAL_UUID", "turn_id": "ACTUAL_TURN_UUID", "item_id": "ACTUAL_COMMAND_ITEM_ID"}}
```

Ссылки на записи берите из результатов writer, native-ссылки — из `read native/ID`. Writer проверяет содержимое и источник. Разрешение выполнить команду и её пересказ не являются доказательством выполнения. QA и reviewer включают собственное успешное native-действие проверки из turn нового отчёта: это подтверждает, что каждый действительно исследовал результат. Одного опубликованного пересказа недостаточно.

Автор добавляет `authored_paths` с абсолютными путями своей работы и ссылается на собственные действия редактирования: `apply_patch`, поддерживаемые native FileChange/CommandExecution либо штатный `generation`. Произвольный shell-скрипт записи сам по себе не подтверждает затронутые пути. Отчёт не должен объяснять все незакоммиченные изменения репозитория.

После остановки правок reviewer проверяет текущий код и подлинные завершённые авторские отчёты из своего `depends_on`. Авторский `outcome: failed|unverified` не определяет результат review: reviewer оценивает свой предмет и указывает ограничения. Невыполненные обязательные проверки остаются `unverified` для итоговой QA. Исторические отчёты вне зависимостей не перепроверяются автоматически. Reviewer возвращает заключение и собственные доказательства. Поля `qa` в его отчёте нет:

```json
{
  "status": "completed",
  "outcome": "passed",
  "summary": "Проверены реализация, сохранность пользовательских изменений и простота решения.",
  "evidence": [
    {"thread_id": "ACTUAL_REVIEWER_UUID", "turn_id": "ACTUAL_REVIEWER_TURN_UUID", "call_id": "ACTUAL_REVIEWER_INSPECTION_CALL_ID"}
  ]
}
```

Необязательное поле reviewer `verification_only` перечисляет ID временных авторских назначений, исключение которых проверено без потери продуктовой работы. Это подтверждение используется только отдельной записью `transfer` с одноимённым purpose; само поле не изменяет состав результата.

После исправления замечаний создайте новые авторские назначения и новые назначения reviewer/QA. В `previous_assignment_id` сохраните связь с предыдущей попыткой, в `depends_on` передайте актуальные зависимости. Каждый проверяющий заново исследует исправленный результат и возвращает собственный отчёт. Предыдущие назначения, отчёты и доказательства сохраняются.

Только после `status: completed, outcome: passed` review запускается QA. В отчёт QA входят `reviewer: {assignment_id}`, исходы каждого критерия и `resolves` для прежних отрицательных reviewer/QA-отчётов. `resolves` сопоставляет ID каждого такого назначения непустому списку успешных evidence refs, подтверждающих устранение замечаний. QA проверяет текущий результат; старые отчёты не заменяются и не проходят повторную валидацию.

```json
{
  "status": "completed",
  "outcome": "passed",
  "summary": "Пустой и валидный ввод проверены штатными тестами.",
  "evidence": [
    {"path": "checks/cli-tests.json"},
    {"thread_id": "ACTUAL_QA_UUID", "turn_id": "ACTUAL_QA_TURN_UUID", "call_id": "ACTUAL_QA_INSPECTION_CALL_ID"}
  ],
  "reviewer": {"assignment_id": "reviewer"},
  "resolves": {},
  "criteria": {
    "ac-1": {"status": "passed", "evidence": [{"path": "checks/cli-tests.json"}]},
    "ac-2": {"status": "passed", "evidence": [{"path": "checks/cli-tests.json"}]}
  }
}
```

Исход критерия — `passed`, `failed` или `unverified`. Для `unverified` обязательна непустая `reason`; поле `evidence` можно опустить или передать пустым массивом. Переданные ссылки проверяются, но не меняют исход на `passed`. Общие `evidence` самого QA-отчёта остаются обязательными и подтверждают его фактическое исследование задачи. Для `passed` нужна успешная фактическая проверка: writer check либо native inspection, относящаяся к критерию. Один текстовый artifact этого не доказывает. Пример выше ссылается на один check без копирования его вывода.

Пример исхода критерия, для которого проверка запрещена:

```json
{
  "ac-3": {
    "status": "unverified",
    "reason": "Пользователь запретил запуск необходимого интеграционного теста."
  }
}
```

Регистрация отчёта сохраняет его результат, включая `outcome: failed`, и не означает успешную приёмку. Отрицательный отчёт назначения не завершает поручение: оркестратор выбирает дальнейшее действие по [правилам продолжения](orchestrator.md). Для успешного final нужны выбранный итоговый QA с `status: completed, outcome: passed` и связанный успешный review. Все критерии QA должны быть `passed`, все прежние отрицательные reviewer/QA-отчёты покрыты `resolves`. Reviewer должен включать актуальные конечные авторские назначения. QA и reviewer независимы друг от друга и от авторов.

Принятые отчёты, назначения, доказательства и переносы неизменяемы. Новая итерация добавляет записи с новыми ID. Старые FAIL остаются историей и не блокируют итог сами по себе. Авторские назначения после приёмки требуют новых review/QA. Актуальный состав авторов учитывает преемников и подтверждённые transfer-записи; незавершённое перенесённое назначение не требует выдуманного отчёта. Журнал не отслеживает изменения продуктовых файлов; исполнители обязаны остановить правки перед проверкой.

## Нормальный порядок на примере

1. Выберите раздел задачи из примера выше. Инициализируйте её и сохраните выданный `RUN_DIR`.
2. Зарегистрируйте author: это реально запущенный worker либо root, который сам пишет код. Передайте корректный request через:

   ```sh
   python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" \
     record --kind assignment --request-file - --operation-id cli-author-assignment
   ```

   В stdin подайте JSON assignment из раздела выше с фактическими UUID и путями.
3. Выполните правку. При необходимости автор запускает writer check под своим зарегистрированным назначением один раз в пределах разрешений; повтор ради отчёта не нужен. QA выполняет свои проверки после review на шагах 5–6. Прочитайте `native/author` после правки и возьмите её `ref`. Для root это также источник текущего `turn_id`. Для worker после его JSON-ответа дождитесь `completed: true` в том же представлении. Зарегистрируйте один отчёт автора:

   ```sh
   python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" \
     record --kind report --request-file - --operation-id cli-author-report
   ```

4. Остановите авторские правки и примите отчёт автора. Запустите независимого `reviewer`, передайте критерии, scope, текущие файлы и отчёт автора. Зарегистрируйте assignment `reviewer`, `kind: reviewer`, с зависимостью `["author"]`. Reviewer получает refs через `read native/reviewer` и возвращает JSON-отчёт. После его остановки возьмите `turn_id` при `completed: true` и зарегистрируйте отчёт. Замечания исправляются в новой итерации с новыми назначениями и отчётами.
5. Только после `status: completed, outcome: passed` review запустите независимого `qa-verifier`. Зарегистрируйте assignment `qa`, `kind: qa`, с зависимостью `["reviewer"]`. Передайте критерии, scope, текущие файлы, авторский отчёт и ID назначения reviewer. Не оформляйте review или QA как `analysis` для обхода этого порядка.
6. QA читает `result`, `requirements`, принятый review и доказательства. Если автор уже выполнил нужный check, QA проверяет его применимость к результату и использует существующую запись. Только недостающую или затронутую исправлением проверку выполняйте через writer:

   ```sh
   python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" \
     record --kind check --request-file - --operation-id cli-tests-execution
   ```

   В stdin подаётся check request, а путь evidence берётся из результата записи. Собственное native-исследование QA обязательно, но им может быть чтение кода, результата и доказательств, а не повтор теста. QA получает свои refs через `read native/qa`, затем возвращает единственный native JSON-отчёт со ссылкой `reviewer`. Оркестратор после его остановки читает `native/qa`, проверяет `completed: true` и регистрирует выданный `turn_id` через `record --kind report` с новым operation ID.
7. Проверьте результат QA и направьте замечание по [правилам продолжения](orchestrator.md). Исправления и повторные проверки оформляются новыми назначениями и отчётами. Если проверка запрещена или недоступна, QA сообщает `outcome: unverified`, отмечая затронутые критерии и причину; это не завершает поручение. Не отправляйте код на переделку без найденного дефекта. Сохраняйте доказательства и не создавайте final во время доработки или ожидания помощи человека.
8. После успешных review и QA со всеми критериями `passed` проверьте сводку и выберите итоговый QA через `--report-id`. Дополнительный reviewer после QA не нужен:

   ```sh
   python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" read summary --format markdown
   python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" \
     finalize --report-id qa \
     --operation-id cli-final
   ```

Значения UUID и call IDs в примерах — места для фактических значений инструментов. Не сохраняйте их буквальными placeholders. Команды демонстрируют контракт, но не утверждают, что конкретный тест был выполнен.

Если поручение окончательно прекращено по правилам оркестратора, root регистрирует собственный итоговый отчёт с неположительным `outcome`, причиной и списком `unverified`. Затем выбирает его:

```sh
python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" \
  finalize --report-id root-stop --operation-id cli-final-stop
```

## Артефакты и прерывания

Для необходимого готового файла используйте:

```sh
python3 -B "$AF_PACKAGE/scripts/journal.py" --run-dir "$RUN_DIR" \
  publish --file artifacts/screenshot.png /absolute/screenshot.png --operation-id cli-screenshot
```

`publish` не записывает отчёты, назначения и final. Не публикуйте копию уже сохранённого check log. Читайте записи через `read`, а не ручное редактирование базы или экспорта.

Final проверяет выбранный итоговый отчёт и связанную приёмку, независимость исполнителей, доказательства, полноту критериев и `resolves`. Он не требует положительного исхода всех исторических назначений. `validate-run.py --run-dir PATH --report-id ID` проверяет выбранный итог; после закрытия ID можно опустить, он берётся из final. Репозиторий не сканируется. SQLite lock защищает запись в базе, но не запрещает внешнему редактору изменить исходник.

В пределах CLI-операции каждая native-сессия разбирается один раз; события индексируются по turn/call/item. Проверка доказательств выполняется до транзакции записи. Перед атомарной записью сверяется `revision`; конфликт требует свежего чтения и явного повторения операции. Кэш не переносится между операциями.

Операции используют существующие SQLite-транзакции, rollback и durability. Отчёт и результат операции сохраняются согласованно. Точный повтор с тем же ID возвращает сохранённый результат; другие аргументы с тем же ID отклоняются. После `BUSY` выясните исход первой попытки, затем повторите явную операцию со свежими входами, если она не завершилась. Автоматического цикла повторов нет.

Команда могла завершиться до сбоя публикации. Отсутствие receipt не разрешает повторять её вслепую: сначала прочитайте native-вывод и проверьте фактическое состояние. Если результат восстановить нельзя, укажите неподтверждённую часть.

Final отсутствует до завершения. После его принятия задача закрыта: доступны чтение и точный повтор завершённых операций, но не новые изменения или повторное открытие.
