## 1. Результат и границы

Выделить общее ядро из проверенной реализации Codex, сохранить её поведение и строгость приёмки, затем подключить Kimi Code вторым адаптером и установленный локальный DeepSeek Harness (DSH) третьим. Переиспользовать существующие journal, workspace, отчёты и проверки результата в их текущем виде 0.7.3. После extraction новая среда добавляется через адаптер, bindings и профили моделей. Названия инструментов, способы вызова и разбор нативных событий принадлежат адаптеру; обязанности ролей и решения приёмки остаются общими.

Один набор сценариев с одними ожидаемыми решениями проверяет Codex, Kimi, DSH и каждый следующий зарегистрированный адаптер через его reader и общее ядро. Нативные fixtures различаются, policy tests и expected verdicts не копируются. Отсутствие fixtures или непроверенный зарегистрированный адаптер не допускают общего PASS.

После создания или актуализации контекста проекта Agent Flow предлагает команду по используемым ролям: `роль → профиль конкретной модели + reasoning + подключение/host`. Пользователь принимает предложение, переопределяет назначения и может изменить их позднее. Это конфигурация проекта; глобальные роли при пользовательском выборе не переписываются. Один проект допускает несколько execution targets.

Дистрибуция не входит в адаптерный контракт. Codex plugin остаётся единственным упакованным артефактом сборки (`agent-flow-X.Y.Z-codex-plugin.zip` через корневой `scripts/build-plugin.py`). Kimi Code и DSH нативно сканируют `.agents/skills/` и `~/.agents/skills/`, поэтому для них Agent Flow распространяется как standalone-скилл существующими механизмами impl-011, включая [update-agent-flow-skill.py](../../scripts/update-agent-flow-skill.py). Новые распространяемые plugin-артефакты, цели сборки, манифесты дистрибуции других платформ и публикация в их маркетплейсах не входят в объём. Условная локальная интеграция ролей DSH из этапа 4 относится к адаптеру и не добавляет цель пакетирования.

Этот документ готовит будущую реализацию через Agent Flow. Подготовка плана не запускает адаптеры, не меняет настройки сред и не означает успешный `validate-run.py`. Архитектурное направление согласовано пользователем; проверки реализации ещё предстоят. `Document status` относится к готовности текста, а `Implementation status` — к выполнению работ.

В объём входят контракты выполнения и доказательств, Codex-адаптер, профили моделей, проектные назначения, Kimi-адаптер, DSH-адаптер и их проверки. Не входят performance-бенчмарки, сравнительный рейтинг моделей, подключение GLM или других названных для примера моделей, фиксированный frontend-маршрут, оркестрация всех desktop-приложений, новый daemon, UI automation как production transport, сервисы, контейнеры, DI-фреймворк и восстановление удалённой в 0.7.x инфраструктуры. Возможности MCP или факт установки приложения сами по себе не подтверждают управляемое подключение.

## 2. Основания и текущее состояние

Основные подтверждённые факты включены ниже, поэтому локальная `.agent-work/` не нужна для понимания и исполнения плана в другой копии репозитория.

Факты пилота DSH (сохранены из редакции 1):

- Пилот на DSH `0.2.0-rc.2` показал три отдельные дочерние сессии author, QA и reviewer с общей файловой системой. QA и reviewer работали на той же модели, что и author; разнообразие моделей в этом цикле не проверялось.
- QA выполнил 18 тестов, reviewer отдельно прочитал код и отчёт QA и обнаружил пробел Unicode. Продолжение через `send_message` создало второй ход той же QA-сессии. Источник сообщения подтверждён журналом.
- Замена `lower()` на `casefold()` оставила тесты зелёными, но checker отклонил новый SHA-256, а QA вернул `rejected`. Восстановление байтов вернуло исходный хеш; последний ход QA остался `rejected`. Это последовательность событий пилота, а не доказательство автоматической инвалидизации принятого отчёта в 0.7.3. Новое принятие отчёта проверяет текущий ход; повторная проверка ранее принятого отчёта следует правилам §3.
- Два отдельных вызова `workflow.agent` подтвердили overrides `deepseek-account/deepseek-flash` и `deepseek-account/deepseek-v4-pro` по конфигурации запроса и `assistant/message.source`. Это проверка маршрутизации на коротком задании, без оценки качества разработки. Runtime model ID не удостоверяет скрытую версию весов провайдера.
- В проверенном workflow доступны provider/model, но нет явного reasoning-параметра; `high` был выбран самим Harness. Workflow-дети были one-shot, background-subagent — continuable. Сочетание выбора модели, явного reasoning и продолжения живым тестом ещё не подтверждено.
- Чтение установленного кода 3 октября показало opt-in `modelSelectionSettings`, параметры `provider`, `model`, `reasoning_effort` и передачу `agentOptions` в `startContinuable`. Текущая пилотная сессия эти параметры не открывает. Настройки не менялись; статическое чтение не доказывает работоспособность сочетания.
- DSH может дополнять вход служебным блоком; followup имеет источник `agent-message/relay`. У синхронного запуска session ID может потребовать сверки с `subagent/catalog`; у workflow различаются `runId`, `childId` и session ID. `agentPreset=standard` не доказывает роль Agent Flow.
- В предыдущей диагностике Codex входы parent→subagent, включая followup, могли оставаться `encrypted_content`, хотя прямые user→CLI-входы читались. Это историческое ограничение доступности доказательств, а не текущий PASS. Уровень `strict_inputs`, упоминавшийся в той диагностике, в действующем контракте 0.7.3 отсутствует.

Факты веб-исследования платформ от 21 октября 2026 года:

- Kimi Code — агентная среда Moonshot AI (CLI, Desktop, Web). Skills в формате `SKILL.md` сканируются из `.kimi-code/skills/`, `.agents/skills/`, `~/.kimi-code/skills/`, `~/.agents/skills/` и `extra_skill_dirs`. Кастомные субагенты — Markdown-файлы с frontmatter (`name`, `description`, `tools`, `subagents`) в `.agents/agents/` и родственных путях; `tools` применяется как реальный allowlist. Встроенные типы `coder`, `explore`, `plan` дальше не делегируют. Есть фоновые субагенты, параллельный запуск и hooks по событию в `config.toml`. Встроенная команда импорта переносит инструкции и skills из Claude Code и Codex. Формат и пути совместимы с конвенцией SKILL.md.
- DeepSeek Harness — открытый репозиторий `deepseek-ai/deepseek-harness` на TypeScript, статус developer preview с ожидаемыми ломающими изменениями. Provenance: локальные `report.ru.md` в редакции от 3 октября, `dsh-capability-review-2026-10-03.json` и `runtime-audit.json` из `.agent-work/diagnostics/dsh-portability-pilot-2026-10-02/`; публичная документация Kimi Code (`kimi.com/code/docs`) и репозитория `deepseek-ai/deepseek-harness` от 21 октября. | `render_agent_toml`, guarded write в [sync-codex-agent-config.py](../../scripts/sync-codex-agent-config.py) | Codex exporter не экспортирует поле `tools` как ограничение — это учитывается при генерации агентов Kimi. Подход guarded write и atomic replace переиспользовать при записи project team; добавить expected revision/hash и проверку stale writer |

[agent_config.py](../../scripts/agent_config.py) содержит закрытые `ALLOWED_MODELS` (строка 13), общий список `ALLOWED_REASONING_EFFORTS` (строка 24) и `ALLOWED_TOOLS` (строка 26), а после удаления `resolve-agent-config.py` — и разрешение настроек роли. Функции оценки моделей, ранее выделенные в `model_eval_adapter.py`, в редакции 0.7.3 отсутствуют; если оценочный backend будет возвращён отдельным поручением, его Codex-специфика локализуется в Codex-адаптере по тем же правилам.

Действующая процедура [чтения контекста](../../references/project-memory-and-env.md#чтение-контекста) собирает достаточный контекст и пересобирает его при изменении запроса. [init-run.py](../../scripts/init-run.py) создаёт журнал; он не заменяет содержательную сборку контекста. Шаг предложения команды встраивается после этой сборки и до первого зависимого назначения.

Для плана применены:

- `ai-agents-architect`: явные результаты native calls, отсутствие слепого retry при неизвестном исходе и неподтверждённой отмены; единая проверка адаптеров. Новые agent loop, registry framework и численные лимиты из примеров skill не вводятся.
- `clean-architecture`: контракты определяет ядро; адаптер переводит операции и события. Это приводит к двум небольшим границам — execution и evidence reader — внутри существующего Python-пакета, без новой инфраструктуры.
- [Implementation Plan Authoring](../../references/implementation-plan-authoring.md): этапы разделены по проверяемому сохранению Codex, новому проектному выбору и двум новым runtime. Проверки входят в каждый этап.
- `humanizer-ru`: факт пилота, требование и неизвестное обозначаются отдельно; условия завершения сформулированы наблюдаемым результатом.

Доступных навыков и проектных источников достаточно для плана. Наблюдаемость минимальных фактов Kimi проверяется до фиксации контракта на этапе 1; полный `wire.jsonl` reader остаётся задачей этапа 3. Production channel DSH с обязательным сочетанием capabilities проверяется на этапе 4. Эти технические проверки входят в будущую реализацию и не означают нерешённого продуктового выбора. Подготовка документа не считается проверкой работы Kimi или DSH.

## 3. Архитектурное решение

### Границы модулей

Ядро хранит обязанности ролей, ограничения назначения, ownership, независимость QA/reviewer, порядок приёмки, handoff, result fingerprint, актуальность и DoD. Оно не знает имён `spawn_agent`, `subagent`, `workflow.agent`, схем нативных аргументов или формата `session.v4.jsonl.zstd` и `wire.jsonl`.

Адаптер среды — единственная точка подключения нового harness. Контракт адаптера состоит из шести операций:

| Операция | Обязательный смысл |
| --- | --- |
| `detect` | Обнаружение среды и декларация capabilities: фоновые субагенты, продолжение сессии, читаемость первичных журналов, выбор модели и reasoning. Незаявленная capability не проверяется молча и не считается поддержанной |
| `session_source` | Reader первичных источников среды, возвращающий нормализованные факты с происхождением. Нативный decoder и отображение событий находятся рядом с адаптером |
| `root_identity` | Идентичность корневой сессии из окружения среды; заменяет чтение `CODEX_THREAD_ID` как единственного источника |
| `provision_roles` | Перевод ролей Agent Flow в нативный формат среды: TOML custom agents для Codex, Markdown-агенты `.agents/agents` для Kimi; для DSH сначала role instructions и launch config штатного provider. Собственный DSH plugin допускается лишь при доказанном пробеле этого пути. Разрешения генерируются по обязанностям роли, а не копированием frontmatter: Codex exporter поле `tools` как ограничение не экспортирует, Kimi применяет его как реальный allowlist. Запись — через существующий guarded-write подход |
| `model_profiles` | Каталог профилей моделей среды и их bindings вместо глобального GPT-only enum |
| `tool_vocabulary` | Отображение имён инструментов в инструкциях ролей на нативные имена среды; неизвестное имя — ошибка генерации, а не молчаливая подстановка |

Execution adapter получает разрешённое назначение и описывает перевод операций запуска, ожидания, продолжения и отмены в доступные инструменты среды. Фактический native call выполняет оркестратор в host-сессии: в Codex через доступный subagent tool, в Kimi и DSH через их нативные инструменты. Python готовит и проверяет пакет, разрешает конфигурацию и читает evidence; он не получает скрытой возможности вызывать инструменты чата. Unsupported-операция возвращает явный отказ. Достаточно декларативных host-инструкций и функций преобразования пакета; daemon, MCP-server и универсальный scheduler не требуются.

Из `completed_turn` выносится только native decoding: проверки всех наблюдаемых моделей, единственного собственного завершения выбранного хода и временного порядка остаются общей политикой. Новое принятие отчёта требует текущего завершённого хода; повторная проверка принятого отчёта использует закреплённый ход с `current=False`, как в 0.7.3. Root author/analysis подтверждает собственные выполненные действия текущего turn без требования сначала завершить этот turn. Из native helpers выносится разбор вызовов и items: адаптер отображает события правок и команд своей среды (Codex call/output, `FileChange` и generation `CommandExecution`; Kimi `Edit`/`Write`/`Bash`; события DSH) в нормализованные факты с provenance. Общими остаются правила: каждый путь из `authored_paths` подтверждён собственным редактированием или штатной generation автора; QA и reviewer имеют собственную успешную нативную проверку. Факт успешной записи файла или генерации не заменяет проверку критерия; неизвестный класс инструмента не засчитывается. Adapter не возвращает решение PASS и не подставляет requested model/reasoning вместо отсутствующего observed. JSON автора и успешный ответ native tool сами по себе не закрывают приёмку.

Предлагаемые новые модули: `scripts/runtime_contract.py`, `scripts/runtime_adapters/codex.py`, затем `scripts/runtime_adapters/kimi.py` и `scripts/runtime_adapters/dsh.py`. Composition root в CLI связывает явные встроенные адаптеры с контрактом. Run-артефакт не может подставить Python import, произвольный reader, команду или синтетический источник. Существующая инъекция тестового source остаётся внутренним test seam.

Добавление новой среды после этой поставки — это новый файл адаптера, его native fixtures и точечная trusted registration. Необходимость правки ядра при подключении среды означает подтверждённый пробел контракта: architect пересматривает контракт, расширяет ownership именно для исправления, повторно проверяет parity всех зарегистрированных адаптеров. Специфичные для среды обходы внутри core запрещены.

### Публичные контракты и данные

| Контракт | Обязательный смысл |
| --- | --- |
| `AssignmentSpec` | Стабильный ID назначения, role slug, версия/хеш инструкций роли и профиля, входные артефакты, ограничения, требуемые capabilities, конкретное подключение и host, выбранный reasoning. Разрешённые значения фиксируются до dispatch |
| `ExecutionRef` | Adapter ID, connection ID, host ID, непрозрачный native session ID и turn. Продолжение ссылается на новый turn той же сессии без переназначения assignment. Пространство идентичности включает target, поэтому одинаковые session ID разных сред не сталкиваются |
| `ExecutionEvidence` | Связь запуска с назначением и родителем, модель/провайдер и reasoning запроса и наблюдаемые значения, начало/конец/состояние хода, вывод, source refs с хешами и указателями, нормализованные действия. Для новых model/profile instructions — адресное подтверждение доставки по source или наблюдаемой host-конфигурации. Requested config сохраняется; доступные сведения о фактическом входе не подменяются запросом. Полная копия prompt и его побайтовое сравнение не обязательны; неизвестные поля остаются неизвестными |
| Action evidence | Нормализованные факты редактирования, проверки и фактического запуска generation writer: вид действия, успешность, пути и происхождение. Для generation — связь native-выполнения с request и receipt. Ядро отдельно проверяет авторство, покрытие текущих изменений и собственную успешную проверку QA/reviewer; один флаг успеха не делает правку проверкой. Отсутствие разбора для класса инструмента — явный gap |
| Capability result | Наблюдённые операции и сочетания для конкретных adapter, version, connection, host и session policy; источник проверки и область применимости. `model selection` и `continuation` по отдельности не означают поддержку их комбинации |
| Model profile | Стабильный ID и версия профиля конкретной модели, её инструкции, допустимые reasoning-варианты и default. Общие правила семейства можно переиспользовать; семейство не заменяет профиль модели |
| Connection binding | Соответствие profile ID реальным provider/model IDs и поддержанным параметрам данного target. Секреты не входят в профиль, назначение или evidence. Alias считается доказанным только при проверенной привязке |
| Project team | Назначения используемых ролей на profile ID, reasoning и connection/host, принятые переопределения и их revision. Сохранённое назначение не доказывает доступность подключения |

Для независимости используется каноническая identity сессии: доверенно разрешённое пространство runtime/host и native session ID. Turn и произвольный connection alias в неё не входят. Два aliases одной сессии должны давать одну identity; новый turn не превращает автора в независимого QA. Реально разные runtime namespaces не сталкиваются при одинаковой строке session ID. Adapter подтверждает namespace по source/binding, а не произвольной метке из run-data.

Политика профиля не вводит GPT-only enum и не требует копии профиля для каждого reasoning. Значения проверяются по пересечению профиля и конкретного binding; одинаковое слово `high` у разных моделей не приравнивает их возможности. Неявный runtime default допускается только как явно выбранный режим с наблюдаемым эффективным значением; он не выполняет требование явно управлять reasoning.

Для проекта предлагается `.agent-flow/team.json` с переносимыми назначениями без секретов. Локальные сведения об управляемых подключениях — `.agent-work/runtime-connections.json`; credentials остаются в уже используемом хранилище среды. На другом host недоступное connection ID требует явного сопоставления. Это продуктовая конфигурация будущей реализации; при написании плана файлы не создаются. Запись team использует expected revision/hash прочитанной редакции: проверка и atomic replace выполняются в одной защищённой операции записи, stale writer получает conflict без перезаписи файла. Подход берётся из существующих guarded-write механизмов, новый storage/lifecycle не нужен. Snapshot разрешённого назначения публикуется существующим journal API до dispatch и связывается с assignment. Изменение team revision действует только на новые назначения. Текущий или завершённый assignment, его модель, target и уже принятые hashes не переписываются.

Инструкции профиля добавляются к существующему delegation packet и host export рядом с инструкциями роли; отдельный instruction engine не нужен. Обязательные правила роли и требования задачи имеют приоритет над советами профиля, конфликтующий профиль отвергается до dispatch. Snapshot связывает версии/хеши инструкций и выбранную конфигурацию. Доставку новых model/profile instructions reader подтверждает адресно по наблюдаемому source либо host-конфигурации, связанной с данным запуском. Наличие локального profile file или пересказ оркестратора этого не доказывает. Полный prompt, включая все системные и служебные добавления среды, для этого не требуется.

Модель, reasoning и target зафиксированного назначения сохраняются. Предусмотренное действующим маршрутом повышение reasoning внутри той же модели проверяется по профилю и применяется к новому назначению с собственным snapshot; существующий assignment и прежние snapshots не меняются. Для one-shot после неудачи новое назначение и приёмка выполняются в новом run. Новые сущности попыток и отдельный attempt lifecycle не вводятся. Недоступность выбранного target останавливает зависимое назначение. Автоматическая замена возможна лишь по заранее принятому правилу для нового назначения; она не перепривязывает существующий `agent_id`.

Unknown outcome native call не разрешает слепо повторить запуск. Сначала доступным способом сверить факт запуска и session reference; если это невозможно, оставить явный gap/blocked для зависимой работы. Timeout не равен завершению, а неподтверждённая cancel не означает остановку worker. Эти правила входят в adapter contract и текущий handoff/journal; новая launch state machine не создаётся.

### Цепочка доказательств и совместимость

Поток данных: контекст → доступные bindings → принятое назначение → snapshot → dispatch → native reference → первичные события → нормализованные факты → решение общего validator. До отправки сохраняются выбранная конфигурация и версии/хеши новых model/profile instructions; доказательство их доставки связывается с запуском. Проверки identity/parent, модели, завершения и действий обязательны. Недоступность полного prompt сама по себе не проваливает приёмку; неподтверждённая доставка новых инструкций оставляет именно этот критерий незакрытым. Побайтовый аудит всего prompt и режим `strict_inputs` не вводятся.

Чтение первичных источников выполняется в момент приёмки через reader выбранного адаптера, как сейчас через `CodexSessionSource`: `accept_report` читает source при записи отчёта, `finalize` повторно вызывает `validate_acceptance` до транзакции и внутри неё, сверяя `result_fingerprint` до публикации. Этот порядок сохраняется для всех адаптеров; отдельный слой capture/freeze, существовавший в ранних редакциях, в 0.7.3 отсутствует и не восстанавливается. Изменение результата между предварительной проверкой и публикацией отклоняется сверкой fingerprint внутри транзакции. Для растущего журнала среды хеш всего файла характеризует момент чтения. Новое принятие проверяет текущий ход, а повторная валидация — закреплённый принятый ход и хеши его доказательств; последующее добавление событий само по себе не портит прежнюю запись. Отдельные Kimi/DSH journal и lifecycle исключены.

Независимость проверяется по фактическим execution identities и источнику запуска. У DSH и Kimi роль связывается с assignment, фактической дочерней сессией и наблюдаемой конфигурацией запуска; `agentPreset`, имя агента в запросе и самоописание ответа этого не доказывают. Доставка новых инструкций проверяется по правилу выше. Для смешанных targets одного локального проекта родительская связь может подтверждаться source-bound dispatch в одной среде и соответствующим событием запуска в другой. Одной записи оркестратора о якобы внешнем запуске недостаточно. При отсутствии связуемых доказательств такой маршрут не допускается к приёмке.

Текущий контракт журнала 0.7.3 один, без миграции старых баз и восстановления поколений состояния run. Штатные записи запуска генератора `generations/` сохраняются. Поля `source` отчётов (`thread_id`, `turn_id`, `root_author`) и native refs в evidence, включая вложенный `native` у generation, обобщаются до adapter-qualified ссылок. Прежние `call_id`, новые `item_id` и составные generation refs читаются через Codex-адаптер по умолчанию без переписывания байтов и hashes. Неизвестная версия identity, смешение `call_id`/`item_id` или конфликт old/new полей отвергаются.

Сохраняются действующие правила независимого QA, reviewer после актуального completed QA, hashes результата/evidence и сверка fingerprint при финале. Новая регистрация отчёта выполняется с `current=True`: требуется актуальный завершённый ход ребёнка. `revalidate_report` использует `current=False` и проверяет ранее принятый ход, его source/evidence hashes и связи отчётов. Поздние native start, unfinished или failed turn без регистрации нового отчёта не аннулируют прежнее одобрение. Root может продолжать работу; завершённый run остаётся читаемым после поздних native-событий. Подмена закреплённого source, изменение fingerprint или принятого отчёта по-прежнему отклоняются. При этом `validate_acceptance` заново пересекает заявленные `authored_paths` с подтверждёнными путями и проверяет покрытие текущего delta. Для generation сохранённое `after` сверяется с текущим inventory отдельно по каждому output: поздняя правка одного файла не обесценивает доказательства остальных, но требует актуального доказательства для изменённого файла. Исторический отчёт не переписывается; одного его наличия для текущего покрытия недостаточно. Это parity 0.7.3, без исключения для CF-05. Reader не выгружает private reasoning или секреты. Если source не позволяет доказать конкретный обязательный факт, фиксируется адресный evidence gap; один недоступный полный prompt таким пробелом не считается.

Штатный generation writer сохраняет семантику 0.7.3: точные outputs в scope/allowed_paths автора, запуск внутри `BEGIN IMMEDIATE` при отсутствии параллельных правок продуктовых входов, before/after, фактические exit/output и receipt. Необъявленные изменения продукта, context или критериев отклоняют запись. Это не sandbox и не rollback: при отказе или timeout файлы могут остаться изменёнными, а отсутствие receipt не разрешает слепой повтор. Авторство требует собственного native-выполнения writer с соответствующим request/receipt и `executed: true`; replay, чужой запуск, ненулевой exit и пустой diff его не доказывают. Записи и логи generation создаёт только writer; обычный `publish` не может подменить их. Неуспешный запуск генератора сам по себе не является зарегистрированным `failed` report: правило нового one-shot run относится к неудаче цикла приёмки. Обычный `check` по-прежнему не меняет продуктовые входы.

Codex сохраняет каноническую форму `generation_invocation`: `/bin/zsh -lc`, heredoc `AF_GENERATION_REQUEST` и наблюдаемый `CommandExecution`. Эти детали вызова и их native-разбор принадлежат Codex-адаптеру. Kimi/DSH подтверждают связь с тем же writer своими первичными событиями; без такой связи generation имеет явный gap/unsupported. Это не разрешает ослабить общую policy или подменить события вымышленным Codex item. Новый writer, журнал или lifecycle генерации не вводятся.

При mutation несовпадающий fingerprint делает QA/reviewer неактуальными. После восстановления исходных байтов снова вычисляется настоящий fingerprint: если текущие зарегистрированные отчёты и hashes ему соответствуют, один поздний native отказ не блокирует принятие. Если же зарегистрирован `failed` report, он остаётся текущим и блокирует положительный final даже после restore. До final continuable-сессия может штатно заменить отчёт того же assignment новым завершённым отчётом; после изменения QA reviewer принимает его новый hash. Отдельная история отчётов не создаётся.

Для one-shot допускается один цикл приёмки на run. Неудачный цикл завершается `finalize --status failed`; исправления и новый полный цикл author → QA → reviewer выполняются в новом run с новыми исполнителями. Все assignments старого run должны иметь completed reports для положительного final: добавление нового QA не нейтрализует прежний failed. Перепривязка `agent_id`, supersession и отдельный attempt-history lifecycle не вводятся. Поддержка continuation проверяется как capability и не требуется для Kimi; обязательное сочетание DSH из RP-11 сохраняется.

Отвергнуты: замена только названий инструментов/UUID; моделирование ролей ответами одного контекста; принятие экспортированного JSON как первичного source; Workflow как единственный backend DSH; глобальное редактирование ролей при выборе команды; автоматический выбор «лучшей» модели по вымышленному рейтингу; обязательный универсальный мост между приложениями; multi-target сборка плагинов для платформ кроме Codex; опора на experimental-мосты совместимости DSH как на production-механизм; восстановление удалённых в 0.7.x механизмов (capture/freeze, seal/delivery, поколения состояния run) ради прежнего текста плана.

### Общий набор проверок адаптеров

В существующих Python tests и запланированном `scripts/test-runtime-contract.py` выделить один acceptance/conformance corpus: сценарий, входные условия и ожидаемое решение определяются один раз. `test-verification-evidence.py` и golden traces дают исходные проверки; journal/workspace tests переиспользуют тот же набор там, где проверяется adapter policy. Native fixtures и decoder tests готовят события конкретной среды, затем общий сценарий проходит через её reader и то же ядро. Mock source injection остаётся внутренним test seam.

Для итоговой приёмки каждого зарегистрированного адаптера выполнить все сценарии corpus. Сверить полноту регистрации с trusted production adapter list: отсутствие fixture, потерянный сценарий, неизвестный adapter или пропуск запуска не превращаются в PASS. Следующий адаптер обязан подключить свои native fixtures к тому же corpus; копирование policy suite/expected verdicts или исключения ради зелёного отчёта запрещены. Новый framework и динамический runtime loader не нужны.

Corpus расширяется вместе с реализацией контрактов, сохраняя одни сценарии и ожидаемые решения для всех адаптеров. На этапе 1 обязательны CF-01, CF-02, CF-04–CF-06, CF-08, существующие role/evidence checks из CF-03 и workspace checks из CF-07. Доставка новых model/profile instructions и их конфликты из CF-03, project team/stale writer и влияние project revision на snapshots из CF-07 относятся к этапу 2. До его завершения эти cases явно отмечаются `pending: этап 2` в отчёте покрытия; это не PASS и не скрытый skip. Этап 1 закрывается по parity реализованных контрактов, а общий PASS corpus пока запрещён. Этап 2 закрывает отложенные cases и повторяет реализованный corpus для всех зарегистрированных к этому моменту адаптеров. Этапы 3, 4 и общая поставка требуют полного CF-01–CF-08 для всех зарегистрированных адаптеров без pending. Эти отметки ведутся в существующих тестовых отчётах; новый stage framework не нужен.

| Общий сценарий | Единое ожидаемое решение |
| --- | --- |
| CF-01: identity/parent, aliases, turns | Подтверждённая независимая сессия допускается; подмена родителя, alias той же сессии и другой turn автора как QA отвергаются |
| CF-02: несколько observed models и параметры назначения | Все наблюдаемые model values должны совпасть с binding; смешанный список и отсутствующее обязательное observed значение не подтверждают назначение |
| CF-03: роль и доставка новых model/profile instructions | Доставка подтверждается адресно по source или наблюдаемой host-конфигурации данного запуска; недоставленный профиль, конфликт обязательных правил и подмена source отвергаются. Отсутствие полного prompt само по себе не проваливает проверку |
| CF-04: source integrity и финальная повторная валидация | Missing/ambiguous source и подмена generation request/receipt/native-выполнения отвергаются; результат, изменённый между предварительной проверкой и публикацией, отклоняется сверкой fingerprint внутри транзакции `finalize`. Unknown runtime, wrong reader, stale team writer и изменение текущего snapshot отвергаются. Условия допуска и отказа каждого сценария задаются заранее. Если runtime не предоставляет операцию, его fixture проверяет явный unsupported-отказ по общему правилу; выдумывать поддержку или пропускать сценарий нельзя. Такой тест подтверждает корректность отказа, но не поддержку обязательной возможности: capability/live readiness остаётся gap. Общий PASS corpus означает согласованность решений на предоставленных событиях; production readiness дополнительно требует живые сценарии каждой среды и фактическую финальную публикацию.

## 4. Этап 1. Выделить Codex и сохранить приёмку

### Результат, границы и порядок

Первый работающий адаптер выполняет существующие назначения Codex через выделенное из текущего кода ядро. Проверки этапа 1 из общего corpus сохраняют сегодняшние положительные и отрицательные решения, включая CF-05; будущие profile/config cases остаются явно pending до этапа 2. В этой же поставке отделяются Codex defaults от содержания ролей: исходные модель/reasoning-настройки сохраняются как baseline profiles/bindings, без смены фактических моделей. Интерактивный проектный выбор относится к этапу 2.

Зависимости: прочитать актуальную редакцию этого плана и affected code, зарегистрировать исходное состояние и доступность Codex evidence на одном изолированном назначении. До фиксации общего контракта обязателен минимальный контролируемый Kimi probe текущей установки: проверить identity дочерней сессии, parent, observed model, собственное завершение, вызовы инструментов и их результаты. Probe проверяет, что контракт опирается на наблюдаемые факты второй среды, а не только на Codex. Он не требует полного reader, отдельного этапа или обязательного probe report: результат входит в штатные evidence и отчёт architect. До probe независимое исследование и Codex extraction допустимы, но общий контракт нельзя считать подтверждённым. DSH probe на этом шаге не обязателен.

С учётом Kimi probe зафиксировать контракт и отображение существующих полей `source` на Codex-адаптер, затем вынести decoder и разбор нативных действий, обобщить параметры recorder/validator и существующих journal/workspace, согласовать инструкции и package inventory. Полный Kimi reader и живой цикл остаются этапом 3; недоступный обязательный факт probe останавливает фиксацию зависимой границы, а не независимую работу над Codex.

Scope относительно `skills/agent-flow/`:

- `scripts/runtime_contract.py`, `scripts/runtime_adapters/codex.py`; `verification_evidence.py`, `validate-run.py`: extraction по карте переиспользования и проверки реализованных контрактов в общем corpus с явным учётом pending cases этапа 2, без второй реализации acceptance policy. `CodexSessionSource` перестаёт быть неявным default: reader выбирается из доверенного adapter binding назначения, для записей без binding действует отображение на Codex.
- `scripts/journal_io.py`, `journal_structure.py`, `journal_lifecycle.py`, затронутые вызовы `journal.py` и `init-run.py`: identity и source refs отчётов и действий через единый контракт `ExecutionRef`; сохранить `record --kind generation`, его writer/guards/receipts, отделить host-форму вызова от общей проверки provenance. Порядок `finalize` (предварительная и внутритранзакционная `validate_acceptance`, сверка fingerprint, идемпотентность) и алгоритмы хеширования не перепроектировать.
- `scripts/task_workspace.py`, `scripts/workspace_scope.py`: scope, inventory, `changed_paths` и `workspace_fingerprint` сохраняются как есть; action evidence адаптера подключается к проверке покрытия изменений в `validate_acceptance`, включая сверку `after` каждого generation output с inventory. Не менять алгоритмы fingerprint и исторические hashes.
- `scripts/agent_config.py`, `validate-agent-config.py`, `validate-role-catalog.py`, `sync-codex-agent-config.py`, `agents/*.md`, baseline profiles в `registries/model-profiles.json`: отделить role content и Codex binding, сохранить legacy read path и текущие defaults. Функции удалённого `resolve-agent-config.py`, которые сейчас выполняет `agent_config.py`, выделяются в resolver профилей без смены поведения.

Target-specific readiness не должна требовать Codex setup для другого adapter. Сборка остаётся одноцелевой (Codex plugin); новые CI/deploy или установка пакета пользователю не входят в scope.

### Приёмка и проверки

`RP-01` — общий policy layer не читает native events, не проверяет Codex UUID и не выбирает модели из глобального GPT enum. Codex decoder воспроизводит факты 0.7.3 для call/output, FileChange и generation-выполнения, общее ядро — прежние решения об авторстве и проверках. До фиксации контракта минимальный Kimi probe подтвердил identity/parent, model, completion и actions/results по первичным событиям. Adapter подставляется только из доверенной composition root. Обязательные проверки этапа 1 из §3 проходят через Codex reader; отчёт покрытия учитывает trusted adapter list и явно показывает будущие cases этапа 2 как pending. `RP-01` подтверждает extraction/parity, а не общий PASS всего corpus. Readiness выбранного target отделена от общей integrity пакета.

`RP-02` — принятые журналы текущего контракта и golden traces читаются без изменения байтов и исторических hashes. Новый malformed envelope, неоднозначная identity, подмена source и конфликт legacy/new fields отвергаются. Команды текущего CLI (`contract`/`record`/`publish`/`read`/`finalize`), включая `record --kind generation`, `generation_invocation` и новые виды evidence refs, сохраняют смысл. Receipt replay не выдаётся за новый запуск. `validate_acceptance` требует актуального покрытия текущего delta, в том числе generation outputs. Workspace scope и `workspace_fingerprint` входят в `RP-02`: результат проходит финальную сверку fingerprint через reader своего adapter; несовпадающий adapter/target или неизвестный runtime отклоняется до публикации `final.json`; положительный отдельный `validate-run.py` не заменяет проверку finalize.

`RP-03` — свежий Codex author → QA → reviewer проходит общую политику; неверная модель, общий execution ID у автора и QA, reviewer до QA, изменённый handoff и stale hashes не проходят. Новое принятие устаревшего или незавершённого хода отклоняется. Повторная валидация принятого отчёта сохраняет `current=False`: поздний native start/unfinished/failed без регистрации нового отчёта не аннулирует принятие. Положительные сценарии покрывают root continuation, чтение завершённого run и последовательные generation с отдельным доказательством текущего состояния каждого output; устаревшее generation-покрытие отклоняется. Mutation/restore проверяет обе ветки CF-05: соответствующий fingerprint допускает прежние неизменные отчёты, а зарегистрированный failed блокирует completed final до штатной замены отчёта того же assignment.

Выполнить существующие `test-verification-evidence.py`, `test-golden-traces.py`, `test-init-run.py`, `test-journal-io.py`, `test-journal-lifecycle.py`, `test-journal-storage.py`, `test-task-workspace.py`, `test-agent-config.py`, `test-validate-agent-config.py`, `test-validate-role-catalog.py`, `test-sync-codex-agent-config.py`, `test-update-agent-flow-skill.py` и корневой `scripts/test-build-plugin.py`. Расширить существующие tests и добавить `scripts/test-runtime-contract.py` как runner общего corpus, без скопированной Codex policy suite. Сопоставить решения до/после extraction на тех же сценариях без исключения CF-05. Сохранить положительный regression `test_observed_tool_output_is_pinned_and_root_continuation_is_allowed`. Native decoder fixtures дополняют эти проверки. Сохранить добавленные в 0.7.3 cases из `test-verification-evidence.py` и `test-journal-io.py`: FileChange add/update/delete/move и failed/foreign/duplicate items; недоступный текстовый output без потери других observations; generation guards, replay/подмена invocation, фактический exit, пустой diff, последовательные outputs и исправление зависимым автором с повторной проверкой покрытия при final. Общие решения включить в CF-04–CF-08, Codex-форматы оставить в native fixtures. Текущие generation fixtures используют `/bin/zsh`; его доступность проверяется для этого набора, не как общее требование ко всем harness.

Через `test-task-workspace.py` проверить workspace-часть CF-07 и CF-08 для покрытия изменённых путей. В journal tests проверить CF-04: повторная `validate_acceptance` внутри транзакции `finalize` отклоняет результат, изменённый после предварительной проверки, а идемпотентный повтор `finalize` не создаёт второй публикации. В package tests проверить integrity и readiness раздельно, включая отсутствие Codex environment для non-Codex target. Проверять выбранный source и отсутствие публикации при отказе.

Живой Codex сценарий выполняется после короткого source-read probe. Проверить identity/parent, модель, завершение и action evidence. Недоступность полного parent→child prompt сама по себе не блокирует `RP-03`; если недоступен конкретный обязательный факт, зафиксировать именно его и оставить соответствующую проверку незакрытой. Доставка новых model/profile instructions проверяется на этапе 2. Ремонт CLI, смена runtime или расшифровка источника не входят автоматически в этот этап.

Риск и фокус Devil's Advocate: decoder может незаметно забрать policy, `completed_turn` — потерять проверку нескольких моделей, а workspace/readiness — сохранить default Codex source. Проверить карту callers и обязательные cases этапа 1, включая alias identity и сверку fingerprint внутри транзакции. Завершение этапа для реализации — extraction и релевантные тесты; формальное закрытие — доказанные `RP-01`–`RP-03` и явный список pending cases этапа 2. Их наличие не блокирует parity этапа 1, но запрещает общий PASS corpus. Любой другой разрыв между реализацией и приёмкой указан явно.

Этап нельзя безопасно объединить с этапом 2: отдельно нужен результат «тот же Codex и та же строгость», прежде чем менять источник ожидаемой конфигурации и пользовательский workflow. Иначе расхождение моделей/приёмки нельзя уверенно отнести к extraction или новому выбору команды.

## 5. Этап 2. Предлагать и сохранять команду проекта

### Результат и затронутые контракты

После готового контекста Agent Flow предлагает назначения используемых ролей из доступных управляемых подключений. Принятый выбор сохраняется, а каждый новый assignment получает immutable snapshot. Настройка допускает разные targets; исполнение включается только там, где соответствующее подключение проверено.

Зависимость — runtime-neutral `AssignmentSpec`, capability result и Codex baseline этапа 1. Продолжать разработку при известном Codex evidence gap можно только с сохранением gap в итоговой приёмке; это не разрешение ослабить проверки.

Scope: расширить `scripts/agent_config.py`, `validate-agent-config.py`, `registries/model-profiles.json`; добавить `scripts/project_team.py` и тонкий CLI `scripts/configure-project-team.py` для валидации, чтения и guarded записи принятой конфигурации по expected revision/hash. Названия новых файлов — целевые границы ownership, не уже существующие команды. `init-run.py`, recorder и journal сохраняют snapshot существующим API. `sync-codex-agent-config.py` и существующий delegation packet/export получают profile instructions с приоритетом обязательных role/task rules и сохраняют прежнее поведение без override. Общие helpers выделяются только для реально общего кода guarded write; новые instruction engine или lifecycle не нужны.

В `references/project-memory-and-env.md`, `orchestrator.md`, `delegation.md`, `subagents.md`, `SKILL.md`, роли orchestrator и двух пользовательских руководствах добавить последовательность: актуальный контекст → используемые роли → discovery → предложение → принятие/переопределение → сохранение → dispatch. Новый `references/runtime-portability.md` описывает общие контракты и пользовательскую настройку. Package inventory и проверки конфигурации дополняются вместе с кодом.

Текущее правило роли «сохранять exact model ID» относится к модели зафиксированного назначения после resolution. В канонических role instructions убрать привязку этого правила к глобальному frontmatter; текущие Codex defaults сохранить как baseline. Если custom-agent TOML или session schema применяют новый project binding только после reload/новой сессии, показать состояния «сохранено» и «применено» отдельно и запросить нужное адресное действие. Уже запущенные агенты продолжают своё назначение; новый snapshot допускается к dispatch только после подтверждения эффективной host-конфигурации.

Предложение использует существующие defaults и совместимость с требованиями назначения; при отсутствии совместимого default показывает доступные варианты и пробел. Оно не утверждает превосходство модели по качеству. Уже принятый пользовательский выбор имеет приоритет. Новая роль, появившаяся после уточнения scope, проходит этот же шаг до её запуска; все роли каталога заранее настраивать не нужно.

### Приёмка, проверки и завершение

`RP-04` — два профиля конкретных моделей остаются различимыми при одном провайдере; один профиль поддерживает несколько допустимых reasoning-вариантов. Некорректный reasoning, неизвестный профиль, неподдержанный binding и незаявленная комбинация capabilities отвергаются до dispatch. Все observed model values сверяются после запуска. CF-03 проверяет фактическую доставку profile instructions и приоритет обязательных role/task rules. Названия моделей из примеров не попадают в available catalog без discovery.

`RP-05` — на новом проекте команда предлагается после контекста и до первого назначения; пользователь принимает и переопределяет отдельную роль, позднее меняет выбор. Сохранённый выбор читается при следующей задаче. Новая роль запрашивает только недостающую настройку. Глобальные role files неизменны при этих действиях.

`RP-06` — обновление team revision не меняет текущие или завершённые assignments и их hashes. Два writer одной старой revision не перезаписывают выбор друг друга: первый сохраняет, второй получает conflict и перечитывает актуальный выбор. Недоступное подключение не вызывает скрытый fallback. Два connection/host bindings сохраняются в проекте; CF-01 различает runtime namespaces и сводит aliases одной сессии к одной identity. Installed-only target не предлагается как управляемый.

Расширить `test-agent-config.py`, `test-validate-agent-config.py`, `test-sync-codex-agent-config.py`, `test-init-run.py`; добавить `scripts/test-project-team.py` для round-trip, override precedence, конфликтов revision/hash и одновременных writers. Реализовать оставшиеся pending cases CF-03/CF-07 и выполнить полный реализованный corpus для всех зарегистрированных к этому моменту адаптеров, включая Codex. Разные reasoning и aliases задаются fixture-каталогом; это не тест доступности вымышленных моделей.

Живой сценарий на реально доступном Codex connection: новый тестовый проект → контекст → предложение двух используемых ролей → подтверждение с override в поддержанных пределах → spawn → смена проектного выбора → повторное чтение текущего и нового assignment. Сохранить входы, предложенные строки, ответ пользователя и разрешённые значения; проверить отсутствие записи в глобальные роли. Capability discovery повторяется перед запуском, чтобы устаревший каталог не разрешал недоступный target. Несколько targets проверяются конфигурационными fixtures; это ещё не доказательство межприложенческого исполнения.

Риск и фокус Devil's Advocate: конфигурация может выглядеть переносимой, но validator продолжит читать свежий глобальный frontmatter или общий reasoning enum. Проверить изменение project/profile files между spawn и acceptance, а также совпадение имён effort при разных bindings. Этап закрывается при доказанных `RP-04`–`RP-06`, закрытых profile/config cases CF-03/CF-07 без pending и актуальных регрессиях этапа 1. Полный corpus проверен для текущего списка адаптеров; Kimi присоединяется на этапе 3, DSH — на этапе 4.

Этап отделён от этапа 3: механизм проектного выбора проверяется на уже работающем Codex, а Kimi имеет собственную неопределённость формата сессий. Объединение сделало бы недоступность источника Kimi неразличимой с ошибкой project resolver. От этапа 1 его отделяет новый контракт пользовательской конфигурации и immutable selection.

## 6. Этап 3. Подключить и проверить Kimi Code

### Условие старта и выбор механизма

Зависимости — выделенное ядро этапа 1, обязательный ранний Kimi probe и project bindings/snapshot этапа 2. На этапе 3 результаты probe развиваются в полный reader фактических сессионных журналов Kimi Code (`wire.jsonl` в каталоге сессий) текущей установки: фиксируются версия, структура записей, parent-связи субагентов, идентификаторы ходов, поля модели и события вызовов инструментов с результатами и изменёнными путями. Документация платформы этого формата не фиксирует; статическое чтение чужих сессий не заменяет собственный контролируемый запуск. Если источник не даёт конкретного обязательного факта приёмки (включая action evidence для CF-08), фиксируется адресный evidence gap. Недоступность полного prompt сама по себе не означает такой пробел.

Роли переводятся в Markdown-агенты `.agents/agents/` операцией `provision_roles`. По документации Kimi Code формат frontmatter близок к формату ролей Agent Flow; разрешения генерируются по обязанностям роли по контракту §3 (поле `tools` — реальный allowlist, а не декоративное описание): авторам нужны правки файлов (`Edit`/`Write`), QA и reviewer — чтение и собственные проверки (`Bash` и др.), делегирующим ролям — запуск субагентов (`Agent`) и ключ `subagents` с допустимыми получателями, ролям с внешними интеграциями — их MCP-инструменты. Проверка сгенерированных агентов входит в этап: allowlist каждой роли покрывает её обязанности, отсутствие необходимого инструмента — дефект генерации. `tool_vocabulary` заменяет Codex-имена `spawn_agent`/`apply_patch` при генерации для Kimi, а не в канонических role bodies. Механизм root identity определяется discovery текущей установки Kimi; `CODEX_THREAD_ID` остаётся входом только Codex-адаптера.

Установка — standalone-скилл в `.agents/skills/` или `~/.agents/skills/` по механизмам impl-011. Плагинный манифест `kimi.plugin.json`, публикация в маркетплейс Kimi и hooks-интеграция не входят в scope: Agent Flow hooks не использует, а сборка плагинов ограничена Codex.

### Scope и порядок

Обычный diff этапа ограничен `scripts/runtime_adapters/kimi.py`, генератором агентов Kimi (часть `provision_roles`), профилями/bindings моделей Kimi, точечной trusted registration, инвентарём пакета в `package_distribution.py`, `references/runtime-kimi.md`, установочной документацией `docs/en/installation.md` и `docs/ru/installation.md` для standalone-формы, а также native fixtures/tests. `scripts/test-runtime-kimi.py` проверяет только Kimi decoding/перевод native calls и генерацию агентов; общая приёмка запускается через CF-01–CF-08 в `test-runtime-contract.py`. В `testdata/runtime-adapters/kimi/` хранятся native данные этих сценариев, без копии expected verdicts.

Зафиксировать разрешённые paths этапа и проверить реальный diff штатным worker conclusion. Общие policy rules, journal/finalize и workspace не получают Kimi-ветвей. Необходимая правка общего ядра обрабатывается как пробел extraction по правилам §3.

Сначала проверить полный reader, разбор действий и комбинацию capabilities одним одноразовым назначением. Затем провести свежий положительный цикл author → QA → reviewer через общий recorder/validator с повторной валидацией и финальной публикацией. Для one-shot негативный цикл выполняется в отдельном run и завершается `failed`; исправление и новая положительная приёмка требуют нового run и новых исполнителей. Дополнить target-aware readiness этапа 1: временно материализованный standalone-пакет проходит Kimi smoke без Codex role setup и `CODEX_HOME`.

### Приёмка и живые сценарии

`RP-07` — независимые author, QA и reviewer Kimi связаны с действительными assignments по первичным записям сессий. Request config и наблюдаемые модели совпадают с bindings; доставка новых model/profile instructions подтверждена по source либо наблюдаемой host-конфигурации запуска; действия исполнителей разобраны из нативных событий (CF-08). Полный prompt не обязателен. Успешный ответ субагента без собственного завершения child-сессии не принимается. После свежей приёмки выполнить штатную повторную валидацию принятых отчётов с `current=False` и `finalize` со сверкой fingerprint через Kimi reader; поздние native-события сами по себе не блокируют чтение завершённого run. Без успешной финальной публикации `RP-07` не закрывается.

`RP-08` — поддержка продолжения сессий Kimi определяется discovery и не является обязательной capability. Если discovery подтверждает continuable custom-agent сессии Kimi, проверяется живое продолжение: выбранные модель/reasoning подтверждены первичным источником, followup дошёл в ту же сессию и породил новый завершённый ход. Если продолжение не поддерживается, `detect` декларирует это ограничение, fixture проверяет явный unsupported-отказ continue. One-shot поддержан с одним циклом приёмки на run: после неудачи — failed final, исправления и новый цикл в новом run, без замены исполнителя существующего assignment. Оба исхода закрывают `RP-08`; непроверенное состояние — нет. Отдельные отрицательные проверки: неподдержанный effort, неправильная модель, незавершённый ход. Continuation подтверждает capability; отдельный lifecycle повторных попыток не нужен.

`RP-09` — mutation принятого результата сохраняет зелёный старый тестовый набор, но меняет result fingerprint; validator отклоняет прежние QA/reviewer. В fixtures CF-05 проверить обе ветки restore: при исходном fingerprint неизменные зарегистрированные отчёты снова соответствуют результату, даже если позже был незарегистрированный native отказ; зарегистрированный failed report продолжает блокировать completed final. Для живого one-shot сценария взять контролируемую изменённую копию результата в отдельный негативный run: независимый QA выявляет mutation и регистрирует failed report, run закрывается failed. Исправление и полный положительный цикл с новыми исполнителями выполняются в новом run; failed run остаётся читаемым и не переоткрывается. Не добавлять нового QA для обхода failed assignment. Проверить также отсутствующий обязательный source, изменённый handoff, неправильного родителя, неоднозначный child ID, failed launch, неподтверждённую доставку новых model/profile instructions и правку файла без нативного действия автора.

Выполнить Kimi native decoder tests и полный CF-01–CF-08 для Codex и Kimi через их readers без pending; повторно использовать затронутые journal/workspace/config tests. Проверить пропущенную регистрацию/fixture отдельной отрицательной проверкой покрытия. Живые сценарии RP-07 и RP-09 остаются обязательными: fixtures и корректный unsupported-отказ их не закрывают. Повторить Codex smoke после подключения адаптера.

Риск и фокус Devil's Advocate: `wire.jsonl` может оказаться транспортным логом без parent-связей, observed model, завершения или событий инструментов — тогда конкретные факты приёмки не доказываются, и зависимая часть остаётся незакрытой до появления связуемого источника. Имя агента в Markdown-файле может быть принято за доказательство роли, а локальный profile file — за доставку новых инструкций; скопированный из Codex allowlist может обрезать роли по инструментам. One-shot нельзя выдавать за возможность заменить failed assignment свежей сессией в том же run. Этап закрывается при доказанных `RP-07`–`RP-09`; один проход conformance corpus не закрывает live evidence gap.

Этап отделён от этапа 4: Kimi проверяет контракт на среде с задокументированным форматом Markdown-агентов, DSH — на штатном subagent provider с developer preview. Объединение сделало бы причину отказа неразличимой между двумя разными механизмами сред.

## 7. Этап 4. Подключить и проверить текущий DSH

### Условие старта и выбор механизма

Использовать текущее установленное приложение DSH; зафиксировать его версию и фактическую schema перед проверками. Ожидаемая исходная версия — `0.2.0-rc.2`; учитывать статус developer preview: при обновлении установки версия и schema фиксируются заново, а результат прежних проверок не переносится автоматически. Не подменять проверку другой установкой, runtime или переустановкой. Действующая авторизация локальных тестов DSH, включая разрешённую работу с пилотным чатом, сохраняется; повторное общее разрешение на тестовые сессии не требуется. Дополнительное согласование нужно лишь для конкретного изменения настроек или доступа вне уже разрешённого scope, если оно потребуется.

Первое действие этапа — подтвердить управляемый production launch/continue channel и reader первичных журналов. Проверить в текущей среде доступность нативного subagent и session policy, способ адресовать child и читать source, включая события вызовов инструментов для action evidence. Различать запуск Agent Flow внутри DSH через его инструменты и удалённое управление DSH извне: пилот доказал первое через диагностическое взаимодействие, но не production connector второго. UI bridge пилота не переносится в production.

Субагенты в DSH реализуются провайдерами плагинов Cordis (`ctx.subagents`), а не Markdown-файлами. Сначала `provision_roles` передаёт role instructions и launch config через штатный provider и проверяет достаточность этого пути для назначения и доказательств. Только конкретный воспроизведённый пробел штатного provider может обосновать собственный plugin-контейнер ролей; до этого он не входит в обязательные scope, ownership и зависимости. Разрешения соответствуют обязанностям роли. Experimental-мосты совместимости hooks (`dsh-hooks-claude-code`, `dsh-hooks-codex`) не используются как production-механизм этой поставки.

Предпочтительный условный путь: штатный DSH subagent provider, который поддерживает `agentOptions` и `prepareContinuable`, с session policy выбора моделей (`modelSelectionSettings` и включённый выбор для сессии) и `backgroundMode=continuable`. На той же установке создать тестовую сессию в пределах действующей авторизации, проверить опубликованную schema и фактический вызов с provider/model/reasoning, затем продолжить ту же сессию. Если необходимое изменение настройки выходит за разрешённый scope, отдельно согласовать именно его. Возможность только в коде не переводит capability в supported.

Если путь требует изменения настроек за пределами разрешённого scope, до согласования этого изменения он остаётся unverified. Если канал управления или комбинация не подтверждены, выполнить независимые reader/contract fixtures, записать точное ограничение и оставить зависимые live-критерии незакрытыми. Workflow можно использовать для отдельных one-shot назначений с provider/model, но он не заменяет обязательный continuation-тест и явное управление reasoning. Продолжение новой сессией не считается same-session continuation. Полная поддержка DSH не объявляется до прохождения обязательного сочетания.

### Scope и порядок

Зависимости — выделенное ядро этапа 1, project bindings/snapshot этапа 2 и доказанный на Kimi адаптерный контракт этапа 3. Обычный diff этапа ограничен `scripts/runtime_adapters/dsh.py`, переводом role instructions/launch config штатного provider, профилями/bindings обнаруженных моделей, точечной trusted registration, инвентарём пакета, `references/runtime-dsh.md` и native fixtures/tests. Plugin-контейнер и его зависимости добавляются только при доказанном пробеле штатного provider, с адресным уточнением ownership и разрешённых путей. `scripts/test-runtime-dsh.py` проверяет только DSH decoding/перевод native calls; общая приёмка запускается через CF-01–CF-08 в `test-runtime-contract.py`. В `testdata/runtime-adapters/dsh/` хранятся native данные этих сценариев, без копии expected verdicts. Подключение следующего адаптера следует тем же правилам.

Зафиксировать разрешённые paths этапа и проверить реальный diff штатным worker conclusion. Общие policy rules, journal/finalize и workspace не получают DSH-ветвей. Необходимая правка общего ядра обрабатывается как пробел extraction по правилам §3 с повторной проверкой parity Codex и Kimi. DSH-specific обход внутри core запрещён.

Reader декодирует фактический `session.v4.jsonl.zstd` на текущей установке: session header, parent, catalog/workflow связи, request config, все `assistant/message.source`, входы, события вызовов инструментов с результатами и изменёнными путями и собственный `turn/end` ребёнка. Оценку этих фактов выполняет общее ядро. Зафиксировать способ декодирования и доступную зависимость, без скрытой установки. Использовать существующий порядок приёмки (чтение при accept/finalize, сверка fingerprint), точные event refs и source provenance; хеш всего сжатого файла описывает прочитанное состояние растущего журнала и не проверяется как постоянный hash будущих состояний. Неподдержанная версия, обрыв и неоднозначность источника дают gap/error. Новые DSH journal/lifecycle или долговременный архив всех raw bytes не нужны; секреты/private reasoning не попадают в fixtures.

Сначала проверить source-read, разбор действий и комбинацию capabilities одним назначением. Затем провести полный свежий цикл author → QA → reviewer через общий recorder/validator, continuation, stale rejection и финальную публикацию с повторной валидацией. Дополнить target-aware readiness этапа 1: временно материализованный standalone-пакет проходит DSH smoke без Codex role setup и `CODEX_HOME`. Использовать существующие packaging helpers, явно указанные workspace/файлы и действующую авторизацию; глобальная установка и миграция настроек не нужны.

### Приёмка и живые сценарии

`RP-10` — независимые author, QA и reviewer DSH связаны с действительными assignments. Request config и наблюдаемые provider/model совпадают с bindings; доставка новых model/profile instructions подтверждена по source либо наблюдаемой host-конфигурации запуска; действия исполнителей разобраны из нативных событий (CF-08). Полный prompt не обязателен. Сначала проверен штатный provider с role instructions/launch config; собственный plugin допускается только при доказанном пробеле. Успех workflow без собственного завершения child не принимается.

После свежей приёмки DSH выполнить штатную повторную валидацию принятых отчётов с `current=False` и `finalize` через DSH reader. Зафиксировать успешную публикацию `final.json`, неизменный result fingerprint и source refs принятых QA/reviewer. Проверить повторное чтение результата с DSH source при том же workspace scope, включая поздние native-события без изменения принятых доказательств. Без успешной финальной публикации и повторной валидации `RP-10` не закрывается, даже если отдельный validator уже вернул положительный результат.

`RP-11` — в одной проверяемой continuable-сессии выбранные provider/model/reasoning подтверждены первичным источником, followup дошёл в ту же сессию и породил новый завершённый ход. Провести отдельные отрицательные проверки неподдержанного effort/комбинации, неправильной модели и незавершённого followup. Это обязательная живая проверка сочетания; исторические два отдельных теста не закрывают её. В отличие от этапа 3, one-shot режим здесь полную поддержку не заменяет.

`RP-12` — до final изменить принятый результат так, чтобы старый тестовый набор оставался зелёным, но result fingerprint изменился. Validator отклоняет прежние QA/reviewer; новый завершённый ход того же QA assignment регистрирует failed report на текущем fingerprint. Восстановить исходные байты и вычислить fingerprint: зарегистрированный failed продолжает блокировать completed final. Продолжить ту же QA-сессию и штатно заменить её текущий отчёт completed-отчётом; затем reviewer в своём assignment проверяет новый QA hash и заменяет свой отчёт до final. Отдельно проверить restore без регистрации failed: поздний native отказ сам по себе не аннулирует прежний отчёт, если fingerprint и закреплённые доказательства совпали. Проверить также отсутствующий обязательный source, изменённый handoff, неправильного родителя, неоднозначный child ID, failed launch, неподтверждённую доставку новых model/profile instructions и правку файла без нативного действия автора.

`RP-13` — фактический diff соответствует `allowed_paths` назначений и подтверждает отсутствие DSH policy в core. Один набор CF-01–CF-08 с одинаковыми ожидаемыми решениями проходит для всех зарегистрированных адаптеров; coverage check обнаруживает отсутствующий adapter/fixture и silent skip. Project team хранит Codex, Kimi и DSH bindings, каждый поддержанный target проходит свой launch/read path и package readiness. Cross-app маршрут допускается только при доступном управлении и подтверждённой связи dispatch→child; иначе он явно отклоняется. Несколько bindings не доказывают работающую смешанную desktop-команду.

Выполнить DSH native decoder tests и один общий CF-01–CF-08 через readers всех зарегистрированных адаптеров; повторно использовать `test-verification-evidence.py`, `test-golden-traces.py`, `test-task-workspace.py` и затронутые journal/config tests. Проверить пропущенную регистрацию/fixture отдельной отрицательной проверкой покрытия. Через корневой `scripts/test-build-plugin.py` проверить integrity поставляемого пакета, а standalone smoke — отдельной материализацией. Живые сценарии RP-10–RP-12 остаются обязательными: fixtures и корректный unsupported-отказ их не закрывают. Повторить Codex и Kimi smoke после подключения третьего адаптера, без benchmark других моделей.

Риск и фокус Devil's Advocate: общую suite могут скопировать для DSH с более мягкими verdicts, unsupported-отказ выдать за support, а policy DSH — незаметно изменить модель/reasoning; ломающее обновление developer preview может устареть decoder между проверками. QA сопоставляет coverage всех адаптеров, native source и live evidence, reviewer — границы diff. Этап закрывается при доказанных `RP-10`–`RP-13`; неизвестный production channel или непроверенная обязательная комбинация оставляют соответствующую часть blocked, даже если conformance corpus проходит.

Этап нельзя объединить с этапом 3: DSH имеет собственный provider API и обязательное сочетание выбора модели/reasoning с продолжением той же сессии. Эти возможности требуют отдельного живого подтверждения. Успех DSH должен потребовать адаптер и binding без переписывания общего policy layer.

## 8. Исполнение через Agent Flow

Реализация начинается отдельным явным поручением пользователя. Оркестратор собирает актуальный контекст, сверяет зависимости и создаёт штатный run до делегирования. Бюджет выбирается по реальному объёму; число этапов не задаёт публичный режим и не добавляет selector/stage state machine.

Критерии приёмки run оформляются по действующему контракту 0.7.3: источник критериев — раздел задачи с подразделом «Критерии приёмки», содержащим непустой плоский Markdown-список; парсер `requirements` присваивает идентификаторы `ac-1` и далее. Для итогового run реализации источником служит полный список ниже. Если этап выполняется отдельной задачей, её уникальный раздел содержит относящиеся к нему пункты с явными RP-ссылками; непроверенные будущие этапы не объявляются passed. Проверка готовности плана не подтверждает выполнение RP реализации. Плоский список выбранной задачи — полный источник критериев run; тексты этапов дают контекст и обоснование. QA отчитывается по каждому `ac-N` со статусом `passed`/`failed`/`unverified`; reviewer проверяет актуальный completed QA по hash отчёта и независимость по execution identities — по правилам `accept_report`. Используются штатные assignments/reports/checks/generations/final, отдельный протокол приёмки не создаётся.

Решения и ограничения архитектора хранятся в одном штатном architect report и этом плане. Справочники архитектуры подключаются только для конкретного вопроса, без генерации отдельного brief/contract. Адаптеры изолируют нативные протоколы; источники и местные настройки не раскрывают private data; независимость и hashes доказываются первичными событиями; integration проверяет реальное выполнение. При подтверждённом пробеле общего контракта architect уточняет решение здесь и в своём отчёте, затем согласует затронутые assignments до зависимых правок.

### Ownership и запреты

Один `python-worker` на активный этап владеет перечисленными в его scope Python-модулями, JSON-конфигурациями и testdata. Этап 1 включает workspace library/tests, readers и validator callers, target-aware package readiness и названные корневые distribution scripts. Этап 2 — resolver, guarded team writes и packet/export. В этапах 3 и 4 разрешены соответствующий adapter, перевод ролей в нативный механизм, profiles/bindings, trusted registration, inventory и tests. Для DSH это сначала штатный provider; plugin-контейнер входит в ownership только при доказанном пробеле и уточнённых путях. На этапах 3 и 4 изменения общего core/journal/workspace запрещены без подтверждённого extraction gap и architect re-check. До spawn оркестратор задаёт точные абсолютные `allowed_paths` в штатном assignment; параллельная работа над общими файлами не назначается. `documenter` получает перечисленные Markdown-инструкции, runtime docs, role bodies, руководства и этот план; role config согласуется с Python worker. Инвентарь пакета в `package_distribution.py` и guards принадлежат Python worker.

QA и reviewer не реализуют продукт. `qa-verifier` сначала проверяет требования и наблюдаемые критерии, затем поведение; reviewer независимо проверяет финальные bytes и QA handoff. Architect делает re-check при изменении границ, возможностей, схем или политики приёмки. Оркестратор маршрутизирует, фиксирует артефакты и интегрирует результат через штатные journal команды; ручные callback-фразы пользователя не участвуют в завершении.

Запрещены вне отдельного поручения: чужая `.playwright-mcp/`, глобальные пользовательские роли/настройки, данные исторических runs, реальные credentials, новые провайдеры, benchmark jobs, CI/deploy, коммиты, переустановка приложений, скрытый fallback, новые распространяемые plugin-артефакты и marketplace targets для платформ кроме Codex. Условная локальная интеграция ролей DSH из §7 не расширяет пакетирование. Для DSH policy учитывается действующая авторизация; отдельно согласуются только изменения настроек или доступа за её пределами. Изменение scope или ожидаемого поведения возвращается пользователю; технический фикс внутри принятого контракта дополнительного approval не требует.

### Ожидаемые доказательства по критериям

Ориентиры для QA при разборе критериев `ac-N`; они не образуют отдельного протокола и не заменяют отчёт по `criteria`.

| Критерии | Основные доказательства | Обязательные отрицательные сценарии |

Положительные и отрицательные сценарии отчитываются раздельно внутри каждого критерия. Для contract-like критериев отрицательное или drift-доказательство обязательно до положительного закрытия. Отчёт автора сам по себе критерий не закрывает.

Stop conditions: ослабление проверок; необходимость переписать принятую историю; неподдержанная обязательная capability; отсутствие source для конкретного обязательного факта; необходимость нового transport/инфраструктуры вне scope. До подтверждённого раннего Kimi probe общий контракт не фиксируется. Отсутствие полного prompt само по себе не является stop condition; неподтверждённая доставка новых model/profile instructions оставляет адресный gap. Останавливается зависимая часть, независимые проверки и диагностика могут продолжаться. One-shot failure завершает run failed; исправление принимается новым run. Для continuable DSH допустима штатная замена текущего отчёта того же assignment до final. Подтверждённый дефект возвращается владельцу, пробел контракта — architect; отдельный gate или автоматическая смена модели не вводятся.

## Критерии приёмки

- RP-01: общий policy layer не содержит Codex-специфики; Codex decoder и общее ядро сохраняют решения 0.7.3 для call/output, FileChange и generation, включая различие авторства и успешной проверки; обязательный ранний Kimi probe подтвердил identity/parent, model, completion и actions/results до фиксации контракта; cases этапа 1 общего corpus проходят через Codex reader с явными pending cases этапа 2.
- RP-02: принятые журналы текущего контракта и golden traces читаются без изменения байтов и hashes; malformed envelope, неоднозначная identity, подмена source, конфликт legacy/new полей и изменение результата перед публикацией отвергаются; команды текущего CLI, включая record generation, сохраняют смысл, receipt replay не доказывает новое выполнение; текущий delta покрыт актуальными доказательствами авторства.
- RP-03: свежий Codex author → QA → reviewer проходит политику 0.7.3; неверная модель, нарушенная независимость, изменённый handoff, stale hashes и новое принятие stale/unfinished turn отвергаются; revalidate с current=False сохраняет принятый отчёт при поздних native start/unfinished/failed без регистрации, root continuation и чтение завершённого run; mutation/restore определяется fingerprint и текущими зарегистрированными отчётами; актуальность generation-покрытия проверяется отдельно по каждому output.
- RP-04: профили моделей различимы при одном провайдере; некорректный reasoning, неизвестный профиль, неподдержанный binding и незаявленная комбинация capabilities отвергаются до dispatch; доставка новых model/profile instructions адресно доказана по source или наблюдаемой host-конфигурации, без обязательной полной копии prompt; все observed model values сверяются после запуска.
- RP-05: команда проекта предлагается после контекста и до первого назначения; принятие, переопределение и позднейшее чтение сохранённого выбора работают без изменения глобальных ролей.
- RP-06: обновление team revision не меняет текущие и завершённые assignments; одновременные writers получают conflict без перезаписи; недоступное подключение не вызывает скрытый fallback; runtime namespaces различаются, aliases одной сессии сводятся к одной identity; installed-only target не предлагается как управляемый.
- RP-07: независимые author, QA и reviewer Kimi связаны с assignments по первичным записям сессий; observed models, доставка новых model/profile instructions и действия подтверждены без обязательной полной копии prompt; результат проходит revalidate с current=False и финальную публикацию через Kimi reader, завершённый run читается после поздних native-событий.
- RP-08: для Kimi доказано либо живое same-session продолжение с выбранными моделью/reasoning, либо явный unsupported-отказ continue с one-shot режимом одного цикла приёмки на run; после неудачи — failed final и новый run без переназначения agent_id, supersession и attempt-history lifecycle; отрицательные проверки выполнены.
- RP-09: Kimi mutation меняет fingerprint и отвергается validator; restore проверяет настоящий fingerprint и текущие зарегистрированные отчёты, failed продолжает блокировать completed final, один native отказ без регистрации — нет; живой негативный one-shot run с failed QA закрыт failed, исправление принято полным положительным циклом в новом run с новыми исполнителями; отрицательные сценарии source/handoff/parent/launch и доставки новых инструкций пройдены.
- RP-10: независимые author, QA и reviewer DSH связаны с assignments; observed provider/model, доставка новых model/profile instructions и действия подтверждены без обязательной полной копии prompt; штатный provider проверен первым, собственный plugin обоснован только конкретным пробелом; результат проходит revalidate с current=False и финальную публикацию через DSH reader, завершённый run читается после поздних native-событий.
- RP-11: в одной continuable-сессии DSH выбранные provider/model/reasoning подтверждены первичным источником и followup породил новый завершённый ход; отрицательные проверки неподдержанных комбинаций пройдены.
- RP-12: DSH mutation до final отвергается validator и новым ходом того же QA assignment; зарегистрированный failed блокирует completed final после restore, а незарегистрированный native отказ сам не инвалидирует принятый отчёт; до final QA штатно заменяет свой отчёт, reviewer проверяет новый QA hash; отрицательные сценарии source/handoff/parent/launch и доставки новых инструкций пройдены.
- RP-13: полный CF-01–CF-08 проходит для всех зарегистрированных адаптеров без pending и пропусков; diff соответствует allowed_paths и подтверждает отсутствие platform policy в core; каждый target проходит свой launch/read path и package readiness.

## 9. Общий контроль и поставка

Отдельного testing-only этапа нет. После четырёх этапов выполнить один общий контроль: полный CF-01–CF-08 для каждого trusted adapter без pending и пропусков, релевантные регрессии, `python3 -B skills/agent-flow/scripts/check-all.py` из корня репозитория, package inventory и адресный smoke временно материализованного пакета существующими distribution helpers. Частичный parity-результат этапа 1 не заменяет итоговый corpus или финальную публикацию. Общий итог отдельно показывает conformance, runtime readiness и живые Codex/Kimi/DSH workflows. Если проверка недоступна, сохранить причину; не превращать skip в PASS и не ремонтировать инфраструктуру молча. UI-тесты не нужны; DSH проверяется через согласованный нативный канал.

Поставлять изменение сначала с Codex defaults и явным opt-in Kimi и DSH. Существующие принятые журналы остаются неизменными. При проблеме с новым target выключить его для новых назначений и сохранить прежние snapshots/evidence; откат не удаляет историю. Никаких per-stage rollback-процедур или миграции всех старых планов.

Перед QA подготовить финальные статусы всех изменённых документов, включая этот план, и полный список delivery files. QA принимает текущий result fingerprint и handoff hashes, reviewer читает принятый актуальный отчёт QA и завершается позже QA. Любая последующая правка возвращает кандидата на соответствующую проверку. Затем штатные recorder/finalize закрывают run по [Definition of Done](../../references/definition-of-done.md). Общий контроль включает успешную финальную публикацию и повторную валидацию живого результата на каждом зарегистрированном adapter и сохранение Codex-пути. Наличие SHA или зелёных unit tests не заменяет эту цепочку.

Для начала исполнения требуется отдельное поручение реализовать план. Для живого этапа DSH сохраняется действующая авторизация локальных тестов; нужны доступный управляемый launch/continue channel и читаемые первичные источники. Для живого этапа Kimi нужна установка Kimi Code с доступом к сессионным журналам. Отдельное согласование требуется только при необходимости конкретного изменения настроек или доступа вне разрешённого scope. Точные route IDs, reasoning options и поддержка их сочетаний определяются discovery текущей установки. Алгоритм сравнительного ранжирования моделей и универсальные межприложенческие мосты остаются вне этой поставки.
