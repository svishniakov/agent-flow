## Результат для пользователя

Agent Flow остаётся одним продуктом с одним исходником. Пользователь выбирает
установку отдельного скилла или плагина Codex. Исправление правил, ролей или скриптов
попадает в обе поставки при следующей сборке. В Codex Desktop установленный плагин
доступен через `@`; его выбор подключает основной скилл Agent Flow.

Разработчик получает полный набор автоматических тестов перед локальным коммитом.
GitHub после каждого `push` проверяет последнее отправленное состояние ветки и
сохраняет новую сборку плагина. Это подтверждённая пользователем семантика:
промежуточные коммиты одного `push` отдельно не собираются.

Первый выпуск поддерживает Codex. Совместимость с ZCode и другими агентами
потребует следующего отдельного плана. Текущая работа не создаёт для них манифесты,
адаптеры или переключатель среды выполнения.

## Контракт поставки

1. `skills/agent-flow/` остаётся единственным редактируемым пакетом. Его `SKILL.md`,
   роли, references, registries, scripts и необходимые fixtures используются
   обеими поставками. Второго поддерживаемого дерева с копиями инструкций нет.
2. Корень репозитория становится корнем плагина Codex. Новый
   `.codex-plugin/plugin.json` указывает `skills: "./skills/"`. Метаданные,
   лицензия и существующие изображения включаются только с проверенными значениями
   и путями. Собственный MCP-сервер для упаковки скилла не нужен.
   В архиве сборщик создаёт `.agents/plugins/marketplace.json` с одной записью
   `agent-flow` и `source: {"source": "local", "path": "./"}`. Имя каталога
   `agent-flow`, его `interface.displayName` - `Agent Flow`. Каждая запись содержит
   `policy.installation: "AVAILABLE"`, `policy.authentication: "ON_INSTALL"`
   и `category: "Productivity"`; `policy.products` не задаётся. Этот каталог
   указывает на корень распакованного плагина; второго дерева `plugins/agent-flow`
   в исходниках нет. Обработку пути `./` подтверждает установочная проверка.
3. Один сборщик выпускает архив отдельного скилла и архив плагина из одного
   снимка исходников. Список включаемых файлов явный. В сборку не попадают `.git`,
   пользовательская `.agent-work`, конфигурации аккаунта, кэши или секреты.
   Репозиторные синтетические fixtures, нужные установленному пакету, сохраняются.
   Архивы не зависят от симлинков наружу и локальных абсолютных путей.
4. Сборка не переписывает исходники, индекс Git или глобальные установки.
   Временное дерево сборки находится вне области обнаружения скиллов. Даже после
   сборки Skills CLI находит в исходном репозитории ровно один Agent Flow.
5. Настройка ролей использует существующий генератор из установленного пакета.
   Наличие `agents/` внутри архива само по себе не считается регистрацией ролей
   Codex. До записи генератор проверяет весь набор конфликтов; пользовательские
   файлы и правки в ранее созданных файлах сохраняются. При конфликте команда
   завершает работу до первой записи и сообщает точные пути.
   Для управляемых файлов сверять сохранённый эталон предыдущей синхронизации;
   старые файлы без достоверной базы не считать автоматически разрешёнными к
   перезаписи. Повторная синхронизация неизменного результата безопасна.
6. Первый запуск плагина проверяет зависимости и соответствие ролей его пакету.
   Недостающая настройка показана как конкретное действие. Роли нельзя молча
   заменить обычными агентами или другой моделью. Установка плагина не обещает
   автоматическую загрузку всех дополнительных скиллов и подключение сервисов.
7. Пользователь может выбрать любой формат; в одном контексте работает одна
   активная форма Agent Flow. Для двух установленных копий инструкция описывает
   выбор активной формы средствами клиента и проверку источника вызова.
   При несовместимых конфигурациях подготовка объясняет конфликт до делегирования.
   Переход между форматами не удаляет другую установку и не меняет журналы проектов.
8. Обновление плагина выполняется средствами Codex и документированным обновлением
   его источника. После обновления повторно проверяются роли. Старый Git-updater
   остаётся для поддерживаемой им установки скилла и не изменяет кэш плагина.

Состав обычного скилла внутри двух архивов должен совпадать побайтно для одного
снимка. Различаться могут только внешняя оболочка плагина и метаданные сборки.

## Этапы реализации

Выбраны три этапа. Первый даёт устанавливаемый продукт, второй защищает локальный
коммит, третий автоматически собирает уже проверенную поставку на GitHub.
Проверки входят в каждый этап; отдельного этапа тестирования нет.

### Этап 1. Общая поставка и работа плагина Codex

**Цель и результат.** Из одного исходника получаются две проверенные установки.
Плагин виден в Codex Desktop, вызов через `@` запускает Agent Flow с его ролями.

**Границы изменений.** Добавить манифест Codex и сборщик в репозиторные `scripts/`.
Изменить только необходимые правила обнаружения корня пакета и явного вызова в
[SKILL.md](../../SKILL.md), проверку и синхронизацию ролей, инструкции установки
и обновления. Затронуты корневые README, документация пакета и тесты этих контрактов.
Существующие правила оркестрации, модели ролей и журналы не перерабатывать.

**Порядок и зависимости.** Сначала сверить поддерживаемый формат Codex и закончить
защиту синхронизации ролей, затем собрать обе поставки и проверить установки.
Проверять в отдельных временных каталогах и профилях: активный глобальный Agent
Flow, которым выполняется работа, не заменять. Если текущий Codex не регистрирует
роли из плагина, использовать явную настройку существующим генератором; не
проектировать недоказанную автоматическую регистрацию.

Путь установки первой версии: скачать архив, распаковать его в постоянный каталог,
добавить этот каталог в Codex и установить из него Agent Flow. Проверенный локальный
CLI предоставляет `codex plugin marketplace add <каталог>` и
`codex plugin add agent-flow@<имя-каталога>`; точные команды и соответствующие
действия Desktop зафиксировать в инструкции по результатам установки.
После этого запустить генератор ролей из фактически установленного скилла и
создать новую задачу. Имя каталога единое и задано в генерируемом marketplace;
версионный путь кэша Codex нельзя зашивать в команды.

**Критерии приёмки.**

- A1. Skills CLI обнаруживает ровно один скилл. Сохраняются действующие команды
  установки отдельного скилла и проверки его зависимостей.
- A2. Обе поставки содержат одинаковый общий пакет; каждый путь манифеста и каждая
  обязательная ссылка пакета разрешаются после переноса в другой каталог.
  Манифест плагина и marketplace проходят проверку актуальной схемы Codex, включая
  обязательные поля `policy` и `category`; распакованный каталог принимается клиентом.
- A3. В новой задаче Codex Desktop плагин можно выбрать через `@`; основной скилл
  получает явный вызов. Обычное сообщение без такого выбора или текстового маркера
  не запускает Agent Flow автоматически.
- A4. После настройки доступны все роли текущего каталога, с теми же инструкциями,
  моделями и reasoning. Проверяются чистая установка, повторная настройка,
  обновление и конфликт с пользовательским файлом. Конфликт не оставляет частично
  переписанный набор конфигураций.
- A5. При наличии обоих форматов документированный выбор одной активной формы
  даёт однозначный источник; несовпадение конфигураций выявляется до запуска
  субагентов. Удаление плагина
  сохраняет отдельно установленный скилл и чужие файлы.
- A6. В обеих формах одинаковая небольшая задача доходит до результата с реальными
  QA и reviewer, корректной привязкой их сессий и успешным `validate-run.py`.
  Проверка проводится в Codex Desktop и CLI на зафиксированных версиях клиентов.
  Недоступный клиент или модель означает незакрытый критерий, а не PASS.

**Проверки.** Добавить в полный набор тестов проверку состава архивов, отсутствия
внешних симлинков, путей с пробелами, обнаружения скилла и отказа при недостающем
ресурсе. Проверить оба JSON-документа; отсутствие обязательного поля `policy` или
`category` должно давать отказ до установки. Покрыть конфликт ролей, ручную правку управляемого файла, повторную
синхронизацию и попытку применить Git-updater к плагину. Прогнать
`python3 scripts/check-all.py` из исходного репозитория. Проверки установленной
копии запускать из самой копии, без подстановки исходного Git checkout.
Для A3 и A6 сохранить отдельные доказательства работы клиента: вывод команд,
версии, выбранный источник и журнал запуска. Платные прогоны модели не входят
в автоматический pre-commit или GitHub; они проверяют совместимость выпуска.

**Риски и фокус Devil’s Advocate.** Проверить, что установка из архива действительно
даёт работоспособный Agent Flow, а не только карточку в каталоге; все роли берутся
из нужной версии, чужие настройки сохраняются, дубликаты не дают двойного запуска.

**Условие завершения.** A1–A6 подтверждены для одной редакции, инструкции позволяют
повторить установку и обновление без доступа к машине автора.

**Почему отдельный этап.** Его результат можно установить и проверить до GitHub.
Смешивание с автоматизацией скроет разницу между дефектом пакета и дефектом
сборочного окружения. Он не зависит от локального Git-hook.

Второй выполнен с отдельно подготовленным окружением в чистом checkout на том же
Mac по разрешению пользователя. Выбранный Linux-контейнер отказал при запуске
Codex sandbox: `bwrap: No permissions to create a new namespace`. Успешная
проверка Linux или другой машины не заявляется. Отрицательный пробный коммит
остановлен за 234,972 секунды из-за ошибки в индексе, исправленной только в рабочем
файле. Неподготовленная ошибка не помешала двум корректным коммитам.

B1–B5 подтверждены полными прогонами и адресными сценариями: добавление,
удаление, переименование, частичное добавление, пробелы в путях, прерывание,
очистка, обязательные инструменты, пропуски, повтор настройки и чужие hooks.
Исполнитель сохраняет байты индекса; сам `git commit` может обновлять служебный
кэш индекса, сохраняя подготовленные записи. Проверки Codex sandbox выполнялись
без вызова платной модели. Доказательства нового результата находятся в задаче
`impl011-stage2`; журнал приёмки: `2026-09-16-impl-011-stage2-acceptance`.
Весь план остаётся `in_progress`: этап 3 не входит в этот результат.

**Цель и результат.** Локальный `pre-commit` разрешает коммит только после успешной
проверки того содержимого, которое попадёт в коммит, включая частично добавленные
файлы. Один полный набор тестов используется локально и впоследствии на GitHub.

**Границы изменений.** Существующий `check-all.py`, его тесты, репозиторный hook
и команда его подключения, описание окружения разработки. Добавить минимальный
исполнитель проверки снимка индекса Git. Отдельный тестовый фреймворк не вводить.

**Порядок и зависимости.** Сверить полный список автоматических тестов с командами
`check-all.py`; добавить тесты этапа 1. Зафиксировать версии Python, Node, Skills
CLI, Codex CLI, pnpm и нужных библиотек. Затем настроить hook. Подготовка окружения
выполняется явно один раз; отсутствие зависимости в проверке должно давать понятный
отказ. Нельзя заменить все тесты быстрым подмножеством или скрытым пропуском.

Снимок индекса проверять в отдельном временном Git checkout, поскольку текущий
`check-all.py` требует Git. Не использовать `stash`, `reset`, `clean` или перенос
неподготовленных правок пользователя. Временная проверка не должна рекурсивно
вызывать собственный hook. Установка hook действует на текущий клон, не на все
репозитории пользователя; существующие hooks и `core.hooksPath` не перезаписываются.

**Критерии приёмки.**

- B1. При подключённом hook перед обычным `git commit` выполняется весь
  автоматический набор, включая новые проверки упаковки. Любое падение блокирует
  коммит; успешное завершение разрешает его.
- B2. Проверяется индекс. Неподготовленное исправление в рабочем файле не скрывает
  ошибку коммитируемой версии; неподготовленная ошибка не ломает корректный снимок.
- B3. После успеха, падения и прерывания сохранены рабочие файлы и индекс;
  временный checkout удалён. Проверяются добавления, удаления, переименования,
  частичное добавление и пути с пробелами.
- B4. Недостающие обязательные инструменты и пропущенные обязательные тесты дают
  отказ с объяснением. Подтверждается выполнение sandbox-проверок с Codex CLI;
  они не требуют обращения к платной модели.
- B5. Одна документированная подготовка подключает hook в новом клоне.
  Повторное подключение безопасно. Конфликт с прежним hook останавливает настройку
  с инструкцией интеграции, сохраняя предыдущие файлы и конфигурацию.

**Проверки.** Выполнить реальные пробные коммиты только во временном репозитории
для B1–B3. Сравнить индекс и содержимое рабочих файлов до и после каждого случая.
Проверить отсутствие рекурсии, отсутствие зависимостей, существующий hook и повтор
настройки. Полный набор прогнать на локальной macOS и чистом целевом Linux runner;
проблемы sandbox или управления процессами исправить до обещания полного CI.
Зафиксировать длительность полного прогона как наблюдение, без выдуманного лимита.

**Риски и фокус Devil’s Advocate.** Главная ошибка здесь - зелёная проверка рабочего
дерева при ошибке в индексе. Также проверить, что «все тесты» не превращены в
условный набор и hook не нарушает незакоммиченные изменения.

**Условие завершения.** B1–B5 подтверждены, полный набор воспроизводится в чистом
окружении. Если выбранный Linux runner не позволяет выполнить обязательную
sandbox-проверку, выбрать проверенный macOS runner и явно зафиксировать причину;
не отключать тест для получения зелёного результата.

**Почему отдельный этап.** Hook защищает другую границу - содержимое локального
коммита и сохранность рабочего дерева. Его ошибки можно воспроизвести без GitHub.
Этап 3 использует уже проверенный набор и окружение, но не вызывает сам hook.

### Этап 3. Новая проверенная сборка после каждого push

**Цель и результат.** В каждом успешном запуске GitHub Actions доступны скачиваемые
архивы обеих форматов, версия сборки, исходный commit SHA и контрольные суммы.

**Границы изменений.** Новый workflow в `.github/workflows/`, параметры существующего
сборщика, метаданные сборки и инструкции скачивания/установки. Публикация каждого
коммита как стабильного релиза в публичном каталоге не входит в этот план.

**Порядок и зависимости.** После этапов 1 и 2 workflow получает точный снимок
`GITHUB_SHA`, подготавливает зафиксированное окружение, выполняет полный набор,
собирает архивы тем же сборщиком и проверяет распакованную поставку. Только после
успеха сохраняет её как artifact - файл результата запуска GitHub Actions.

Триггер `push` не ограничивается основной веткой или списком путей. Новый push
не отменяет предыдущую сборку автоматически. Удаление ветки не создаёт пакет,
поскольку новой редакции для установки нет. Обновление версии сборки не требует
автоматического коммита в репозиторий.

Каждый push здесь означает обычное событие при включённом workflow, без намеренной
команды пропуска CI в сообщении коммита. GitHub может не создать запуск из-за
`[skip ci]`, `[skip actions]` и других встроенных директив, включая `skip-checks`.
Такой пропуск не даёт новую сборку и не считается успешной проверкой. Инструкция
описывает восстановление обычным новым push без директивы пропуска. Обходить явную
команду пользователя отдельным механизмом этот план не требует.

Версия продукта хранится в одном месте - исходном манифесте Codex. Сборщик получает
базовую версию и добавляет номер запуска и повторной попытки в версию тестовой
сборки, например `X.Y.Z-dev.RUN.ATTEMPT`. Это шаблон, а не буквальное значение
манифеста. Commit SHA хранится рядом и входит в имя скачиваемого результата.
Повтор с теми же входами даёт те же байты архива; разные идентификаторы сборок
не перезаписывают прежние результаты. По SemVer такая предварительная версия ниже
стабильной `X.Y.Z`, поэтому переход на неё выполняется явной переустановкой по
проверенной инструкции. Автоматическое обновление со стабильного выпуска не
обещается. Две последовательные сборки должны устанавливаться без устаревшего кэша.

Права workflow ограничены необходимым чтением репозитория. Actions привязаны к
проверенным полным commit SHA, инструменты - к конкретным версиям. В сборку не
передаются аккаунт Codex или API-ключи. Загрузка artifacts перечисляет только
подготовленные файлы. Общий кэш хранит зависимости, а не доказательства успешных
тестов. Сбой тестов не позволяет выдать старую сборку за результат нового push.

**Критерии приёмки.**

- C1. Обычный push, push с несколькими коммитами, изменение только документации
  и push в другую ветку запускают проверку её вершины. Следующий push не отменяет
  уже начавшуюся проверку. Отдельный негативный сценарий подтверждает отсутствие
  запуска и новой сборки при встроенной директиве пропуска; следующий обычный push
  снова проходит полный набор. Искусственные события не заменяют реальный прогон.
- C2. Падение теста или проверки пакета делает запуск неуспешным; устанавливаемый
  artifact этого запуска отсутствует. Диагностические логи можно сохранить.
- C3. Успешная сборка содержит два архива с одинаковым общим пакетом, точный SHA,
  уникальную корректную версию и проверяемые SHA-256 суммы. Загруженный файл
  скачивается и проходит проверку состава и установки в чистом окружении.
- C4. Переход с предыдущей сборки на следующую не оставляет старые роли активными
  незаметно. Инструкция описывает обновление источника плагина, его настройки и
  создание новой задачи Codex после обновления.
- C5. В workflow нет записи обратно в исходную ветку, пользовательских секретов,
  собственных условий пропуска полного набора или автоматической отмены предыдущего push.
  Workflow использует те же тесты, что pre-commit.

**Проверки.** Проверить YAML с `actionlint`, права и закреплённые версии; прогнать
сценарии C1–C5 в GitHub на согласованной тестовой ветке при реализации. Включить
заведомо падающий тест и затем исправление; проверить вывод, exit codes и состав
artifacts. Скачать настоящий успешный результат и установить его по написанной
инструкции. Локальная имитация workflow не закрывает приёмку GitHub.

**Риски и фокус Devil’s Advocate.** Проверить точный commit сборки, отсутствие
старых artifacts при падении, полноту файлов и реальное обновление версии.
Скачиваемый artifact и публикация стабильного релиза должны быть различимы
в интерфейсе и документации.

**Условие завершения.** C1–C5 подтверждены реальными запусками; пользователь может
получить свежую сборку из успешного push и установить её. Настройку GitHub считать
завершённой только после такой проверки.

**Почему отдельный этап.** Внешний runner, события GitHub, права и хранение artifacts
имеют собственные причины отказа. Их проверка зависит от рабочего пакета и полного
набора тестов; локальная установка и локальный hook её не заменяют.

## Выпуск и совместимость

Отдельная установка скилла остаётся документированным способом распространения.
Первый плагин вводится рядом с ней после приёмки этапа 1. Автоматические сборки
этапа 3 имеют статус тестовых; они не объявляются стабильными публичными релизами.
Срок хранения artifacts задаётся явно в пределах политики репозитория и указан
в инструкции. Постоянное хранение стабильных выпусков и публикация в сторонние
каталоги потребуют отдельного решения о канале выпуска.

Git позволяет пропустить локальный hook, поэтому GitHub повторяет полный набор
независимо от него. Настройка обязательных проверок перед merge не входит в запрос.

При неудачном обновлении вернуть предыдущую проверенную поставку и соответствующие
ей управляемые конфигурации ролей. Не откатывать пользовательские правки, другую
форму установки или `.agent-work` в проектах. Старый artifact должен быть доступен
в пределах заявленного срока хранения.

## Основание готовности плана

Применены профильные скиллы:

- `plugin-creator`: структура манифеста и путей, упаковка общего скилла, проверка
  ресурсов и ограничения установки. Локальный валидатор не принят за доказательство
  всех возможностей текущего Codex; загрузку ролей подтверждает установка.
- `CI/CD Pipeline Security Expert`: минимальные права, закреплённые зависимости,
  отдельные результаты сборки и запрет выдавать непроверенный пакет за успешный.
  Примеры фильтрации файлов, пропуска дорогих тестов и публикации релизов не
  перенесены: пользователь запросил все тесты и каждый push.
- `humanizer-ru`: конкретные результаты и условия приёмки, без необоснованных
  обещаний совместимости или дополнительных процессных механизмов.

План проходит независимый `qa.requirements` и Devil’s Advocate по одной редакции.
Принятие документа не подтверждает выполнение A1–C5: эти критерии относятся к
будущей реализации. В её поставку включить этот план и все изменённые инструкции
установки, обновления, настройки окружения и выпуска, закрыв их фактические статусы.
