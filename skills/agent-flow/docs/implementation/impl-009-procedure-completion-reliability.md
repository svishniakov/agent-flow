# Штатная запись доказательств и проверка перед завершением

Implementation plan 009 · 2026-09-10 · база `main`, `969a0f613dc0d72da58fc36b8cd0c56480d698b3`.

Статус: реализация разрешена пользователем 2026-09-10. Первое независимое ревью Sol/high потребовало уточнить предварительную запись root UUID и точность времени; замечания внесены в эту редакцию. Независимое принятие текущего текста обязательно перед реализацией. Commit, merge, push и глобальная установка требуют отдельного разрешения.

## Цель и граница гарантии

Agent Flow должен выполнять доступную процедуру до объявления результата готовым: создавать штатный журнал, регистрировать реальные назначения, получать принятие текущей редакции от QA и reviewer, запускать итоговый валидатор и только после успеха закрывать задачу.

Локальный Python-валидатор контролирует вызванную проверку. Он не перехватывает произвольный финальный ответ Codex и запись `Status: done`, если агент вообще не вызывает команду. Поэтому план сочетает исправления исполняемого пути, порядок действий в инструкциях и обязательную проверку соблюдения этого порядка настоящей моделью. Новый скрипт-обёртка сам по себе не устраняет возможность пропуска команды; отдельный finalizer не добавляется.

Если свежий модельный прогон снова завершится без проверки, реализация не принимается. Полный запрет такого ответа потребует подтверждённой интеграции с механизмом завершения самого Codex. Наличие такого механизма здесь не установлено; новый launcher, hooks и изменения приложения в этот план не входят.

## Основания и уточнение диагноза

Проверена завершённая задача `01a08b73-fcad-7cb3-a5fa-a21fe229b89b`, «Реализовать intake PRD Flow v2 (new)». Подробные доказательства остаются в рабочей памяти проекта: `.agent-work/tasks/canonical-intake-final-audit-20260910.json`.

Фактически работали python-worker на `gpt-6-astra/medium`, QA на `gpt-6-astra/high` и reviewer на `gpt-5.6-sol/high`. QA и reviewer приняли одну редакцию из 20 файлов; текущие байты совпали с принятой редакцией. Распределение моделей исправлять не требуется.

Установлены следующие проблемы:

1. Root прочитал `--help` штатных команд, затем вручную создал несовместимый `delegation-summary.json`. Итоговый `validate-run.py` не вызван. Независимый запуск команды дал восемь ошибок и код выхода 1.
2. Отсутствие UUID в ответе инструмента было принято как ограничение среды. Реальные UUID и номера завершённых обращений присутствуют в исходных локальных сессиях. `CodexSessionSource.read` умеет читать известный UUID, но не искать назначение по возвращённому canonical task name.
3. Прямой вызов `completed_turn` для настоящего QA дал `source timestamp missing`. Codex записал `completed_at` как целое число секунд Unix, а `timestamp()` принимает только строку. Этот дефект скрывался за первой ошибкой структуры summary. Предыдущий вывод «сбой только в процедуре» был неполным.
4. Reviewer завершил ответ прозой и необрамлённым JSON. `final_json()` принимает целый JSON-объект либо завершающий fenced JSON. Прямое чтение этой сессии дало `completion final answer must end in a JSON object`.
5. Автор самостоятельно вычислил хеш только списка файлов. Контракт impl-008 включает также исходный снимок и границы задачи. Даже после исправления структуры старые handoffs не доказывают принятие штатного хеша.
6. Для S10 действительно запускали свежих агентов, но отсутствуют `behavioral_checks` и предварительная запись полных входных пакетов. Копии CLI JSON не доказывают точный текст переданных агентам инструкций.
7. В `references/orchestrator.md`, раздел Final Integration, установка `Status: done` стоит перед финальной валидацией. Общий запрет ложного завершения не устраняет это противоречие в последовательности.
8. `init-run.py` сейчас создаёт полный набор файлов и не имеет выбора compact. Поэтому инструкция «создать компактный запуск штатной командой» требует поддержанного способа инициализации, иначе снова оставляет агенту ручную сборку.

## Этап 1. Провести штатный запуск через весь контракт завершения

### Результат, зависимости и ответственность

До реализации повторно проверить ветку, текущие изменения, рабочую память и доступность подписки. Продолжать имеющуюся рабочую ветку, сохраняя подготовленные изменения. Незавершённая реальная приёмка V9 плана 008 остаётся отдельным обязательством; совпадающий прогон можно зачесть обоим планам только при выполнении критериев каждого.

При делегировании один Python-исполнитель владеет командами и их tests; root владеет инструкциями и интеграцией. QA и reviewer независимы от авторов. Модели и базовые уровни брать из действующих ролей: исполнитель Astra/medium, QA Astra/high, reviewer Sol/high. Повтор проверки не означает автоматической смены reasoning; повышение допускается только по существующему основанию и внутри точного ID модели. Новые попытки ради исправления журнала автоматически не назначать.

### 1. Исправить чтение настоящих сессий

- Сначала добавить падающую регрессию с наблюдаемым форматом `completed_at: 1789047701` и внешним `timestamp: "2026-09-10T13:41:41.240Z"`. Использовать обезличенную fixture, не копировать чужие полные журналы.
- Поддержать наблюдаемые форматы времени: ISO-строка с часовым поясом и целое число Unix-секунд. Исключить bool; не угадывать миллисекунды и единицы по длине числа. При отсутствии внутренней метки использовать внешнюю метку события по существующему правилу. Некорректное присутствующее значение не скрывать исправной внешней меткой.
- Целое число задаёт секундный интервал. Если есть внешняя метка события, она должна попадать в эту секунду; согласованную внешнюю метку использовать для уточнения порядка. Конфликт отклонять. Без внешней метки сохранять секундную точность; перекрывающиеся интервалы не доказывают строгий порядок. Проверить два последовательных завершения в одну секунду и конфликт внутреннего integer с внешним timestamp.
- Сохранить проверки собственного `task_started`, `turn_context`, единственного `task_complete`, роли, модели, родителя и совпадения итоговых ответов. Проверить порядок времени; точность Unix-секунд не выдавать за миллисекундную.
- Повторить read-only чтение исходного QA через production `CodexSessionSource`. Никаких правок исходного JSONL, подставных IDs и заменённых моделей.

### 2. Разрешать идентификаторы по данным среды

Расширить существующий recorder узким способом разрешения назначения: предлагаемые параметры `--resolve-session` и `--agent-path`. Корневой ID брать из уже заполненного `verification.root_thread_id`. Это поиск реальной дочерней сессии, а не проверка модели или запуска root.

Искать в том же каталоге исходных сессий, который использует `CodexSessionSource`. Кандидат обязан одновременно совпасть по точному canonical agent path, UUID родителя и канонической роли; найденный ID проверить штатным reader. Использовать только метаданные, не искать имя в произвольном тексте чужих диалогов. Если ID уже возвращён инструментом, сохранить прямой путь записи по нему.

При нуле совпадений, нескольких кандидатах, конфликте явного UUID с найденным или недоступных исходниках вернуть конкретную причину без записи успешного события. Не выбирать «самую свежую похожую» сессию. Повторный запуск назначения с тем же именем требует различимого ID, а не догадки по времени.

Для QA/reviewer номер обращения разрешать из собственного завершённого хода, связанного с нужным handoff и текущим хешем. Незавершённое продолжение или неоднозначный выбор не должны возвращать старое принятие. Поддержку добавить к тому же режиму recorder; явный `--completion-turn-id` сохранить. Найденные значения передать существующему `completed_turn`, не дублировать условия приёмки.

Вывод resolver должен содержать использованные UUID и номера событий для проверки. Не выгружать скрытые рассуждения. Обновление записи не создаёт дополнительную модельную попытку, не меняет историю и не записывает задним числом `spawned`: время регистрации и наблюдаемое время запуска различаются.

### 3. Дать один рабочий порядок записи

Вынести краткую обязательную последовательность в начало исполняемых инструкций оркестратора; подробные примеры оставить в `traceable-runs.md`. Удалить противоречащие инструкции, не размножать весь контракт по файлам.

Добавить в `init-run.py` выбор существующего формата `--mode compact|full`, сохранив прежнее поведение по умолчанию. Compact создаёт `run.md`, `checks.md`, `final.md`, штатный summary, timeline и нужный для verification `context.md` с исходным снимком; не создаёт фиктивную lane-map или архитектурные handoffs. Full сохраняет имеющиеся шаблоны. Несовместимые флаги compact с архитектурной генерацией отклонять до записи. `--reuse` не преобразует формат существующего запуска молча. Это выбор формата журнала, не новый режим работы Agent Flow.

1. До первого делегирования создать run через `init-run.py`, заполнить снимок исходного состояния и границы задачи. Использовать создаваемый summary версии 1. Затем через `record-agent-trace.py --execution-mode role-lane --stage verification --status active --verification-json ...` записать частичный verification: реальный `root_thread_id`, ссылки `initial_snapshot` и `task_scope`, `task_kind: null`, пустые `author_thread_ids`, `result_files`, `behavioral_checks`, `qa: null`, `reviewer: null`. Recorder заполняет отсутствующие SHA-256 ссылок и проверяет имеющиеся также на этом промежуточном шаге; result hash вычисляет только после установки `task_kind: change` и полного `result_files` перед QA. Этот шаг сохраняет root UUID до первого canonical-only spawn без ручной правки summary и без преждевременного хеша результата. `--reuse` сохраняет существующее состояние; некорректный summary требует явной диагностики и исправления, а не молчаливой перезаписи.
2. Зарегистрировать каждое назначение recorder. Ответ инструмента с одним canonical name направляет к разрешению ID из источника. Не превращать отсутствие ID в этом ответе в общий отказ от контракта.
3. До поведенческого теста сохранить полный начальный пакет и каждый followup, записать `behavior-input-prepared`. После запуска связать их с исходными событиями и UUID в `behavioral_checks`. При выборе такого критерия сразу зафиксировать достаточность доступных входов и `strict_inputs`; не ослаблять приёмку после обнаружения шифрования.
4. Перед QA зафиксировать полный task-owned `result_files` и вычислить хеш через существующий recorder. Передавать проверяющим именно этот хеш вместе со снимком и границами. Самодельные формулы хеширования исключить из рабочих примеров.
5. QA возвращает целый JSON-объект в точном формате `completed_turn`; повествовательный отчёт остаётся в handoff-файле. Пути handoff относительны run-каталогу и совпадают с `--artifact`. Reviewer получает уже зарегистрированное принятие QA и возвращает целый JSON с `qa_handoff_sha256`. Не расширять parser поиском произвольных фигурных скобок внутри прозы.
6. Recorder проверяет и регистрирует оба завершения. Ошибка оформления исправляется с сохранением исходных журналов. Если нужен новый ответ модели, использовать продолжение того же назначения с прежними моделью, достигнутым reasoning и счётчиком; старый ответ не переписывать.
7. Любое изменение результата после проверки делает принятие старого хеша недействительным. Запустить необходимые проверки изменённой редакции и получить новые подтверждения по существующей процедуре. Исправление лишь технического оформления журнала не требует полного повторения продуктовых tests, если результат и его доказательства не изменились.

Передать в каждое назначение полные инструкции роли и актуальные доказательства. После QA сразу проверять записываемость его завершения, до запуска reviewer; ошибку интерфейса не откладывать до конца.

### 4. Перенести завершение после проверки

Подготовить `final.md` с допустимым полем `Verdict`, необходимые события timeline и остальные документы. Пока финальная команда не прошла, это кандидат итогового отчёта, задача остаётся `in_progress`.

Вызвать обычный `validate-run.py --run-dir ...` без `--allow-pending` и `--allow-no-check`. Сохранить фактический stdout/stderr и код выхода в `checks/final-validation.txt`; отчёт команды не включать в собственный проверяемый хеш, не использовать его как кэш разрешения. Следующее завершение всегда требует свежего вызова валидатора. Соседние gates продолжают действовать.

При коде 1 исправить доступные технические ошибки и повторить команду. При недоступных обязательных доказательствах записать `verification.blocker` и отрицательный итог. Формулировки «готово, но инфраструктурный валидатор не заявляется», число пройденных тестов и текстовое одобрение reviewer не разрешают `done`.

Только после успешной финальной команды обновить текущую запись рабочей памяти на `Status: done` и сообщить итог пользователю. Это обновление памяти не меняет продуктовый результат. Если после проверки меняются результат, handoffs, summary или итоговый отчёт, выполнить нужное повторное принятие и свежую валидацию до завершения.

Диагностики команд должны называть нарушенное поле и следующий допустимый шаг: разрешение ID, регистрация собственного завершения, штатный пересчёт хеша либо повтор проверки. Не добавлять параметр обхода ошибок или автоматическое изменение критериев.

### Критерии приёмки и проверки

| ID | Критерий | Необходимое доказательство |
| --- | --- | --- |
| P1 | Reader принимает настоящий формат времени | Регрессия numeric Unix time падает до исправления и проходит после; порядок двух завершений в одну секунду подтверждается согласованными внешними метками. Bool, конфликт меток, некорректные значения и чужие/унаследованные обращения отклоняются. Read-only проверка исходного QA больше не падает на времени |
| P2 | Canonical name разрешается без догадок | Tests одного, нулевого и нескольких кандидатов, одинаковых имён у разных root, конфликта роли/UUID, незавершённого продолжения. Реальное назначение с ответом без UUID записано по найденному исходнику |
| P3 | Весь путь записи работает публичными командами | Compact init, частичный verification с root UUID через recorder, canonical-only spawn и resolver по exact path/parent/role, затем change verification, штатный хеш и зарегистрированные QA/reviewer без ручного создания summary. CLI test последовательно выполняет эти команды; отрицательные шаги не записывают успешные события |
| P4 | Формат ответов совместим с reader | Целый JSON и уже поддерживаемый fenced JSON принимаются; неподдерживаемое оформление диагностируется сразу после QA. Неверный путь, чужой QA hash и самодельный result hash отклоняются |
| P5 | Завершение происходит после валидатора | В исходном логе реального root успешная команда предшествует записи `done` и положительному финальному ответу. Прогон с намеренно отсутствующим обязательным полем не объявляет готовность; после исправления команда повторяется |
| P6 | Поведенческие доказательства готовятся вовремя | Свежий краткий диалог с синтетическим источником: полные входы сохранены до отправки, исходные события и outputs связаны. Валидатор отклоняет позднюю копию; QA отклоняет отсутствие записи по выбранному критерию. При недоступных строгих входах итог blocked |
| P7 | Принятие относится к текущей редакции | Изменение результата, границ или QA handoff делает старое принятие недействительным. После требуемого повторного принятия новый результат проходит; посторонний файл вне задачи его не сбрасывает |
| P8 | Нет регрессии режимов и соседних правил | Compact/full/auto, analysis, отрицательные архитектурные fixtures, `--reuse`, история A/B/C, роли, модели и reasoning сохраняют правила impl-007/008 |

Для P6 недостаточно проверять только непустой массив после заполнения. До запуска тестов поведенческие обязательства должны быть явно отражены в scope/плане и QA checklist. Независимый QA сверяет выбранные критерии с `behavioral_checks`; существующий валидатор проверяет их структуру и исходники. Универсальный смысловой parser произвольного Markdown не добавляется. Модельный отрицательный прогон проверяет именно то, что пропуск обязательной записи не превращается в положительный итог.

Регрессии нового дефекта времени и разрешения IDs сначала показать падающими. Воспроизведение прежнего некорректного summary уже должно падать на базе: это сохранённая защита, а не новая исправленная регрессия. Исторический run не ремонтировать и не выдавать поздние копии за исходные доказательства.

Детерминированные tests записи используют существующую внутреннюю подстановку `session_source` при вызове той же функции команды; при необходимости сделать аргументы её `main` тестируемыми без изменения production-источника. Не добавлять CLI-флаг или переменную среды для загрузки экспортированного JSONL вместо настоящей сессии. Проверки subprocess относятся к настоящему разбору параметров и отказам; полный публичный путь подтверждают реальные прогоны ниже.

Локально выполнить существующие `test-verification-evidence.py`, `test-init-run.py`, `test-validate-run-lanes.py`, `test-golden-traces.py`, затем `check-all.py` и `git diff --check`. Новые узкие тесты зарегистрировать в существующем check-all. Временные проекты и генерируемые конфигурации не должны менять глобальную установку.

### Реальные прогоны и независимая приёмка

Через подписку выполнить свежий compact docs/change в Desktop и небольшое full code/change в CLI, с настоящими QA/Astra и reviewer/Sol. В одном включить поведенческий критерий и один заранее обозначенный сбой регистрации. Задания использовать синтетические; проверяемая версия skill берётся из временной копии пакета и явно передаётся всем участникам. Источник сессий остаётся штатным.

Наблюдатель проверяет исходные tool calls, `task_complete`, модели, последовательность подготовки входов, вызов валидатора, его результат и момент записи `done`. Самоотчёт модели, успешный unit test и два несвязанных запуска не закрывают P2/P5/P6. При отсутствии UUID непосредственно в ответе инструмента использовать resolver; при отсутствии самих исходников зафиксировать точный блокер.

Реальный CLI не заменять API. Сбросы подписки автоматически не использовать. Недоступная обязательная среда оставляет соответствующий критерий открытым; доступную работу завершить. Старое отрицательное воспроизведение допускается тестировать на обезличенных fixtures, но оно не заменяет новый успешный модельный прогон.

Итоговую реализацию принимают отдельные QA на Astra и reviewer на Sol по действующей матрице. Reviewer проверяет точный diff, результаты P1–P8 и фактическое соблюдение процедуры root. После исправлений повторить затронутые проверки и ревью изменённой редакции. Эти назначения разрешены текущим запросом после реализации; ревью плана выполняется перед ней.

### Риски и условие завершения этапа

При независимом ревью проверить прежде всего: ложное разрешение чужой сессии; ошибочные единицы времени; принятие устаревшего обращения; новый ручной путь заполнения вместо recorder; постановку `done` раньше проверки; подмену полного входного пакета CLI JSON; ослабление `strict_inputs`; обещание запрета финального ответа без механизма в Codex.

Этап завершён только после P1–P8, доступных локальных проверок, обоих реальных прогонов и независимого принятия актуальной редакции. Повторный пропуск процедуры моделью означает незакрытый P5, даже если все Python tests прошли. Не переименовывать этот результат в успех с оговоркой.

## Границы выпуска

Не менять PRD Flow и другие продукты, исторические журналы, глобальный конфиг, модельный resolver, пределы reasoning, счётчики попыток и матрицу ролей. Не добавлять registry, сервис, новую state machine, новые workflow-режимы или автоматическую миграцию старых запусков.

Реализация согласована пользователем; перед изменением кода требуется независимое принятие текущей редакции плана. Commit, merge, глобальная установка и push требуют отдельного разрешения после реализации и проверки. Само создание этого документа не означает, что описанная проблема уже исправлена.
