## Цель

Новая задача не должна останавливаться только потому, что старая запись осталась
`in_progress` или `blocked`. Перед остановкой агент проверяет фактическую зависимость.
После завершения работы он закрывает все её документы и записи в затронутых
репозиториях. В завершающий коммит документы входят с явной отметкой `done`.

Коммит подготовленного плана завершает документ. Коммит части реализации не
завершает всю функцию. Статусы должны сохранять эту разницу.

## Стек и выбранный подход

Стек затронутого механизма: Markdown-инструкции, Python со стандартной библиотекой,
существующие recorder, validator и тесты. Новые библиотеки и сервисы не нужны.

Применён `implementation-plan-authoring`: один связный этап, проверки входят в него,
готовность плана требует независимого Devil’s Advocate. `code-as-agent-harness`
применён к разделению сохранённой памяти, фактического состояния и проверяемого
условия завершения: текстовые guards дополняются настоящими поведенческими прогонами.
`markdown-documentation` применён к ссылкам и структуре критериев, `humanizer-ru`
к формулировкам и различию между готовым документом и выполненной реализацией.
Пробелов в доступности профильных навыков для этого объёма нет.

Сначала исправить канонические инструкции и порядок действий, затем подтвердить
их настоящими запусками. Не создавать новый менеджер задач, Markdown-парсер всей
памяти, новый реестр статусов, daemon, блокировки Git или автоматическое закрытие
всех исторических планов. Анализ смысла задачи остаётся у агента; скрипт не может
вывести завершение функции только из слова `done` или существования коммита.

### 1. Проверять зависимость после сверки фактов

`Status: in_progress` и `Status: blocked` служат поводом прочитать запись.
Они не подтверждают, что другая сессия сейчас меняет проект.

До классификации агент выполняет ограниченную проверку по найденной задаче:

1. Читает её scope, оставшиеся пункты и причину блокировки. Сопоставляет с новым
   запросом по конкретным файлам, контрактам и необходимым результатам.
2. Ищет поздние записи о завершении по тому же plan/task ID в памяти и связанных
   документах всех указанных репозиториев. Проверяет имеющиеся SHA и результат
   проверок. Не считает похожее название или общий раздел Reports доказательством
   конфликта.
3. Если дана ссылка на сессию, читает её фактическое состояние доступным инструментом.
   Завершённая или прерванная сессия сама по себе не доказывает завершение реализации.
   Недоступность списка сессий сама по себе также не создаёт блокировку.
4. Отделяет состояние старой работы от её отношения к новой задаче. Невыполненная
   работа может быть независимой; завершённый документ может описывать ещё будущую
   реализацию.

| Проверенные факты | Решение |
| --- | --- |
| Позднее подтверждённое завершение, прежняя причина `blocked` снята, новых работ по этой записи нет | Исправить старую запись точечно; продолжить |
| Другая работа продолжается и меняет тот же необходимый файл или контракт | Остановить зависимую часть, назвать факты и реальное пересечение |
| Старая работа незавершена, но новая от неё не зависит и не меняет её область | Продолжить новую задачу; старый статус сохранить |
| Нет данных для закрытия старой записи, но независимость нового scope подтверждена | Продолжить; не присваивать старой работе `done` |
| Новая задача требует результата старой, а готовность этого результата не подтверждена | Проверить доступные источники; при оставшемся существенном пробеле остановить зависимую часть с точным недостающим фактом |

Возраст записи, неотмеченный checkbox, отсутствие прежнего run и формулировка
`uncertain` не служат самостоятельным запретом. Существенная неопределённость
блокирует только конкретную зависимость. Независимую часть разрешённой работы
продолжать. Пользователя привлекать после доступной проверки, когда без его решения
или отсутствующего факта нельзя безопасно продолжить зависимую часть.

Настоящие конфликты не обходить автоматическим закрытием. Сохранить существующие
варианты ожидания, объединения работ или согласованного разделения scope.

### 2. Исправлять историческую запись без повторного выполнения старой задачи

Применять одинаково к `in_progress` и `blocked`. Не требовать полностью отмеченного
старого checklist, если поздние проверенные материалы прямо подтверждают его
пункты. Для `blocked` отдельно подтвердить снятие указанной причины.

Точечная запись закрытия содержит идентификатор задачи, что завершено, источники
проверок, SHA и репозиторий, когда commit был частью поставки, дату и причину
исправления статуса. Ссылки на позднее завершение имеют приоритет над ранним pending.
Не отмечать пункты выполненными только потому, что появился коммит. Если часть
работы перенесена, указать её продолжение, сохранив незавершённые требования.

Для исправления памяти достаточно проверить источники закрытия. Новый QA/reviewer
старой реализации и новый run для неё не требуются. Текущая реализация всё равно
проходит действующую независимую приёмку. Старые журналы, итоговые сообщения и
доказательства не переписывать. Повторная сверка той же записи ничего не добавляет
и не возвращает её в активные блокеры.

### 3. Закрывать все документы завершённой поставки

В начале задачи root составляет в существующем scope полный список связанных
документов: PRD, ADR, design/spec, implementation plan, исследование и другие
создаваемые или меняемые документы. При работе в нескольких репозиториях список
и проверка относятся к каждому из них. В список включать также исходный план,
чья реализация завершается, даже если продуктовые правки его ещё не затрагивали.

Использовать явные поля в служебном блоке документа:

```text
Document status: done
Implementation status: not_started
```

`Document status` описывает завершение текущей редакции документа. При подготовке
это `in_progress`; завершённая и проверенная редакция получает `done`.
`Implementation status` требуется у плана или спецификации, по которым выполняется
отдельная реализация: `not_started`, `in_progress`, `blocked` или `done`.
У исследования и справочного документа без отдельной реализации это поле не нужно.
Существующие статусы решения ADR (`accepted`, `rejected`, `superseded`) сохранить:
они описывают решение, а не готовность текста.

При завершении реализации закрыть относящиеся к ней implementation-статусы и
чеклисты связанных документов. Удалить или явно пометить историей противоречащие
активные формулировки. Частичная реализация, незакрытый критерий или промежуточный
коммит сохраняют соответствующий `in_progress` или `blocked`.
Каждый коммит готовых документов содержит `Document status: done`; это не позволяет
объявить незавершённую реализацию выполненной. Незавершённый черновик не включать
как готовый документ; явный пользовательский запрос на промежуточный снимок
сохраняет правдивый статус и обозначение WIP.

### 4. Согласовать статусы, проверку и commit

1. Закончить продуктовый scope и проверки. Подготовить окончательные статусы
   связанных документов до снятия хеша и передачи QA/reviewer. Пока приёмка не
   завершена, это кандидат результата, а текущая запись задачи остаётся активной.
2. Проверить каждый документ из списка, совпадение его статуса с фактическим
   результатом, наличие в `result_files` и отсутствие забытых связанных документов.
   QA и reviewer принимают полные bytes, включая поля завершения.
3. Если commit разрешён, сверить staged diff со списком принятой поставки.
   Проверить статусы в index, затем создать scoped commit. Проверить его SHA
   и содержимое документов через `git show`, отдельно для каждого репозитория.
4. Записать commit evidence в рабочую память и timeline, подготовить final,
   выполнить свежий штатный `validate-run.py` без ослабляющих флагов. Только затем
   закрыть текущую запись задачи и дать положительный итог.

Хеш собственного будущего коммита не писать внутрь документа этого же коммита.
Он сохраняется в памяти и журнале после commit. Изменение статусов документов
после QA меняет результат и требует повторного принятия изменённой редакции.

При неудаче commit текущая задача остаётся незавершённой по поставке; не сообщать
о сохранённых в Git документах. При отказе финального validator после успешного
commit сохранить его SHA и конкретную непроверенную часть, продолжить исправление
в рамках разрешения. Сам commit не превращает всю задачу в `done`.
Если commit не запрошен, не создавать его как условие закрытия: готовый документ
и задача подготовки могут завершиться после применимой приёмки.

### 5. Проверить поведение, а не только формулировки

Текстовый guard обновить вместе с каноническими инструкциями и запретить прежние
безусловные правила `stale notes => uncertain => stop`, остановку до доступной
сверки и повторную приёмку старой реализации ради исправления памяти.
Проверка наличия строки не называется доказательством поведения.

Для сценариев ниже использовать настоящие изолированные запуски с исправленным
пакетом. До запуска сохранить полный вход, критерий и ожидаемые наблюдаемые
действия. Использовать действующий формат `behavioral_checks` и независимый QA;
подмена ответа модели синтетическим transcript не принимается. Git-репозитории
с историей для проверок создаются во временной папке; реальные CRM-репозитории
не изменяются. Недоступный запуск остаётся непроверенным критерием.

| ID | Сценарий | Критерий приёмки |
| --- | --- | --- |
| S1 | Старый `in_progress`, неотмеченные пункты, позднее завершение и проверки в соседнем репозитории | Агент сверяет источники, исправляет запись, начинает новую разрешённую задачу без вопроса «закрыть старый план?» |
| S2 | Старый `blocked`, затем отдельное подтверждение снятия причины | Запись закрыта точечно; повторный запуск даёт тот же результат без дубликата closure |
| S3 | SHA есть, обязательный критерий не выполнен | Агент не закрывает реализацию по одному commit |
| S4 | Другая сессия меняет общий необходимый контракт | Агент обнаруживает подтверждённое пересечение и останавливает зависимую часть; не закрывает чужую работу |
| S5 | Данных для закрытия старой задачи мало, новый scope независим | Новая работа продолжается; старая запись остаётся правдивой |
| S6 | Новая задача требует старого результата, готовность недоказана | После доступной сверки назван конкретный пробел и зависимая часть остановлена; независимая часть продолжается |
| S7 | Подготовка и commit нового плана без реализации | В Git `Document status: done`, `Implementation status: not_started`; задача подготовки завершена, будущая функция не объявлена готовой |
| S8 | Полная реализация в двух репозиториях, PRD и план ранее отслеживались отдельно | Завершающие коммиты содержат все относящиеся документы с корректными done-статусами; закрыты записи обоих репозиториев; следующий запуск не блокируется ими |
| S9 | Документ изменён после QA либо commit завершился ошибкой | Нет ложного положительного итога; требуются актуальное принятие либо завершение поставки, без выдуманного SHA |
| S10 | Commit не запрошен; рядом чужие активные документы и исторический run без современных evidence | Завершение текущего scope не требует commit и повторной сертификации старого run; чужие документы сохранены |

S1, S2 и S8 обязательны в новой сессии после завершения предыдущей: один успешный
финал не доказывает отсутствие блокировки при следующем старте. В S4 проверять
реальную параллельную сессию, не имитировать активность словом `in_progress`.
В S8 проверять bytes обоих коммитов и повторный intake, а не только текущий worktree.

### Проверки, риск и условие завершения

Выполнить `python3 skills/agent-flow/scripts/check-all.py` и `git diff --check`.
Для инструкций прочитать полный diff и поиском проверить все места остановки и
закрытия, включая роль оркестратора и EN/RU описание. Если изменены существующие
tests, выполнить соответствующие suites; не переписывать старые журналы ради PASS.

Основной риск: ослабление проверки может пропустить настоящий конфликт, а
безусловное закрытие по commit может скрыть незавершённые требования. S3, S4 и S6
проверяют эти случаи. Отдельный фокус Devil’s Advocate: полнота списка документов,
честность двух статусов, работа без списка сессий, отсутствие повторной приёмки
истории, сохранность чужих записей и порядок status/hash/QA/commit/validator.

Этап завершён, когда S1–S10 подтверждены, QA и reviewer приняли текущую редакцию,
штатная финальная валидация прошла и документы самого фикса закрыты по новому
контракту. Фикс не обещает перехватывать произвольный ответ Codex или запрещать
commit вне Agent Flow: гарантия относится к соблюдению проверенной процедуры.

### Условия поставки

Выполнить весь разрешённый этап и применимые проверки.
Commit разрешён пользователем после успешной верификации и независимого ревью; в него включить код
проверок, инструкции и завершённый impl-010. Push и глобальная синхронизация
установки требуют разрешения на эти действия. Массовая миграция старых документов
не входит в фикс: старые записи сверяются при обращении к ним, связанные документы
закрываются при завершении своей поставки.
