## Выбранный подход

Два этапа: согласованное хранение всего опубликованного журнала в одной локальной SQLite-базе; затем отдельная рабочая копия с исходным снимком, полным сравнением и сохранённым кандидатом для приёмки. Рабочую копию и принятый результат сохраняет инструмент. Штатная поставка указывает их точные пути и автоматически подготовленный состав изменений. Исходник не изменяется; автоматическое применение назад и универсальное слияние в объём не входят. Это уточнение передано root в ходе исследования.

У пользователя остаётся обычная задача и понятный результат. Он не создаёт, не редактирует и не проверяет JSON, SQLite, идентификаторы повторов или служебные списки файлов.

SQLite выбран вместо собственного протокола каталогов редакций и атомарного указателя. Python уже предоставляет интерфейс sqlite3; отдельного сервера не нужно, но модуль optional в некоторых сборках Python, поэтому его наличие проверяется до инициализации. В текущем окружении доступны Python 3.12.6 и SQLite 3.45.3. [Python sqlite3](https://docs.python.org/3/library/sqlite3.html).

## Контракт хранения

Единственный источник опубликованного состояния нового run: `run/.journal/state.sqlite3`. Имена здесь предложены для реализации; это новый внутренний формат хранения, а не новая схема lane-map или режим Agent Flow.

Минимальные таблицы:

| Таблица | Содержимое и назначение |
| --- | --- |
| `run_state` | Единственная строка: версия хранения, run UUID, номер редакции, логический run root, исходный project root; после этапа 2 также идентичность workspace и ссылка на sealed candidate. |
| `documents` | Канонический логический путь, тип file/directory, исходные bytes файла и SHA-256. JSONL, JSON, Markdown, handoffs, checks, artifacts и необходимые пустые каталоги составляют один набор. |
| `operations` | Устойчивый идентификатор операции, digest содержательных входов, committed revision и результат вызова. Запись подтверждения сохраняется в той же транзакции, что документы. |

Не дробить доменные JSON-поля на дополнительные реестры. Общий модуль хранит bytes и транзакции, существующие функции продолжают проверять роли, приёмку и структуру. SQLite connection не передаётся агенту как интерфейс составления отчётов.

Каждая запись начинает `BEGIN IMMEDIATE`, читает текущие документы внутри этой транзакции, проверяет входы и строит полный набор связанных изменений. Затем одним COMMIT публикует документы, номер редакции и receipt операции. Timestamp журнала назначается при сериализации операции; время события исходной сессии остаётся отдельным фактом. Не читать summary/timeline до блокировки и затем сохранять вычисленное поверх более нового состояния.

Отдельные соединения используют `journal_mode=DELETE`, `synchronous=EXTRA`, `read_uncommitted=OFF`, без shared cache. На Darwin включается `fullfsync=ON`. PRAGMA задаются и перечитываются на каждом соединении; молчаливого перехода на MEMORY/OFF/WAL нет. `BEGIN IMMEDIATE` сериализует writers; при занятой базе команда ограниченно ждёт и возвращает понятную техническую причину без изменения данных. SQLite не показывает читателю чужую незавершённую транзакцию. [SQLite isolation](https://www.sqlite.org/isolation.html), [SQLite transactions](https://www.sqlite.org/lang_transaction.html).

Писатель не держит транзакцию во время работы модели, subprocess-проверок или ожидания агента. Внешнюю evidence он заранее захватывает в bytes; при публикации перепроверяет относящиеся к ней текущие journal preconditions. Изменённые preconditions требуют повторного вычисления, а не перезаписи новым результатом старого snapshot.

### Чтение, экспорт и ссылки

`JournalSnapshot` открывает read transaction, первым SELECT фиксирует редакцию и считывает её набор документов. После этого immutable bytes-map можно использовать без долгой SQLite-блокировки. Все операции read/exists/list/section/reference выполняются через этот объект. Для большого run допустим внутренний неизменяемый snapshot export вместо хранения всего map в RAM; его bytes должны быть захвачены одной read transaction. Не вводить виртуальный Path, незаметно перечитывающий «текущую» редакцию.

Вход `--run-dir` остаётся логическим адресом run. Новые reader entry points создают snapshot один раз и передают его всем вложенным проверкам. `harness_promotion` проверяет и читает одну редакцию; subprocess validator получает готовый snapshot identity, либо вызывается тот же Python validator напрямую с объектом snapshot. Не проверять одну редакцию и продвигать записи другой.

JSON/Markdown для чтения человеком экспортируются в `run/.journal/views/<revision>/`. Инструмент выводит точные пути готовой редакции. Экспорт создаётся в private temporary directory, проверяется по source snapshot, затем публикуется под новым именем. Никакой authoritative «current» symlink или повторно используемый mutable каталог не нужен. Оборванный export не считается редакцией и пересоздаётся автоматически. Повторный export не создаёт нового result_hash и не сбрасывает QA/reviewer. Отсутствие export после успешного COMMIT означает «запись сохранена, представление надо восстановить», а не откат принятия.

Редактируемые агентами Markdown и выводы команд сначала находятся в private drafts/check captures. Domain recorder или небольшой `journal.py` с операциями publish/read/export принимает готовое содержимое и публикует bytes. Связанные документы и событие публикуются одной транзакцией. Непубликованные drafts никогда не участвуют в validator или приёмке. Произвольная прямая запись в старый flat path не становится журналом нового формата. Все инструкции прямого редактирования служебных run-файлов переводятся на этот порядок; пользователь в нём не участвует.

Логическая идентичность evidence отделена от физического пути экспортированной копии. Ссылка содержит прежний source-bound path, run identity и digest; resolver отображает её на bytes выбранного snapshot. `result_hash`, `task_scope`, `initial_snapshot` и handoff source fields нельзя автоматически заменять абсолютным адресом export или временного workspace. Физические пути чужого run и произвольные paths внутри `.journal/views` не принимаются как новое независимое доказательство.

Контекст чтения явно хранит `source_root` для происхождения, `artifact_root` для логических run references и `candidate_root` для product bytes этапа 2. `JournalSnapshot.read_bytes/exists/list_paths` работают с logical journal paths, `resolve_evidence` сохраняет source reference identity, `result_hash` читает product manifest запечатанного кандидата. Вложенность `.agent-work` больше не выбирает корень product bytes. Ни CLI-флаг с произвольным read root, ни новый путь export не разрешают заменить уже зарегистрированный candidate.

`require_own_reviewer_handoff` сначала сравнивает канонические логические `(run UUID, path)`. Две физические копии одного logical handoff в разных export-каталогах остаются одним handoff и отклоняются. При импорте файлов сохраняется проверка symlink/hardlink aliases; новый publish не принимает symlink как journal file. Исходное завершение сессии по-прежнему должно буквально назвать свой handoff и его digest. Проверки исходной роли, модели, root/author identity, completion и порядка QA/reviewer сохраняются. Исходные Codex sessions остаются read-only внешним источником и не входят в SQLite-транзакцию.

### Повтор и восстановление

У каждой логической команды есть machine-owned operation ID, сохранённый вызывающим инструментом до первого исполнения и повторно используемый после неизвестного исхода. Источником ID source-bound операций служат устойчивые run/thread/turn/stage данные; для остальных ID автоматически создаёт слой вызова и сохраняет private invocation envelope. Временной штамп и случайный новый ID при каждом retry не подходят. Пользователь этим не управляет. Один ID с другими входами отклоняется; тот же ID и входы возвращают receipt без новых событий и побочных записей. Это не очередь задач и не диспетчер исполнения.

При открытии SQLite сам восстанавливает незавершённую транзакцию. После kill до COMMIT читатель видит прежний целый run; после успешного COMMIT видит новый целый run. При kill после COMMIT, но до ответа повтор возвращает прежний receipt. Ошибка ввода-вывода или неясный исход COMMIT требуют нового соединения и проверки receipt перед решением о retry. Нельзя обещать, что любое исключение COMMIT означает rollback. SQLite corruption не разрешает собирать успешное состояние из exports или отбрасывать невалидную строку JSONL.

Повтор прежнего пригодного QA/reviewer сохраняет исходные bytes, source identity, время и текущую приёмку. Новое содержательное QA-заключение продолжает инвалидировать reviewer по действующему правилу. Проверки актуальности выполняются и на техническом повторе; receipt не заменяет подтверждение пригодности исходного completion.

### Диск и платформенная граница

`EXTRA` в DELETE mode синхронизирует каталог после удаления rollback journal. `FULL` в этом режиме не даёт одинаковой гарантии сохранности последнего commit на всех файловых системах; `fullfsync` запрашивает F_FULLFSYNC на macOS. [SQLite PRAGMA](https://www.sqlite.org/pragma.html#pragma_synchronous).

Создание самого run и `.journal` также требует синхронизации новых parent directories до успешной инициализации. Запрещено подменять подтверждённую сохранность простым `flush()` Python. Поддерживаемый профиль первой реализации: локальная файловая система macOS/Linux с рабочими file locking и sync primitives. Инициализация проверяет доступность sqlite3, запрошенные PRAGMA, запись/чтение, file sync и directory sync; для Darwin отдельно проверяет доступность F_FULLFSYNC на временном файле того же тома. Неподдерживаемая среда получает точную ошибку до обещания durable run.

Проверка PRAGMA не доказывает физическую запись в устройство. В Unix VFS SQLite есть fallback с F_FULLFSYNC на fsync и некоторые directory-sync ошибки игнорируются; это дополнительно требует проверки платформы и fault injection. [SQLite Unix VFS, full_fsync и unixSync](https://raw.githubusercontent.com/sqlite/sqlite/master/src/os_unix.c).

Обязательная гарантия после успешного ответа: операция опубликована целиком, прошла предусмотренную синхронизацию и не теряется при падении процесса. При отключении питания атомарность и сохранность опираются на соблюдение файловой системой, драйвером и устройством их sync-контракта. Нельзя обещать сохранность при лгущем контроллере, повреждении носителя или сломанной реализации блокировок. Эти физические пределы названы заранее; они не разрешают пропускать синхронизацию или тесты аварий процесса. [SQLite atomic commit, hardware assumptions](https://www.sqlite.org/atomiccommit.html).

### Старые run

Историческое чтение старого flat run остаётся диагностикой прежнего формата и явно не доказывает новую crash-safe гарантию. Новый run всегда создаётся транзакционно. При возобновлении прежнего run инструмент сначала автоматически захватывает его целый согласованный набор bytes в новую базу одной транзакцией и сохраняет исходную идентичность ссылок. При повреждении или изменениях во время захвата он останавливается с точной причиной; не обнуляет файлы и не просит пользователя исправлять JSON.

Первый COMMIT `run_state` обозначает завершение перехода. Неполная база без такой записи не переключает reader на новый формат; повтор инициализации завершает переход. Существующая опубликованная база с ошибкой не вызывает fallback к flat files. Старые файлы остаются исходным материалом перехода; после него текущие операции пользуются только базой. Во время перехода старые writers должны быть остановлены: они не знают новых SQLite locks. Перезапуск старого бинарника не входит в поддерживаемый write contract.

Перенос хранения, восстановление export и повтор регистрации не должны сами менять прежний result_hash и пригодный QA/reviewer. Добавление новой гарантии workspace имеет отдельный hash contract этапа 2 и не выдаётся за ретроспективную полноту старой задачи.

Проверки отсутствия изменений сравнивают опубликованные logical document bytes, события и приёмку; физический файл SQLite и восстанавливаемый export не обязаны быть побайтово прежними. На этапе 1 T16 проходит journal publish/read/export, сбой и повтор с сохранением приёмки. На этапе 2 T16 расширяется сквозной цепочкой prepare/publish/seal/приёмка/delivery; inventory и workspace-команды не являются условием завершения этапа 1. Формулировка «регрессии T01–T16 проходят» далее означает эти явно уточнённые ожидания нового storage, а не одновременное требование мигрировать и не мигрировать.

## Рабочая копия, полный состав и приёмка

### Исходное состояние

`task_workspace.py` отвечает только за source identity, копирование, полный обход, сравнение, запечатывание и поставку результата. Небольшой `task-workspace.py` предоставляет команды prepare, inspect/seal и delivery без пользовательского JSON. Имена нового модуля и команд предложены, а не объявлены уже существующими.

Для исходного Git repo получить `git rev-parse --show-toplevel`, `--absolute-git-dir` и `--git-common-dir`; поддержать обычный `.git` directory и linked worktree с `.git` file. Не выводить product root из расположения run или установленного пакета Agent Flow. Workspace принадлежит одному run; его ownership marker и расположение проверяются перед повторным использованием/очисткой. Автоматической очистки принятой поставки нет.

Создать отдельный локальный repo без общих writable objects и без новых commits, затем перенести реальное содержимое source worktree. Git metadata для истории получать локально без checkout filters/hooks и без обращения в сеть. Не использовать HEAD archive как полный baseline. Source HEAD/index/refs остаются неизменными. Исходные staged и unstaged состояния фиксируются как source metadata; baseline для сравнения результата содержит фактические bytes рабочего дерева. Точный staging layout исходника не требуется воспроизводить в index копии, но его нельзя стирать в источнике или приписывать текущей задаче.

Полный lstat/scandir обход включает tracked, untracked, ignored, скрытые файлы, удаления tracked относительно HEAD, тип файла и mode. Git используется как metadata, а не единственный перечень. Не пропускать node_modules, vendor и другие каталоги лишь из-за их имени или ignore-правила. Исключения задаются точными проверенными корнями: actual Git metadata, собственные run/workspace roots и canonical project runtime-metadata root, только если весь этот namespace прямо назначен служебным в принятой области исходного проекта. Для последнего инструмент сохраняет связь с выбранным source/Git root, no-follow identity каталога и immutable reference/digest такого назначения в записи exclusions workspace manifest. Одно имя .agent-work, ignore rule или наличие run внутри не подтверждает назначение всего каталога. Если существующий .agent-work другого source не имеет подтверждённого служебного назначения, он участвует в scan за вычетом точных собственных run/workspace subroots; неподдерживаемые объекты приводят к прежнему явному отказу. Произвольные excludes, glob-фильтры и подмена root не допускаются. Один и тот же объявленный набор исключений входит в baseline/candidate manifest и применяется при копировании, сравнении и seal. Запрещена рекурсия копии в собственную рабочую память.

SOURCE — единственный исходный репозиторий этой задачи, закреплённый в неизменяемом journal artifact `checks/plan-source-clarification.md` (SHA256 `4be7665b289b7c769764f41745c4b77cfb92ad221f6dca61dc3a10f497d1ec21`) и принятом metadata namespace proof. Это обозначение не разрешает произвольный будущий `--source` и не переносит назначение на другой репозиторий. Указанный SHA относится к историческому принятому уточнению; окончательные bytes этого плана получают собственный hash и финальную проверку QA/reviewer.

Для реализации этого плана исходный проект SOURCE использует точный SOURCE/.agent-work как project runtime-metadata namespace: общая рабочая память, текущие и исторические runs, сохранённые workspace/model-eval/comparison copies. После приёмки настоящего уточнения этот root целиком исключается из product scan с указанным назначением; его содержимое сохраняется в исходнике. Это назначение не распространяется на одноимённые каталоги других source roots. Исходный bootstrap manifest из 1993 entries описывает дерево за вычетом точных .git и .agent-work roots. Production prepare строит новый полный baseline в этой же области; два подтверждённых чужих additions дают 1995 entries, сохраняются в candidate и не относятся к изменениям impl-013. Initial snapshot и его исходные references не переписываются; перенос изменений задачи отдельно сверяется с сохранёнными initial bytes.

Файлы копируются byte-for-byte без hardlinks на источник; обычные symlinks сохраняются как links с исходным target text. Источник дважды сканируется вокруг копирования, а copy сверяется с baseline; изменение во время обхода вызывает повтор захвата либо техническую остановку до работы исполнителя. Это проверка стабильности наблюдаемого дерева, а не обещание атомарного снимка произвольных несотрудничающих процессов.

Копировщик и scanner работают от открытого descriptor исходного root, а не повторно разрешают абсолютные paths. Сам root открывается покомпонентно от доверенного parent с no-follow и сверкой заранее выбранной `(st_dev, st_ino)`; предварительный Path.resolve не заменяет эту проверку. Каждый descriptor-relative вызов принимает один basename без slash, абсолютного пути, `.` или `..`. На macOS/Linux каждый parent открывается по одному basename относительно parent descriptor с `O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC`; regular file — с `O_RDONLY|O_NOFOLLOW|O_NONBLOCK|O_CLOEXEC`. До первого чтения `fstat` подтверждает regular type и `(st_dev, st_ino)` из no-follow stat того же parent; bytes читаются и хешируются только через этот descriptor. После чтения сверяются identity, type, mode и наблюдаемая стабильность данных/записи. Замена или исчезновение записи прерывает захват. Один `O_NOFOLLOW` на полном pathname недостаточен: промежуточные компоненты тоже нельзя разыменовывать.

Открытый parent descriptor не перенаправляется при замене имени каталога на symlink. Symlink читается как target text через `readlink` относительно проверенного parent, не открывается как файл; его identity проверяется вокруг чтения. Создание destination идёт внутри owned root через проверенные directory descriptors, с exclusive/no-follow созданием файлов; замена destination parent не разрешает запись за его пределами. Этот порядок применяется в prepare, scanner, seal и формировании сохраняемой поставки. Проверка доступности нужных flags/dir_fd/scandir(fd) входит в платформенный preflight. Неподдерживаемая платформа получает отказ без небезопасного path-based fallback; Linux-only openat2 не является зависимостью решения.

Двойной scan остаётся проверкой стабильности дерева, но не заменяет защиту открытия. Отрицательный fixture синхронизированно подменяет regular file или parent directory внешней ссылкой между stat/open/read и затем восстанавливает имя. Ни одного внешнего marker byte не должно оказаться даже во временной копии до cleanup; source и внешний файл не меняются. Проверяется также подмена destination parent: за пределами owned destination ничего не создаётся. Prepare/seal не получают success при обнаруженной подмене. Дополнительные варианты: иной regular inode между stat/open отклоняется до read; FIFO не блокирует процесс и не читается; подмена уже открытого parent не перенаправляет его descriptor даже при восстановлении имени до последнего scan. Тестовая instrumentation проверяет identities всех читаемых FD, staging buffers/files, DB evidence и export до cleanup. Небезопасный контрольный lstat/open вариант должен захватить marker и провалить тот же тест. Каждый сценарий запускается для prepare и seal с детерминированными барьерами, а не случайным sleep.

Работа всех авторов задачи направляется в эту копию. Исходный root передаётся только как read-only reference. Одной instruction недостаточно считать hostile sandbox доказанным; обычная изоляция здесь означает отсутствие общих writable product files и направленные в копию операции. Изменения, которые пользователь или другой процесс позже внесёт в source, сохраняются: поставка их не перезаписывает и не откатывает.

### Краевые типы и полнота

| Случай | Обязательное поведение первой реализации |
| --- | --- |
| Regular file, новое имя, удаление, rename | В inventory отражаются old/new type, mode, digest или отсутствие. Rename допустимо представить удалением и созданием. |
| Игнорируемый файл | Участвует в копировании и сравнении. Автоматическая полнота не зависит от `--exclude-standard`. |
| Symlink | Хешировать target text и тип, не bytes цели. Directory symlink не обходить. Относительные ссылки, остающиеся внутри копии, поддерживаются, включая dangling targets. Ссылка, которая выходит из копии, останавливает prepare/seal с путём: её нельзя разыменовать в source или молча превратить в обычный файл. |
| Submodule или nested repository | До prepare success явно обнаружить. Минимальная первая реализация останавливается с именем неподдерживаемого вложенного repo, сохраняя исходник; одного gitlink для «полноты» недостаточно. Поддержка рекурсивной работы не предполагается молча. |
| Unreadable, исчезновение при чтении, special device/FIFO/socket | Inventory incomplete, prepare/seal не успешен. Не пропускать и не читать потенциально блокирующий special file. |
| Имена с пробелом, переводом строки, Unicode; case collision | Не разбивать Git paths по строкам; использовать NUL separators. Bytes имён сохранять обратимо. Коллизия или невозможность точного представления на целевом томе останавливает копирование с причиной. |
| Hardlink в источнике | Копия не разделяет inode с источником. Учёт результата идёт по путям; топологию hardlinks не обещать сохранять незаметно. |
| Mode/type-only изменение, empty directory | Inventory обнаруживает. Не ограничивать result_hash только read_bytes существующих regular files. |

Отказ на неподдерживаемом объекте означает отсутствие гарантированно полной рабочей копии, а не успешный run с пропущенными файлами. Он не требует обслуживания JSON пользователем. Эти случаи входят в отрицательные критерии приёмки. Поддержка выполнения внутри такого repo требует отдельного расширения типов до реализации.

Полнота означает итоговую разницу между baseline и проверяемым кандидатом. Временный файл, созданный и удалённый до seal без следа в результате, не требует истории всех системных вызовов. Автоматический инвентарь нельзя фильтровать декларациями worker, `result_files` или allowlist. Обнаруженный путь вне согласованной области остаётся видимым и требует обычного решения по границам задачи; его нельзя скрыть из accepted result.

### Seal и delivery

Перед QA инструмент дожидается завершения авторских записей, повторно сканирует всю копию, вычисляет разницу с baseline и создаёт отдельный immutable candidate с полным деревом для чтения и запусков. Используется новая owned directory без hardlinks к mutable workspace; частичная копия не получает статус sealed. Проверка source/candidate manifests до и после копирования обнаруживает гонку. Baseline bytes сохраняются, чтобы исходные dirty-фрагменты можно было отличить от изменений задачи.

До COMMIT ссылки на sealed candidate синхронизируются его файлы, manifest и parent directories по поддерживаемому профилю платформы. Запись о seal публикуется только после успешной сверки и синхронизации. Kill до COMMIT оставляет максимум неиспользованный owned candidate, который инструмент распознаёт по manifest; kill после COMMIT не оставляет журнал со ссылкой на недостроенную копию. Не удалять candidate только потому, что ответ вызывающей команде не успел вернуться.

Два набора обязательны: полный candidate manifest и delta от baseline. Manifest содержит path, type, mode, digest/target и явно описанные внутренние исключения. Delta автоматически формирует `run_changed_files`, `result_files`, соответствующую boundary evidence и Worktree Hygiene. Декларации помогают связать автора и границы, но не определяют полноту и не убирают найденные пути. Нельзя приписывать каждому worker весь общий diff как независимое доказательство его личных изменений; при нескольких авторах нужен checkpoint baseline его назначения или честный общий run-level inventory.

Принятый result_hash нового workspace формата включает hash-version, workspace identity, baseline manifest digest, полный candidate manifest digest, delta и прежние обязательные source/scope references. Отличаются regular bytes, link target, тип, mode и deletion. Включение полного manifest не даёт незаметно заменить неизменённый dependency file, от которого зависели тесты. Старый формат hash сохраняет прежнюю формулу только для исторической приёмки; его нельзя использовать для нового positive workspace result.

Планы и связанные документы входят в снимок до QA окончательными bytes со статусами. Документы за пределами product tree, уже используемые как task_scope/initial_snapshot, импортируются как immutable evidence без переписывания исходного адреса. Приёмка не хеширует свой собственный receipt или final export: сначала candidate и source evidence, затем result_hash, QA, reviewer, технический final. Исправление принятого плана или candidate создаёт новую редакцию результата и требует актуальной приёмки; восстановление представления журнала этого не делает.

QA/reviewer получают одинаковый candidate identity. Тесты, которым нужна запись, запускаются на временной копии sealed candidate; выходы тестов регистрируются в журнале. Они не изменяют принятые product bytes. Перед final проверяется соответствие сохраняемой поставки candidate manifest. Настройки chmod помогают избежать случайного редактирования, но не защищают от владельца файловой системы; финальная hash-сверка обязательна.

Поставка содержит точный путь сохранённой принятой копии, baseline/delta evidence и человекочитаемый перечень изменений. При необходимости инструмент генерирует обычный diff для просмотра; manifest и bytes candidate остаются полным источником для binary/symlink/delete случаев, которые текстовый patch выражает не полностью. Пользователь может открыть результат без служебных операций. Исходник, index, refs, commits и посторонние изменения не меняются. Применение назад не добавляется как скрытое условие завершения.

## Этапы и условия приёмки

### Этап 1. Весь опубликованный журнал хранится и читается согласованно

Зависимости и порядок: принять baseline текущего кода и уже выполненной унификации; сначала закрепить последовательную частичную запись, потерю конкурентного обновления и смешанное чтение воспроизводимыми регрессиями, затем реализовать storage и подключить всех потребителей одной поставкой. Протокол рабочего пространства этапа 2 пока не нужен. Контракты этапа: JournalSnapshot, транзакционная запись, operation receipt, logical evidence identity, импорт и экспорт. Один ответственный исполнитель владеет всеми общими файлами из таблицы модулей.


Самостоятельный результат: любой существующий journal consumer видит одну целую транзакцию, а технический сбой или повтор не повреждает пригодное принятие. Область включает storage, init/reuse, полный переход consumers, публикацию evidence, immutable export и инструкции. Проверки входят в этап.

| ID | Поверхность и проверка | Критерий |
| --- | --- | --- |
| JD-01 | storage, positive/negative | Kill до/после каждой связанной записи и во время больших транзакций: после нового открытия все документы принадлежат прежней или новой целой редакции, никогда смеси. |
| JD-02 | CLI/storage, positive/negative | Одновременные append, handoff, trace и final: события не теряются, операция не появляется после final, timestamps корректны. Занятая база не вызывает partial write. |
| JD-03 | reader/CLI, positive/negative | Writer меняет все взаимосвязанные документы между чтениями validator и harness promotion. Один вызов читает только одну редакцию; отдельный новый вызов видит новую. |
| JD-04 | CLI/storage, positive/negative | Kill после COMMIT до ответа и повтор операции; тот же QA/reviewer; другой payload под тем же ID. Первый повтор сохраняет bytes/принятие, конфликт ID отклоняется. |
| JD-05 | storage/export, positive/negative | Disk full, permission/I/O/sync failure, оборванный export: нет ложного durable success; опубликованная DB восстанавливается независимо от представления. |
| JD-06 | parser/CLI, positive/negative | Old run import/reuse, kill во время перехода, malformed old data: отсутствует смешение двух форматов и выдуманная полнота. |
| JD-07 | source/evidence, positive/negative | Копии одного logical QA handoff под разными export paths, подмена root/absolute scope path, raw-source mismatch отклоняются; нормальный технический перенос сохраняет прежнюю пригодную приёмку. |

Для fault injection использовать subprocess/SQLite hooks внутри тестов и отдельное контролируемое заполнение тестового тома либо SQLite page limit; не заполнять пользовательский диск. Ошибки fsync проверять на границе вызова и, где доступно, через test VFS/syscall trace. SQLite upstream crash guarantees не заменяют тесты собственного группирования документов и CLI.

Фокус Devil’s Advocate: скрытые flat readers, mutable external handoffs, stale read-modify-write, ложная трактовка commit error, export как второй источник истины, обход own-handoff identity. Этап завершён только после полного подключения consumers и соответствующих отрицательных сценариев.

### Этап 2. Полный автоматический состав и сохранённая принятая копия

Зависимости и порядок: этап 1 принят; сверить фактический статус impl-012 и общий hash API. Сначала закрепить регрессиями пропуск ignored/необъявленных файлов и mode-only изменений, затем реализовать prepare, полный baseline, seal и всю цепочку приёмки/поставки. Контракты этапа: task_workspace, отдельные product/evidence roots, versioned result_hash и автоматический inventory. Область — строка «Рабочая копия» таблицы модулей и связанные recorder/validator/инструкции; владелец общих файлов один.


Зависит от согласованного журнала: baseline, candidate, source evidence и принятие должны публиковаться без разрыва. Область включает prepare, scanner, seal, hash contract, recorder/boundary/final и delivery. Это один этап: scanner без принудительного использования его результата при приёмке оставил бы прежний обход через декларации.

| ID | Поверхность и проверка | Критерий |
| --- | --- | --- |
| WC-01 | filesystem/CLI, positive/negative | Обычный repo и `.git` file worktree с staged, unstaged, untracked, ignored: baseline/copy совпадают, source bytes/index/refs не меняются; изменения источника во время prepare обнаруживаются. File/parent swap между stat и open не читает external marker bytes и не получает prepare/seal success. |
| WC-02 | inventory/CLI, positive/negative | Создать, изменить, удалить tracked/untracked/ignored и mode/type, не объявив их нигде: все итоговые изменения присутствуют в machine inventory и final. Исходный dirty diff отдельно не приписан задаче. Exact metadata exclusions не скрывают product paths: обычный .agent-work без подтверждённого namespace назначения и одноимённый вложенный каталог включаются в inventory; произвольное исключение и root/identity spoof отклоняются. Production baseline и candidate сохраняют оба чужих impl-014 additions без task attribution; первоначальные 1993 entries и связь task delta с ними проверены отдельно. |

| WC-04 | acceptance/evidence, positive/negative | Исключить файл из деклараций; изменить sealed bytes, mode, link, scope или финальный статус плана: positive acceptance невозможна со старым hash. |

Фокус Devil’s Advocate: implicit ignore exclusions, source hardlinks/symlinks, автоматическое принятие полноты без всех paths, подмена root расположением run, accepted-plan bytes после проверки, mutable copy вместо sealed delivery, автоматическое применение назад.

Этапы нельзя безопасно слить в одну непроверяемую поставку: первый меняет источник истины всех journal consumers и процедуру восстановления. Второй опирается на него и меняет определение проверяемого product result. Их независимые failure modes позволяют сначала доказать отсутствие mixed journal, затем доказать отсутствие пропусков inventory. Дополнительный отдельный этап тестов или этап автоматического merge не нужен.

## Сквозная проверка, соседний план и ограничения решения

Запустить профильные тесты, полный пакетный `check-all.py`, корневую оболочку `scripts/check-all.py`, compact/full/auto, init/reuse, обычные и архитектурные fixtures. Реальный CLI проходит prepare, изменение в копии, capture/publish, seal, QA, reviewer, render-final, validate-run и открытие доставленного candidate. Проверить сохранность предсуществующих product bytes и отсутствие commits. Linux/macOS подтверждаются отдельными запусками; mock Darwin на Linux не подтверждает F_FULLFSYNC. SIGKILL доказывает процессный сбой, а не физическое отключение питания.

План `impl-012-requirement-result-evidence.md` подготовлен, но не реализован. Он меняет `verification_evidence.py`, recorder, validator, acceptance hashing и инструкции. Рекомендуемый будущий порядок: этап 1 этого плана как storage foundation, затем последовательное согласование семантики impl-012 и этапа 2 на актуальном коде; параллельное редактирование общих contract-файлов исключить. Ни наличие, ни отсутствие реализации impl-012 не должно тайно внедрять его требования здесь. Если impl-012 выполнен раньше, новый reader хеширует уже принятый acceptance/source contract из того же pinned snapshot. При другой последовательности impl-012 использует новый result payload и не возвращает live reads. Формула расширяется один раз на общей актуальной базе, с явной версией; source/acceptance references не теряются и цикл hash не создаётся.

Отвергнутые альтернативы: fsync каждого старого файла не даёт общей транзакции; lock только вокруг write пропускает stale reads; immutable directories с единственным указателем требуют собственного commit/recovery/GC/fsync protocol; JSON views как authoritative fallback создают второй источник истины; WAL добавляет checkpoint/sidecar lifecycle без необходимости короткого журнала; git diff/HEAD archive/model-eval как готовое решение не покрывают требуемый dirty/ignored baseline.

Риски с заранее определённым последствием: SQLite missing или неподдерживаемая локальная FS останавливают инициализацию; special/escaping/nested/unreadable source останавливает prepare/seal с путём; большой ignored tree увеличивает копирование и место, но не даёт права молча исключить его. При нехватке места кандидат не принимается. Политика объёма не расширяется до автоматического удаления данных пользователя или фоновой оптимизации хранилища.

Архитектурное основание: architect одобрил указанные контракты в handoff этого запуска. Stop conditions будущей реализации: невозможно подключить reader к одному snapshot; предложен dual-write/fallback; требуется source mutation или новый commit; предлагается объявить неполный inventory полным; доставка требует неподтверждённой физической гарантии. Такой drift возвращается архитектору до worker continuation. Не требуется запускать новый архитектурный режим ради этого исследовательского документа.

## Завершение этапов и всего плана

Этап 1 завершён, когда JD-01–JD-07 и регрессии T01–T16 с уточнённым выше storage-контрактом проходят, все объявленные consumers используют один snapshot, а настоящие QA/reviewer принимают текущую реализацию после full check-all и git diff --check. Неподключённый consumer или невоспроизводимый отрицательный сценарий оставляет этап in_progress. Этот этап отдельно доказывает миграцию хранения; его нельзя безопасно слить с изменением состава product result этапа 2.

Этап 2 завершён, когда WC-01–WC-07 и предыдущие проверки зелёные, полный сквозной CLI выполнен на обычном repo и linked worktree, а принятая копия открывается и совпадает с manifest. Две одновременные задачи от одного source должны иметь независимые workspace/candidate и не стирать исходные/чужие bytes. Скрытое изменение после QA получает новый hash и не проходит со старым принятием. Этот этап зависит от доказанного транзакционного storage и отдельно проверяет полноту результата.

В каждой таблице positive/negative означает два воспроизводимых сценария с конкретными exit status и проверкой состояния, а не один положительный тест с перечислением рисков. Для источников QA/reviewer используются fixtures в тестах и настоящие независимые завершения в live-сценарии; оригинальные сессии не редактируются. Профильные тесты подключаются к полному check-all. Linux и macOS проверяются в реальных доступных окружениях; если второго нет, соответствующий профиль не объявляется проверенным или поддержанным без доказательства, а ограничение блокирует обещание его готовности.

В финальном live-сценарии исправленный путь выполняет операцию, переживает контролируемый сбой экспорта/ответа, повторно регистрирует то же пригодное QA/reviewer и сохраняет их принятие без нового вызова модели. Затем свежий validate-run проверяет текущий журнал без ослабляющих флагов. Проверки исходных ролей, моделей, source turn, root/author identity, SHA и порядка приёмки остаются обязательными.

Перед приёмкой реализации обновить этот план и связанные поставляемые документы до окончательных статусов; их bytes входят в candidate до QA/reviewer. После принятия менять их нельзя без актуальной повторной проверки. Проектная задача закрывается после свежей финальной валидации; Implementation status меняется на done только после обоих этапов. Итог сообщает путь принятой копии, перечень изменений, результаты проверок и точные платформенные пределы. Автоматического удаления поставки или применения в исходник нет.
