# Implementation Plan 016: Сборка актуального контекста

Document status: done
Implementation status: done
Дата: 2026-10-01.
Дата обновления: 2026-10-02.

Основание: [PRD-001](../prd/prd-001-document-context.md) и
[ADR-002](../adr/adr-002-document-context.md) и решение пользователя от 2026-10-02
перенести готовую процедуру в основной Agent Flow, а общую инфраструктуру
проверять отдельно. ADR сохраняет статус Proposed. Повторное согласование
требований и общая формальная приёмка не входят в текущую интеграцию.

## 1. Цель и границы

Процедура реализована и интегрирована в основной Agent Flow. Восемь готовых
файлов инструкций перенесены из проверявшегося кандидата без изменения их
содержимого. PRD, ADR и этот план отражают текущий объём задачи.

Решение пользователя от 2026-10-02 заменяет прежние условия завершения этого
плана: общие инфраструктурные проверки выполняются отдельно и не блокируют
перенос. В текущую задачу не входят `check-all.py`, браузерные и CLI-пилоты,
проверка `strict_inputs` и повторная формальная приёмка старого запуска.
Тесты и общие правила Agent Flow сохраняются.

Это решение не означает успешного прохождения прежних проверок.
Фактическое чтение чата по явно указанной пользователем ссылке в C08 остаётся
непроверенным; прохождение `strict_inputs` и `check-all.py` не подтверждено.
Исторические результаты и причины остановки сохранены без изменений в локальном
run `2026-10-01-impl-016-context-execution`. Следующий шаг — проверка пользователем
на реальном кейсе; она ещё не выполнена.

Встроить процедуру сборки контекста в действующие инструкции Agent Flow.
Агент должен начать с источников конкретной задачи, собрать достаточные сведения,
сохранить принятые решения и пересобрать контекст при изменении запроса.
Результат текущей задачи: интегрированные инструкции и актуальные статусы
документов. Требования C01–C22, включая уточнения ADR о записи решений и границах
`context.md`, сохраняются; перенос не выдаётся за полную поведенческую приёмку.

Работа касается Markdown-инструкций, делегирования и подготовки документов.
Используются существующие поиск и чтение файлов, Git и Python-команды журнала.
Схемы данных, алгоритмы журнала, модели ролей, зависимости и инфраструктура
не меняются. UI, API и миграций в этой задаче нет.

Границы первой версии заданы PRD §8 и ADR §5. Программный сборщик, индекс,
реестр решений, фоновое наблюдение и массовое обновление старых документов
не добавляются. Риск неизвестной замены документа принят: отдельного поиска
таких замен нет. Известные замены и обнаруженные противоречия учитываются.

Подготовка этого плана не запускает реализацию, установку обновлённого пакета
или коммит. Выбор состава документов для пользовательских задач сохраняется.

Точки запуска, сохранение решений и передача контекста составляют единый порядок
работы. Отдельной миграции или промежуточного контракта нет. Для текущей интеграции

Автор переносит файлы, проверяет точность переноса, ссылки и границы diff.
Общая цепочка QA и reviewer не запускается повторно в этой задаче по решению
пользователя от 2026-10-02.

### Порядок работы

Пункты 1–4 описывают реализованную процедуру. В текущей задаче соответствующие
инструкции переносятся из готового кандидата без повторной реализации.

1. В `project-memory-and-env.md` описать основной порядок по ADR §§2.1–2.3:
   запрос и обязательные источники → чтение недостающего → проверка достаточности
   → действие. При неизменном запросе использовать проверенные неизменные сведения;
   при смене запроса собирать пакет заново. До большого PRD оценить продуктовый
   объём и предложить декомпозицию, если он объединяет самостоятельные задачи.
2. Добавить сохранение по ADR §2.4. Основной агент отвечает за немедленную запись
   и её проверку. Существующий подходящий документ обновляется, даже если правка
   не была запланирована. Пока документа нет, используется локальная запись задачи.
   При появлении документа решение переносится с проверкой фактической записи.
3. Определить обновление пакета по ADR §2.5: прочитать `context.md` через журнал,
   заменить только раздел `Рабочий пакет`, опубликовать документ. Остальные разделы,
   включая `Initial Worktree Snapshot`, сохранить. Изменение принятых доказательств
   проходит существующую повторную приёмку. В задаче без журнала новый run только
   ради сборки контекста не создаётся.
4. Связать с процедурой остальные файлы таблицы. В задании субагента указать его
   часть и обязательные источники; в результате требовать использованные источники
   и существенные пробелы. Основной агент собирает общий контекст из проектных
   документов любого авторства и необходимых отчётов. При смене запроса обновить
   зависимые задания до продолжения их выполнения.
5. Сохранить исходные целевые файлы и перечень отсутствующих, перенести восемь
   инструкций без изменений, обновить статусы PRD, ADR и этого плана. Проверить
   точность переноса, относительные ссылки, diff и сохранность служебных разделов.
   Общие проверки ниже не запускать в рамках текущей интеграции.

### Проверки и критерии приёмки

Для текущей интеграции проверить точность переноса восьми инструкций, ссылки и diff
всех изменённых файлов, сохранность ограничений ADR и служебных разделов.
Проверка текста подтверждает согласованность инструкций; выполнение C01–C22
подтверждается живыми действиями.

Описанная далее программа общих и поведенческих проверок сохранена для отдельной
работы. По решению пользователя от 2026-10-02 она не является условием завершения
текущей интеграции и не запускается в этой задаче. Следующий практический шаг —
реальный кейс пользователя; его результат пока неизвестен.

Команды существующей проверки пакета выполняются из корня исходного Git-проекта
в штатной среде проверки. Пишущие проверки запускаются на расходной копии:

```bash
git diff --check
python3 scripts/check-all.py
```

Если штатная среда недоступна, сохранить конкретную ошибку и оставить эту проверку
невыполненной. Устанавливать зависимости или менять глобальные роли ради плановой
проверки без разрешённой настройки не требуется. Успешный `check-all.py` не заменяет
поведенческую проверку.

Для живых проверок использовать изолированные копии небольшого проекта с файлами
требований и затронутой реализации. Примеры ниже задают проверочные входы, а не
функции сборщика. До запуска QA сохраняет точные входные файлы и сообщения,
ожидаемый результат и разрешённые источники. Ожидания не передаются исполнителю
вместо обычного пользовательского задания.

Три задания сохранённой программы поведенческой проверки:

1. **Первое использование.** Проект каталога вложений содержит README, собственный
   план добавления поиска и исходный код; памяти Agent Flow нет. Запрос:
   «Agent Flow, подготовь изменения поиска по приложенному плану». В проекте также
   есть не относящийся к поиску документ об уведомлениях. Проверить чтение нужных
   источников, остановку при достаточности и отсутствие навязанного PRD/ADR.
2. **Следующая задача.** В той же локальной копии передать задачу по другой части
   каталога. До запуска изменить относящийся к ней документ без коммита и дать
   документ с явной заменой прежнего решения. Проверить учёт рабочей редакции,
   известных замен и отсутствие переноса лишних сведений из первой задачи.
   Не прятать заменяющий документ: поиск неизвестных замен не является критерием.
3. **Подготовка документа.** Попросить содержательно пересмотреть PRD хранения
   вложений и явно заменить локальное хранение облачным. Проверить немедленную
   запись в существующий PRD, удаление отменённых требований, пересборку пакета
   и актуальное задание исполнителю. Затем проверить продолжение с чистым
   контекстом: решения должны восстанавливаться из файлов, а не прежнего диалога.

Для независимых ветвей сценария использовать отдельную исходную копию.

«контекст проверен» недостаточно. Для случаев с продолжением предыдущий диалог
не передаётся; используются отдельные тестовые назначения с доступом к проектным
документам и разрешённой локальной памяти. Реальные пользовательские проекты
и чаты ради этих проверок не изменяются.

В C08 проверяется правило: агент читает другой чат только по ссылке, которую
пользователь явно указал как источник. Для проверки фактического чтения нужен
доступный чат, разрешённый пользователем для этого теста. При запросе ссылки
объяснить проверяемое правило и цель теста обычными словами; одного номера C08
недостаточно. Искусственный URL и ответ заглушки не доказывают фактическое чтение.

Если ссылки для теста нет или чат недоступен, реализация и остальные проверки
продолжаются, включая проверку запрета читать чат по ссылке, найденной в файле.
Проверка чтения по явно указанной пользователем ссылке остаётся невыполненной.
Полная приёмка C08 подтверждается только после выполнения обеих проверок.

По тем же заданиям до и после изменения инструкций записать число прочитанных
источников, повторных чтений и уточнений. Размеры возвращённых фрагментов учитывать,
если они доступны в инструментах. Фиксировать различия входов и недоступные данные;
числового порога экономии нет. Сокращение чтения при потере требования — отказ проверки.

### Риски и фокус Devil's Advocate

Главный риск — расхождение коротких правил в точках запуска с подробной процедурой.
Reviewer сверяет все файлы таблицы, особенно разрешение на чтение чатов.
Второй риск — пакет выглядит верным, но агент продолжает действовать по старому
решению. Поэтому QA проверяет последующие действия, документы и задания исполнителей.

Devil's Advocate отдельно проверяет, не вернулись ли отклонённые требования:
поиск неизвестных замен, архив отменённых решений, обязательный ADR для каждой
части, новый программный механизм или отдельное согласование пакета. Проверяет
ответственность за запись решения и сохранность служебных разделов `context.md`.

Текущая интеграция завершается при выполнении следующих условий:

проверка пользователем на реальном кейсе. C08, `strict_inputs` и `check-all.py`

Завершённая интеграция не означает полной поведенческой приёмки или обновления
уже загруженных ролей. Глобальные настройки и сгенерированные роли не меняются.
