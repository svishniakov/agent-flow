# Профиль Astra-Sol и его проверка

Текущий профиль задан в [impl-007](implementation/impl-007-astra-sol-rollout.md).
Он назначает `gpt-6-astra` 26 ролям, а роли `reviewer`, включая назначение
`reviewer.qa`, - `gpt-5.6-sol`. Главный агент запускается отдельно на Astra `high`
с пределом `xhigh`; файл `orchestrator.md` относится к его помощнику.
Reasoning, глубина рассуждения модели, повышается по обоснованной причине в пределах
роли. Этот профиль отличается от фиксированных настроек исторических A/B/C.

| Роли | Исходный reasoning | По обоснованному trigger |
| --- | --- | --- |
| Architect, Reviewer, Product Manager, Marketing Growth Strategist, RAG Retrieval Engineer, Design Orchestrator, UI/UX Design Director, Documenter, QA Verifier, Senior QA, Visual QA | `high` | `xhigh` |
| Supervising Architect | `xhigh` | `xhigh`, предел уже достигнут |
| Остальные 15 ролей, включая исполнителей кода и помощника Orchestrator | `medium` | `high` |

Ревью плана обычно начинается на Sol `high`. Финальный независимый `reviewer.qa`
получает отдельное назначение на Sol `xhigh` через существующий trigger `qa-critical`.
Trigger обозначает предусмотренную для роли причину повышения. Главный агент может
перейти с `high` на `xhigh`, когда сложность координации или архитектурного решения
подтверждена после проверки требований, контекста и инструментов.

## Повышение и продолжение работы

Сначала нужно установить причину затруднения: недостающее требование, потерянный
контекст, инструмент, ошибка реализации, тест или план. Пересмотр архитектуры нужен
по результату этой проверки. Обычная исправимая ошибка теста не запускает всю цепочку
восстановления Blocked Recovery Path.

До повышения оркестратор записывает предусмотренный trigger, причину и
подтверждающий факт, прежний и выбранный уровни, связь с сессией и счётчик попыток.
Штатное повышение в рамках утверждённого профиля не требует повторного разрешения
пользователя. Точный ID модели, service tier (режим обслуживания), `assignment_id`
(идентификатор назначения), цель, границы правок, контекст и число попыток сохраняются.
Повторный trigger не даёт ещё одного уровня или попытки. Автоматический переход
на `low` или `max`, подмена модели и изменение service tier запрещены.

После повышения все обращения продолжаются на достигнутом уровне. Resolver
выбирает конфигурацию без хранения истории; действующее состояние назначения
сохраняет оркестратор. Вызов resolver без trigger не разрешает вернуться к базе.
Отдельное новое назначение начинается по своей конфигурации; переименование
прежнего не обнуляет попытки. Blocked Recovery Path сохраняет прежний порядок:
после первой блокировки попытки разрешения подключаются Senior QA и архитектор,
после второй - Supervising Architect, после третьей работа завершается с `blocked`
или `fail`.

До зависимого выполнения нужно подтвердить, что среда применила выбранные
настройки. Если они закреплены за сессией, допустимо поддерживаемое средой явное
продолжение в новой сессии той же модели. Прежнее исполнение останавливается;
сохраняются `assignment_id`, оба ID сессий, полный рабочий контекст, владелец правок
и счётчик попыток. Настройки новой сессии тоже требуют подтверждения.
Незаметное изменение через close/resume не считается разрешённым повышением:
поведение этого пути нужно отдельно проверить в текущей версии среды.
Если механизм или его применение подтвердить нельзя, зависимая работа блокируется
с точной причиной; независимую работу можно продолжать.

При каждой передаче сохраняются исходная цель и условия приёмки, принятые и
отменённые решения, неизвестное, выполненные правки, результаты проверок,
запрещённые повторы, границы работы и доступные ссылки на доказательства.
Агент не может заменить требование пользователя собственной правкой спецификации.
Согласованность новых документов и тестов сама по себе не доказывает выполнение
исходного требования.

## Инструкции и запуск

Общие инструкции находятся в `references/astra-instructions.md`. Их текст,
включая исторический заголовок Astra, сохранён для обеих моделей: это правила
работы Agent Flow, а модель задаёт конфигурация роли. Генератор Codex добавляет
их к профессиональному контракту роли. Resolver с флагом
`--include-instructions` возвращает тот же текст для запуска с явными параметрами.

```bash
python3 scripts/validate-agent-config.py
python3 scripts/resolve-agent-config.py --role python-worker --trigger public-contract --include-instructions
python3 scripts/resolve-agent-config.py --role reviewer --trigger qa-critical --include-instructions
python3 scripts/sync-codex-agent-config.py --output-dir <test-project>/.codex/agents
python3 scripts/sync-codex-agent-config.py --output-dir <test-project>/.codex/agents --check
```

Использовать свежую сессию Codex с входом через ChatGPT и установленным в тестовом
окружении экземпляром этой ветки. Не полагаться на ранее загруженные глобальные
роли. Файл custom agent может перекрыть аргументы запуска. Если именованная роль
закрепляет другой reasoning, использовать поддерживаемый запуск `default` с
явными настройками, полными инструкциями роли и ограниченным контекстом согласно
`references/delegation.md`. Если такой запуск недоступен, зафиксировать блокировку.

Успех синхронизации доказывает содержимое конфигурации. Фактическое применение
модели и reasoning проверяется отдельно по данным среды исполнения. Самоотчёт
модели доказательством не является; обнаруженное перенаправление делает прогон
непригодным для сравнения заданных конфигураций.

## Исторический протокол сравнения с Astra-only

Ниже сохранён первоначальный протокол парного сравнения. Он относится к прежним
фиксированным настройкам и не задаёт правила текущего профиля. Исторические A/B/C
и их журналы не переписываются. Перенос остальных ролей и польза повышения reasoning
не доказаны тем сравнением; нынешние проверки переходов описаны в этапе 2 impl-007.
Этот раздел не поручает повторно запускать сравнение.

Задача: реализация плана `prd-flow-v2-runtime-interview-fix-implementation-plan.md`
из проекта PRD Flow. Зафиксировать текущие файлы вместе с уже сделанными локальными
исправлениями. Второй прогон начинается с того же снимка, без результатов первого.
Использовать одинаковые версии инструментов, зависимости, критерии и ограничения.

Сначала выполнить Astra-only. В варианте Astra-Sol менять модель роли `reviewer`,
включая её работу как `reviewer.qa`, на Sol при сохранении reasoning. Остальные роли,
порядок проверок и задание сохраняются. Не добавлять второго проверяющего только
одному варианту: иначе сравнение смешает эффект модели с эффектом ещё одного ревью.

Оценивать выполненные требования R1-R4 и D1-D5, подтверждённые дефекты, ложные
замечания, лишние изменения, число исправлений, время и доступные показатели
подписочного расхода. Одна парная задача даёт наблюдение, а не универсальный рейтинг.

Публикация корпоративного шаблона и ручная приёмка новой сессии остаются отдельными
условиями исходного плана. Локальный тест не выдаётся за их выполнение. Не менять
корпоративные источники ради сравнения и не возобновлять старую тестовую сессию.

## Локальные проверки конфигурации

```bash
python3 scripts/test-agent-config.py
python3 scripts/test-sync-codex-agent-config.py
python3 scripts/test-validate-agent-config.py
python3 scripts/test-validate-role-catalog.py
python3 scripts/check-all.py
```

Локальные проверки должны отклонять смену точной модели и service tier, понижение
и превышение предела; выбирать Sol `high` для reviewer и Sol `xhigh` по `qa-critical`;
не отмечать достигнутый предел как новое повышение; сверять resolver с генератором
и матрицей всех 27 ролей. Чтение итогового diff и поиск старых правил проверяют
согласованность инструкций.

Эти проверки не подтверждают запуск или изменение реальной сессии. Пять сочетаний
Astra `medium`, `high`, `xhigh` и Sol `high`, `xhigh`, переходы обеих моделей и
родителя, сохранение повышенного уровня при продолжении и короткий прогон семи
назначений требуют отдельных свидетельств среды по этапу 2 impl-007. Пока таких
свидетельств нет, соответствующие условия остаются непроверенными. Исторические
данные model-eval сохраняются; прежний синтетический benchmark не запускается.
