## 1. Краткое описание

Agent Flow собирает актуальный контекст при первом использовании в существующем проекте и в начале каждой новой задачи. Перед созданием или содержательным изменением PRD, ADR и Implementation Plan он проверяет собранные сведения и добавляет необходимое для документа. Явное изменение запроса требует пересобрать контекст под новый запрос.

Первая версия сборщика — процедура внутри Agent Flow, использующая существующие инструменты поиска и чтения. Отдельное программное решение рассматривается, если проверка покажет, что процедура не справляется.

PRD описывает продуктовые требования, ADR фиксирует архитектурное решение, Implementation Plan задаёт план реализации. Сборщик работает внутри явно запущенного Agent Flow. Первичный сбор обязателен и для задачи с готовым планом. Постоянный фоновый пересбор во время реализации в этот этап не входит.

## 2. Участники

| Участник | Ответственность |
| --- | --- |
| Пользователь | Принимает продуктовые и архитектурные решения, разрешает противоречия, которые нельзя снять по источникам |
| Основной агент | Собирает общий контекст из проектных документов независимо от их авторства и необходимых отчётов субагентов, проверяет актуальность решений и достаточность контекста |
| Субагенты | По необходимости готовят проектные документы и отчёты исследований; получают сведения и источники своей части, читают обязательные документы и добирают только недостающее для задания |

Основой общего контекста могут быть как PRD, ADR и Implementation Plan, так и отчёты исследований субагентов. Выпуск новых документов или повторное исследование перед каждой задачей не требуются, если имеющихся актуальных источников достаточно.

## 3. Проблема

По мере развития продукта решения меняются. Агент находит старую запись и воспринимает её как действующее ограничение, хотя пользователь уже явно выбрал новый подход. Работа останавливается на повторном согласовании принятого решения.

При первом подключении Agent Flow проект может иметь собственные планы, критерии готовности и процессы. Отсутствие памяти Agent Flow не означает, что контекста нет. Нужно изучить существующие источники в пределах запроса, затем проверять и дополнять сведения для следующих задач.

## 4. Цель и оценка результата

Агент получает действующие решения, ограничения и критерии своей задачи, сведения о текущей реализации и необходимые источники. Пользователь не подтверждает повторно явно принятую смену подхода.

Результат проверяется на сценариях раздела 7.6:

- Заменённые решения не используются как действующие требования. Одно лишь расхождение с историей не останавливает работу.
- Каждое утверждение о принятом решении связано с источником; предложение агента не выдаётся за решение пользователя.
- Неразрешённое противоречие вызывает точечный вопрос, независимая работа продолжается.
- Первый запуск использует существующие документы и реализацию без предварительного перевода проекта на форматы Agent Flow.
- Каждая задача получает актуальный контекст. Изменение запроса приводит к пересборке, без смешения прежних и новых требований.
- Сбор ограничен запросом и прекращается, когда сведений достаточно для следующего действия. Другие чаты читаются только по ссылкам, которые пользователь сам явно указал как источники контекста.

Дополнительно сравниваются объём повторного чтения и число уточнений с прежним процессом. Числовая цель экономии определяется после замера; сокращение объёма не оправдывает потерю требований. Приёмка проверяет действия агента после получения контекста, а не только наличие пакета.

## 5. Для кого и в каких случаях

Сборщик нужен пользователю, который впервые подключает Agent Flow к существующему проекту или уже развивает продукт с его помощью. Один продукт может включать несколько репозиториев.

При первом запуске изучается только необходимая для текущего запроса часть проекта. Для каждой следующей задачи проверяются применимость и актуальность накопленных сведений, затем добирается недостающее. Контекст предыдущей задачи не переносится целиком как готовый ответ.

Поддерживаются прежние цепочки документов:

- PRD → ADR → Implementation Plan.
- PRD → Implementation Plan.
- ADR → Implementation Plan.
- Только Implementation Plan.

Сборщик не меняет правила выбора документов. ADR нужен, когда задача затрагивает архитектуру. Готовый план не отменяет первичный сбор и не требует повторно создавать документы. Исправление опечаток и оформления в уже ведущейся задаче само по себе не вызывает повторный сбор.

## 6. Польза для пользователя

Пользователь меняет подход одним явным решением, без повторного согласования и ручного сбора контекста.

## 7. Требуемое поведение

### 7.1. Запуск, достаточность и пересборка

При явном запуске Agent Flow для новой задачи сбор начинается автоматически. Наличие проектных файлов само по себе Agent Flow не запускает.

При первом использовании сборщик изучает существующие планы, требования, критерии, процессы и затронутую реализацию. Форматы Agent Flow и его собственная память заранее не требуются. Отсутствующие решения не выдумываются.

Сбор завершается, когда понятны цель, действующие требования, затронутые компоненты и способ проверки результата, а существенных неизвестных для следующего действия нет. Читаются только сведения, связанные с конкретным запросом. Сбор информации «на всякий случай» исключён. Существенный пробел требует изучить связанные источники или задать точечный вопрос; зависимое действие не начинается, независимую работу можно продолжить.

Перед каждым PRD, ADR и Implementation Plan, а также перед содержательным пересмотром документа, агент проверяет актуальность контекста и добавляет необходимое для документа. Пока запрос не изменился, проверенные неизменные сведения можно использовать повторно. Изменения источников, включая рабочие файлы без коммита, учитываются при проверке; прежний пакет автоматически актуальным не считается.

Если запрос изменился, контекст пересобирается под новый запрос. Дополнить прежний пакет отдельными сведениями недостаточно: отменённые требования могут смешаться с новыми. Прежний пакет не переносится автоматически как действующий. Пересборка ограничена новым запросом; история отменённых решений в рабочий пакет не включается.

Например, переход от локального хранения файлов к облачному требует заново собрать контекст новой задачи, а не добавить сведения об облаке к прежним ограничениям локального хранения.

При потере контекста пакет также собирается заново из доступных источников. Прежняя передача сведений не доказывает, что агент ещё располагает ими. Эти события не требуют постоянного фонового пересбора во время реализации.

В начале подготовки контекста PRD агент определяет, сколько продуктовых изменений затрагивает запрос и как они пересекаются. Если один PRD объединяет несколько самостоятельных продуктовых задач и становится слишком большим, агент явно сообщает об этом пользователю и предлагает декомпозицию до подготовки большого документа и реализации.

Условный пример: большой запрос объединяет оплату, возвраты и отчётность. Его можно разделить на продуктовые задачи с отдельными контекстами и соответствующими документами. Пример иллюстрирует принцип декомпозиции и не задаёт функции или предметные правила реализации сборщика.

Декомпозиция не делает ADR обязательным для каждой части и не разрешает автоматически начинать все выделенные задачи. Технические части одной функции, например её frontend и backend, не становятся отдельными продуктовыми задачами только из-за разделения работы между исполнителями.

### 7.2. Источники и границы

Допустимые источники:

- Текущий разговор, включая явно принятые пользователем решения.
- Документы, планы, критерии, описания процессов и проектная память, относящиеся к задаче, в том числе созданные до внедрения Agent Flow.
- Затронутая реализация продукта: код и технические контракты, необходимые для понимания текущего состояния.
- Связанные репозитории и документы, если связь указана пользователем или в документации проекта.
- Другие чаты, на которые пользователь сам явно указал ссылку как на источник контекста.

Самостоятельный поиск по истории чатов не допускается. Найденная в файле ссылка не разрешает чтение чата. По явно указанной пользователем ссылке агент читает чат без повторного запроса разрешения. Существующая запись в проектной памяти доступна как самостоятельный источник. Эти правила распространяются и на чтение связанных сессий при проверке зависимостей.

Связь с продуктом не требует читать все его репозитории целиком. Отбор определяется запросом, областью решения и подготавливаемым документом. Недоступный источник не считается прочитанным. Если его отсутствие оставляет существенный вопрос, агент обозначает пробел и уточняет зависимую часть.

### 7.3. Актуальность решений

| Ситуация | Требуемое поведение |
| --- | --- |
| Пользователь явно меняет продуктовое или архитектурное решение | Новое решение действует сразу; повторное подтверждение не требуется |
| Новое решение явно заменяет прежнее | Агент применяет новый подход и обновляет документ по правилам раздела 7.4 |
| Агент предложил вариант, пользователь его ещё не принял | Вариант остаётся предложением |
| После проверки источников конфликт остаётся, явной замены нет | Агент задаёт один точечный вопрос и продолжает независимую часть |
| Код соответствует прежнему решению | Агент различает текущее и требуемое состояние; код не отменяет новую цель |
| Документ свежее, но принятие решения не подтверждено | Дата сама по себе не доказывает замену |

Если область отдельно не названа, решение относится к обсуждаемой функции или части продукта. На весь проект оно распространяется только по явному указанию пользователя. Например, облачное хранение фотографий товаров не становится правилом для логов и временных файлов.

Замена касается затронутого решения и положений, зависящих только от отменённого подхода. Незатронутые требования сохраняются. Последствия изменения, например переделка существующей функции, учитываются в результирующем документе. Само отличие от истории не блокирует работу.

### 7.4. Сохранение решений и обновление документов

Явно принятое решение записывается сразу после ответа пользователя, до продолжения работы. Подготовки документа или завершения задачи ждать не нужно.

Постоянные решения хранятся в соответствующих PRD, ADR и Implementation Plan, включаемых в Git. Пока соответствующего документа нет, решение временно сохраняется в `.agent-work`, затем отражается в документе. Фактическая запись в документ проверяется; одного намерения перенести решение недостаточно. Отдельный постоянный реестр решений не создаётся.

`.agent-work` остаётся локальной и исключается из коммитов. До отражения решения в проектном документе и его коммита временная запись не передаётся через Git. Сохранение решения не означает разрешения на автоматический коммит.

При изменении решения внутри того же PRD устаревшие требования полностью удаляются вместе с положениями, которые зависят только от отменённого подхода. Незатронутые требования сохраняются. Архив отменённого текста, ссылка на предыдущую редакцию или отдельный документ ради истории не нужны. Например, при смене локального хранения на облачное из PRD удаляется всё, что относится только к локальному хранению.

Если новый документ заменяет договорённости из другого документа, он кратко называет отменённые или заменённые решения и содержит ссылку на тот документ, при необходимости — на конкретный раздел. Отмена касается только названных решений; остальные требования сохраняются. Это правило не требует копировать старый текст в рабочий контекст. Массовая перезапись других PRD, ADR и планов или удаление файлов в эту функцию не входят.

При следующей задаче агент проверяет действующие документы и применимость решений, чтобы не возвращать отменённые требования в работу.

### 7.5. Результат и передача контекста

Общий контекст включает цель и границы задачи, действующие решения, относящиеся к работе ограничения и критерии, состояние затронутой реализации, открытые вопросы и ссылки на источники. История отменённых решений исключается из рабочего пакета. Сведения о текущем коде сохраняются, когда нужны для изменений или миграции: они описывают фактическое состояние, а не отменённое требование.

Основной агент собирает общий контекст из проектных документов независимо от их авторства и необходимых отчётов исследований субагентов. Каждый исполнитель получает сведения и источники своей части, читает обязательные документы и добирает только недостающее для своего задания. Повторять полное исследование проекта каждому исполнителю не нужно.

Содержание зависит от документа: для PRD нужны продуктовый замысел и ожидаемое поведение; для ADR — также технические ограничения и существующая архитектура; Implementation Plan связывает принятые требования с затронутой реализацией и проверками.

Пакет используется автоматически. Пользователь получает сообщения о существенных заменах решений и нерешённых вопросах. Обязательная сводка перед каждой задачей или документом и отдельное утверждение пакета не требуются.

Выжимка не заменяет обязательное чтение инструкций, требований и доказательств. Непоместившиеся сведения обозначаются явно, обязательные требования не обрезаются молча. Слишком большой продуктовый объём выявляется при подготовке контекста PRD по разделу 7.1; распределение одной чрезмерной задачи между исполнителями не заменяет раннюю продуктовую декомпозицию.

### 7.6. Сценарии приёмки

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| C01 | Новый документ по явному решению пользователя заменяет договорённости из другого PRD | Агент применяет новое решение без повторного согласования. Новый документ кратко называет заменённые или отменённые договорённости и ссылается на прежний PRD, при необходимости — на раздел. Остальные требования сохраняются; исторический текст в рабочий пакет не копируется |
| C02 | Новый документ заменяет только часть решений старого ADR | Документ указывает заменённые решения со ссылкой на ADR; остальные требования сохранены. История отменённых решений не включается в рабочий пакет |
| C03 | Следующая задача встречает ранее заменённое решение | Агент проверяет действующие документы и не возвращает отменённое требование или его историю в рабочий пакет |
| C04 | В источниках противоречащие решения без доказанной замены | Один точечный вопрос; независимая работа продолжается |
| C05 | Более свежий черновик содержит предложение агента | Дата не превращает предложение в принятое решение |
| C06 | Между PRD и ADR принято новое решение или изменилась затронутая реализация | Контекст проверен перед следующим документом. При изменении запроса он пересобран; иначе неизменные проверенные сведения используются повторно |
| C07 | Новый подход ещё не реализован в коде | Документ различает текущее и требуемое состояние, описывает необходимые изменения |
| C08 | Ссылка на другой чат найдена в файле либо пользователь сам явно указал её как источник контекста | Найденная в файле ссылка не разрешает чтение. По явно указанной пользователем ссылке чат читается без повторного согласования; самостоятельного поиска нет |
| C09 | Задача затрагивает связанный репозиторий | Связь подтверждена указанием пользователя или документацией; прочитаны только относящиеся к задаче сведения |
| C10 | Создаётся или содержательно меняется документ в любой допустимой цепочке | Сбор выполняется перед нужным документом; лишние документы не добавляются |
| C11 | Исправляется опечатка в уже ведущейся задаче либо Agent Flow не запущен | Опечатка не вызывает повторного сбора; вне явно запущенного Agent Flow механизм не запускается |
| C12 | Источник недоступен либо необходимый контекст не помещается | Пробел виден; отсутствующие сведения не выданы за прочитанные или проверенные, обязательные требования не обрезаны молча. Существенный пробел не позволяет начать зависимое действие |
| C13 | Agent Flow впервые используется в проекте со своими планами, критериями и процессами | Контекст собран по существующим источникам и реализации; отсутствие памяти Agent Flow не блокирует работу, перевод существующих документов в другой формат не требуется |
| C14 | Следующая задача затрагивает другую область продукта | Относящиеся к задаче накопленные сведения проверены; недостающее собрано из источников новой области |
| C15 | Между задачами изменились решение, документ или реализация, в том числе без коммита | Изменения учтены; прежний пакет не считается актуальным автоматически |
| C16 | Новая задача передана с готовым Implementation Plan | Первичный сбор выполнен; повторное создание PRD, ADR или плана не навязано |
| C17 | Цель, требования, компоненты и проверки понятны; остаются документы вне запроса | Сбор завершён. Нерелевантные документы «на всякий случай» не читаются |
| C18 | Решение принято до появления документа, затем работа прервана и продолжена в том же проекте | Решение записано в `.agent-work` до продолжения работы и найдено следующей задачей. При подготовке документа оно отражено в нём; если заменяет договорённости из другого документа, добавлены краткое указание замены и ссылка. Автоматического коммита нет |
| C19 | Пользователь выбрал облачное хранение фотографий товаров, не указав область отдельно | Решение применяется к фотографиям, не переносится на логи, временные файлы или весь проект |
| C20 | Для общей задачи доступны проектные документы разных авторов, а по одной части нужно исследование субагента | Основной агент собирает общий контекст из документов независимо от авторства и необходимого отчёта; исполнители получают свои сведения и обязательные источники. Уже проверенные и актуальные материалы не исследуются заново |
| C21 | Условный проверочный пример: при подготовке PRD большой запрос объединяет оплату, возвраты и отчётность | Агент до подготовки большого PRD сообщает о необходимости декомпозиции на продуктовые задачи с отдельными контекстами. ADR не навязывается части, которая не затрагивает архитектуру |
| C22 | Условный пример: в том же PRD локальное хранение заменено облачным; после пересборки агент потерял контекст | Из PRD удалены отменённые требования и зависящие только от них положения, незатронутые требования сохранены. Архив, ссылка на прежнюю редакцию и отдельный документ ради истории не нужны. Новый пакет исключает историю отменённых решений; сведения о текущем коде сохранены, если нужны для изменений или миграции. После потери контекста пакет восстановлен из источников, прежняя передача не считается доказательством сохранённого знания |

### 7.7. Что уточнить в ADR

Процедурный подход первой версии принят. ADR должен описать его через существующие средства Agent Flow: отбор источников, проверку актуальности, сохранение действующих решений и их области, временную запись до появления документа и передачу контекста исполнителям. Порядок обновления документов должен учитывать удаление отменённых требований внутри одного PRD и ссылки при замене договорённостей между разными документами.

Нужно определить, как процедура использует проверенные сведения между задачами и восстанавливает контекст после его потери без истории отменённых решений. Связанные чаты читаются только по ссылкам, которые пользователь сам явно указал как источники контекста. Эти технические детали не требуют повторного согласования уже принятых продуктовых решений.

## 8. Первый выпуск и границы

Первый этап охватывает сбор при первом использовании Agent Flow, при каждой новой задаче и при подготовке документов, а также пересборку после изменения запроса или потери контекста. Следующие результаты этапа: ADR процедуры, Implementation Plan, обновлённые инструкции и проверка сценариев C01–C22.

По решению пользователя от 2026-10-02 текущая задача завершается переносом готовой процедуры в основной Agent Flow. Общие инфраструктурные проверки выполняются отдельно и не блокируют эту интеграцию. Сценарии C01–C22 сохраняются; интеграция не означает, что все они прошли проверку. Следующий шаг — реальный кейс пользователя.

Живая проверка должна охватить первое использование в существующем проекте, сбор для следующей задачи и подготовку документа. Конкретные задачи выбираются до запуска проверки; сроки пока не оценены. Программный сборщик рассматривается только при подтверждённой недостаточности процедуры.

В текущий этап не входят диагностика журнала, постоянный фоновый пересбор во время реализации, запуск вне Agent Flow, самостоятельный просмотр прошлых чатов и массовая актуализация исторических документов. Специальная обработка гипотетического отказа прав на запись в доступную папку проекта в MVP не добавляется.
