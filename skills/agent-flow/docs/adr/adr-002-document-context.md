# ADR-002: Процедура сборки актуального контекста

инструкции реализованы и интегрированы в основной Agent Flow. По решению

[Implementation Plan 016](../implementation/impl-016-document-context.md#1-цель-и-границы).

## 1. Контекст

Agent Flow должен находить действующие требования конкретной задачи, даже если проект ещё не использовал его форматы и память. Сведения распределены между разговором, проектными документами, рабочими файлами и результатами субагентов. Новое решение пользователя может расходиться с существующей реализацией или заменять прежнее требование.

PRD задаёт границы: читать только необходимое, пересобирать пакет при изменении запроса, сохранять принятые решения и исключать историю отменённых решений из рабочего контекста. Нужен единый порядок этих действий внутри существующего процесса Agent Flow.

## 2. Решение

Сборка контекста становится процедурой основного агента и исполнителей. Она использует доступные средства поиска и чтения, проектную документацию, локальную память и существующий журнал запуска. Отдельный сервис, индекс, база данных, машинная схема пакета и постоянный реестр решений для первой версии не вводятся.

Основной агент отвечает за цель, область запроса, достаточность общего контекста и согласование результатов исполнителей. Он использует проектные документы независимо от авторства и необходимые отчёты исследований субагентов. Каждый исполнитель отвечает за источники своей части и чтение обязательных документов, перечисленных в задании.

### 2.1. Точки запуска

Точки запуска и исключения заданы в [PRD §7.1](../prd/prd-001-document-context.md#71-запуск-достаточность-и-пересборка). В явно запущенном Agent Flow основной агент выполняет процедуру при начале задачи и перед созданием или содержательным пересмотром документа. Готовый план не отменяет проверку источников; первое подключение использует существующие форматы проекта.

Изменение запроса запускает пересборку по §2.3, потеря контекста — восстановление по §2.5. Фонового наблюдения за файлами и повторной сборки ради опечаток нет.

### 2.2. Отбор источников и завершение сбора

Основной агент начинает с запроса, обязательных инструкций и указанных пользователем документов. Недостающее ищет адресно, например через `rg` и список файлов, в границах [PRD §7.2](../prd/prd-001-document-context.md#72-источники-и-границы). Совпадение в поиске служит указателем для чтения, а не доказательством принятого решения. Локальную проектную память агент читает без автоматического перехода в исходный чат: для чтения чата нужна ссылка, явно указанная пользователем как источник.

В пакете или задании агент указывает существенные решения, их область, источники и пробелы; непрочитанный источник не отмечает как проверенный. Сбор прекращается по критерию достаточности из PRD §7.1. При существенном пробеле агент читает связанный источник или задаёт точечный вопрос, приостанавливая только зависимую работу.

До составления PRD основной агент оценивает продуктовый объём запроса и при необходимости предлагает декомпозицию по PRD §7.1. Правила выбора документов для выделенных задач сохраняются.

### 2.3. Актуальность и повторное использование

Перед следующим документом или задачей агент сверяет используемые источники с текущей рабочей копией, включая незакоммиченные и новые файлы. При неизменном запросе проверенные неизменные сведения используются повторно; если актуальность установить нельзя, нужный источник читается заново. Отдельный кеш не создаётся.

При изменении запроса основной агент заново определяет цель, требования, источники и состав заданий по PRD §7.1. Задания исполнителей, зависящие от отменённого подхода, обновляются до продолжения этой работы.

При обнаруженном противоречии агент проверяет принятие и область решений по [PRD §7.3](../prd/prd-001-document-context.md#73-актуальность-решений). Явную замену применяет без повторного согласования, неразрешённый конфликт выносит в точечный вопрос. Обязательный поиск неизвестных замен документов не вводится; принятое ограничение описано в §5.

### 2.4. Сохранение решений

Принятое решение записывается сразу после ответа пользователя, до продолжения работы. Если соответствующий проектный документ уже существует, решение отражается в нём независимо от того, планировалась ли его правка. Основной агент отвечает за фактическую запись и её проверку; если правку выполняет субагент, основной агент передаёт ему решение и проверяет результат.

Временная запись нужна только пока соответствующего документа нет. Для неё используется текущий раздел задачи в `.agent-work/tasks/todo.md` либо уже используемая проектом локальная запись этой задачи. Дополнительный проектный документ или постоянный реестр ради сохранения решения не создаётся.

Временная запись содержит действующее решение, его область, основание и документ, в котором его предстоит отразить. При подготовке этого документа агент переносит решение, проверяет фактическую запись и помечает временную запись как отражённую со ссылкой на документ. Временная запись помогает продолжить работу в той же локальной копии; передача решения через Git начинается после записи в проектный документ и его коммита. Само сохранение решения не разрешает автоматический коммит.

Правила обновления документов различаются:

- В пересматриваемом PRD отменённые требования и положения, зависящие только от них, удаляются. Незатронутые требования сохраняются. Архив отменённого текста и ссылка на прежнюю редакцию не нужны.
- Если новый документ отменяет договорённости другого документа, он кратко указывает отмену, её область и ссылку на тот документ. Старый текст в рабочий пакет не копируется. При последующем чтении источников эта ссылка помогает распознать замену.

Постоянные решения остаются в PRD, ADR и Implementation Plan проекта, включаемых в Git. `.agent-work` не коммитится. Массовое обновление прежних документов и отдельный механизм для гипотетического отказа прав на запись не входят в решение.

### 2.5. Рабочий пакет и передача исполнителям

Пакет — краткое изложение сведений для конкретного действия, а не новый вид проектного документа. Он содержит цель и границы, действующие решения, необходимые ограничения и критерии проверки, состояние затронутой реализации, открытые вопросы и ссылки на источники. История отменённых решений в пакет не включается.

В запуске с журналом общий пакет хранится в разделе `Рабочий пакет` существующего `context.md`. Перед обновлением агент читает текущую запись через `journal.py read`, меняет только этот раздел и публикует документ через `journal.py publish`. При первой записи раздел добавляется. Остальные разделы сохраняются, в том числе исходный снимок `Initial Worktree Snapshot`; сборщик его не переписывает.

Если изменение затрагивает уже принятые доказательства, их ссылки и хеши обновляются с повторной проверкой по [существующему порядку приёмки](../../references/traceable-runs.md#запись-и-собственный-итог-проверяющего). Новый механизм версий не вводится.

В задаче без журнала используются текущий контекст агента и существующая локальная запись задачи для принятых решений и возобновления работы. Создавать run только ради сборщика не требуется. Проектные документы остаются источниками постоянных требований при обоих вариантах.

Основной агент передаёт исполнителю цель его части, ограничения, критерии результата, нужные сведения и ссылки на обязательные источники через существующий delegation packet. Исполнитель читает эти источники и добирает только недостающее для задания. Его документ или отчёт указывает использованные источники и оставшиеся пробелы; основной агент объединяет результаты и разрешает противоречия по правилам §2.3. Новый отчёт не требуется, когда имеющихся актуальных документов достаточно.

Передача выжимки не заменяет обязательного чтения источников. После потери контекста агент восстанавливает сведения по документам и текущей локальной записи задачи; при необходимости повторно читает обязательные источники. Если необходимое не помещается, пробел обозначается явно и зависимое действие не начинается. Обязательные требования не сокращаются молча.

Пакет применяется без отдельного утверждения пользователем. Пользователю сообщаются существенные замены решений и вопросы, требующие его ответа.

## 3. Изменения в существующих инструкциях

Реализация должна согласовать следующие места; этот ADR сам их не изменяет:

| Место | Изменение |
| --- | --- |
| [SKILL.md](../../SKILL.md), Project Memory And Environment Gate и Dependency Gate | Закрепить точки запуска процедуры и достаточность контекста. Убрать обязанность читать связанную сессию только потому, что её ссылка найдена в памяти |
| [project-memory-and-env.md](../../references/project-memory-and-env.md), Required Intake и Dependency Gate | Описать ограничение источников запросом, проверку актуальности, немедленную запись решений и восстановление после потери контекста |
| [orchestrator.md](../../references/orchestrator.md), Start Of Request | Включить сборку и проверку контекста перед планированием и зависимой работой без нового approval gate |
| [delegation.md](../../references/delegation.md), Delegation Packet и Handoff Format | Уточнить обязательные источники исполнителя, адресный добор и передачу результатов основному агенту |
| [implementation-plan-authoring.md](../../references/implementation-plan-authoring.md), Required Authoring Sequence | Согласовать получение актуального контекста перед планом с общей процедурой |

В части чтения связанных сессий решение заменяет прежнюю инструкцию Dependency Gate в [SKILL.md](../../SKILL.md) и [project-memory-and-env.md](../../references/project-memory-and-env.md): ссылка из найденного документа или памяти не разрешает переход в чат. Требуется ссылка, явно указанная пользователем как источник. Остальные проверки зависимостей сохраняются.

[ADR-001: Локальный CodeGraph](adr-001-codegraph.md) описывает другой механизм и остаётся самостоятельным предложением. Его принятие или реализация не являются условием этого ADR: процедуре достаточно существующих инструментов поиска и чтения.

## 4. Рассмотренные варианты

| Вариант | Оценка |
| --- | --- |
| Процедура в существующих инструкциях | Выбран: применима к проектам с разными форматами документов и не требует нового программного слоя. Качество зависит от соблюдения процедуры агентами |
| Отдельный программный сборщик с индексом и хранением состояния | Отложен согласно PRD до подтверждённой недостаточности процедуры. Сейчас потребовал бы новых правил хранения и интеграции, необходимость которых не установлена |
| Постоянно дополняемый пакет контекста | Отклонён: после изменения запроса сохраняет риск смешения новых требований с отменёнными |

## 5. Последствия

Проект может использовать процедуру без миграции своей документации. Исполнители получают только сведения своей части, а принятые решения доступны следующей задаче через документы и локальную запись. Изменение запроса не наследует отменённые ограничения.

Принят риск, что замена решения останется незамеченной, если её нет в указанных пользователем и прочитанных по задаче источниках. Ради этого редкого случая отдельный поиск замен по проекту не выполняется. Известные замены учитываются по §2.3; C03 проверяет их применение, а не полноту обнаружения всех замен в проекте.

Пересборка при изменении запроса может потребовать повторного чтения; сокращать его ценой потери требований нельзя. До переноса временной записи в документ и коммита решение доступно только в локальной рабочей копии.

Переход к программному сборщику рассматривается, если проверки обнаруживают повторяющиеся нарушения, которые уточнённая процедура не устраняет. Такой переход требует отдельного решения; текущий ADR не запускает его автоматически.

## 6. Проверка решения

При реализации проверяются действия агента и содержимое документов, пакета и заданий. Наличие записи `context.md` само по себе не доказывает выполнение процедуры.

| Сценарии PRD | Что проверять |
| --- | --- |
| C01–C03, C05, C07, C19 | Область и актуальность решений; применение известных замен между документами со ссылкой; различение предложения, действующего требования и состояния кода |
| C04, C12 | Точечный вопрос или обозначение пробела; зависимая работа не начинается, независимая может продолжаться |
| C06, C10, C14–C16 | Проверка источников перед задачей и документом, включая рабочие изменения без коммита; готовый план не создаёт лишних документов |
| C08–C09 | Соблюдение границ чатов и связанных репозиториев, без самостоятельного поиска по истории |
| C11, C13, C17 | Запуск только внутри Agent Flow, отсутствие повторного сбора ради опечатки, работа с существующими форматами, остановка при достаточности |
| C18 | Немедленная временная запись, возобновление работы и отражение решения в проектном документе без автоматического коммита |
| C20–C21 | Контекст по части исполнителя, использование документов разных авторов, ранняя продуктовая декомпозиция без навязанного ADR |
| C22 | Удаление устаревших требований из того же PRD, пересборка и восстановление пакета без истории отменённых решений |

Живая проверка охватывает первое подключение к существующему проекту, следующую задачу и подготовку документа. Конкретные задания и способ фиксации результатов определяются в Implementation Plan. Эта таблица связывает решение со всеми C01–C22 и не является отчётом об их прохождении.
