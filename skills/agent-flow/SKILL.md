# Agent Flow

Agent Flow применяется только по явному поручению пользователя: `Agent Flow`, `AgentFlow`, `$agent-flow`, `agent-flow` или «агент-флоу». Обсуждение скилла и чтение этого файла не запускают процесс. Начатая задача продолжается без повторного маркера до её завершения, отмены или замены пользователем.

## Основной порядок

1. Прочитайте запрос, проектные инструкции, выбранную задачу или план и относящиеся к ней To Do, Lessons, Implementation Notes. Установите ограничения на правки, команды и внешние действия. Не загружайте всю историю проекта.
2. Выберите минимальный flow из [flows.md](references/flows.md). Для всех документов соблюдайте [общее правило утверждения](references/flows.md#утверждение-документов): открытые вопросы исключают `approved`, а разработка по документу требует утверждённой текущей редакции без открытых вопросов. Для подготовки [PRD](references/flows.md#подготовка-prd) и [ADR](references/flows.md#подготовка-adr) соблюдайте соответствующий единый порядок авторства, редакторской и независимых проверок. Для простой консультации достаточно ответа. Для изменения файлов используйте один SQLite-журнал с текущим контрактом из [traceable-runs.md](references/traceable-runs.md).
3. Укажите источник критериев: уникальный раздел задачи и подраздел «Критерии приёмки» с плоским списком проверяемых результатов и необходимых проверок. Само прохождение review и QA проверяет Agent Flow при завершении; не включайте его в критерии QA. Не создавайте отдельную копию требований или Definition of Done для прогона.
   До инициализации отделите локальную разработку и локальный QA от внешней настройки, удалённого CI и live-проверок в самостоятельные задачи с отдельными критериями. Наличие credentials и доступность сервиса не являются условиями завершения локальной задачи. Правила границ находятся в [implementation-plan-authoring.md](references/implementation-plan-authoring.md).
4. Инициализируйте задачу на реальных рабочих каталогах. Сохраните пути области работы и ссылку на раздел требований. Agent Flow не сканирует репозиторий и не отслеживает изменения файлов. Чужие незакоммиченные правки сохраняйте точечным редактированием.
5. Уточните существенные требования и архитектуру до зависимых правок. Применяйте профильные skills по существу задачи. Для нового или существенно изменённого плана назначьте независимое requirements review существующему `qa-verifier`; оно не заменяет итоговую проверку продукта.
   Архитектор применяет `arch-simplicity-guard` при подготовке и пересмотре решения; существующий независимый `reviewer` проверяет архитектуру и план до зависимой реализации. Каждый вызывает селектор внутри своей сессии и использует инструкции для собственной фактической модели. Оркестратор возвращает блокирующие архитектурные замечания архитектору, а спорные решения ADR сразу передаёт `supervising-architect` по порядку подготовки ADR. После исправления нужна независимая проверка; до этого зависимая реализация не начинается. Недоступность guard оставляет эту проверку невыполненной.
6. Выполните работу самостоятельно либо разделите её по [delegation.md](references/delegation.md). У каждого пути одновременно один исполнитель. Дополнительный агент нужен для независимой проверки или самостоятельного объёма работы.
7. При работе с журналом каждый исполнитель возвращает один отчёт с непустой строкой `summary`. Writer принимает последний завершённый native-ответ субагента либо отчёт основного агента из текущего turn. Автор может использовать собственные подтверждённые действия с начала назначения, включая предыдущие завершённые turn. Исправление оформления отчёта не требует повторять правки или генерацию. Для [PRD и ADR только в чате](references/flows.md#prd-и-adr-только-в-чате) используйте собственные ответы участников без регистрации в журнале.
8. Завершите правки перед независимым `reviewer`. Он проверяет текущий результат и отчёты авторов. Только после успешного review запускайте `qa-verifier`; при работе с журналом требуется принятый `completed` review и ссылка на его `assignment_id`. Reviewer и QA независимы друг от друга и от авторов. Порядок: результат → review → QA → final. При подготовке PRD и ADR проверяется документ, а не реализация описанного приложения.
9. Замечания поступают оркестратору: он направляет дефект реализации разработчику, архитектурную проблему архитектору, недостаток доказательств проверяющему, а за необходимыми сведениями или ручным действием обращается к человеку. Сохраняйте исходную цель и разрешения; продолжайте доработку по [правилам оркестратора](references/orchestrator.md), без ручного перезапуска поручения. После собственных содержательных исправлений повторяйте review изменения и затронутые проверки QA. Журнал не сравнивает содержимое файлов или отчётов. Правки соседнего чата не отменяют приёмку этой задачи. После успешного QA дополнительный reviewer не нужен.
10. Если задача ведётся в журнале, завершите его через `finalize`. Final появляется только в конце с `completed` либо `failed`. Передайте пользователю итог со ссылками на отчёты, фактическими проверками и оставшимися ограничениями. Для PRD и ADR только в чате передайте проверенный текст и статус без вызова `finalize`.

## Полномочия и доказательства

Запуск Agent Flow не разрешает автоматически установку зависимостей, контейнеры, commit, push, публикацию или deploy. Соблюдайте ограничения пользователя и действующие правила среды. При уже полученном разрешении не спрашивайте его повторно.

Не считайте текст «всё проверено» доказательством. Отчёт ссылается на реальные действия и результаты команд. Запрещённая, недоступная или невыполненная проверка остаётся неподтверждённой. Отрицательный отчёт требует решения оркестратора о продолжении; исправимый дефект, помеха или ожидание помощи человека не завершают поручение. Финальный `failed` допустим только при окончательном прекращении невыполненной работы по [правилам оркестратора](references/orchestrator.md), с причиной и перечнем непроверенного.

SQLite хранит единственные текущие записи назначений, отчётов и final. Markdown формируется при чтении. Не поддерживайте параллельно lane-map, summary, timeline, handoff-файлы или матрицы с теми же фактами. Отчёты нужны текущей задаче у текущего провайдера; после обновления Agent Flow начинайте новый чат.

Операции SQLite защищают согласованность записей, но не замораживают исходники и не обеспечивают однократность внешней команды. После прерывания проверяйте её фактический результат до повтора.

## Качество без лишней процедуры

- Архитектор нужен для подготовки ADR и при изменении границ модулей, публичных контрактов, потоков данных или иных существенных технических решений. Решение и ограничения хранятся в ADR, когда его подготовка входит в задачу, либо в отчёте или существующем проектном документе.
- Перед QA проверьте простоту основного решения: нет ли ненужной абстракции, дублирования, зависимости, запасного режима или расширения задачи. Исправляйте причину; косметическая правка отчёта не исправляет код.
- Тесты проверяют требования и реальные риски. Не создавайте матрицу редких случаев, не повторяйте неизменённые проверки ради нового receipt.
- Для UI проверяйте реальный пользовательский путь. Скриншот доказывает только видимую на нём часть интерфейса.
- Для разрешённого исправления документов и продуктовых артефактов используйте [ai-slop-gate.md](references/ai-slop-gate.md). Роль `ai-slops-hunter` убирает дефисы и тире только из пользовательской прозы, сохраняя синтаксис кода, команд и других технических фрагментов; режим отдельных замечаний не предусмотрен. Обычные ответы и черновики только в чате не требуют `humanizer-ru` или `ai-slops-hunter` без явного запроса на редактуру; исключения — подготовка PRD и ADR по [flows.md](references/flows.md). Отдельного проверяющего комментариев нет: применяйте `development.md` при обычном ревью.
- Не меняйте состав ролей, модель и reasoning без соответствующего поручения. Выбирайте параметры через существующий `agent_config.py`.
