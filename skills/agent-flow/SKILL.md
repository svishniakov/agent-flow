# Agent Flow

Agent Flow применяется только по явному поручению пользователя: `Agent Flow`, `AgentFlow`, `$agent-flow`, `agent-flow` или «агент-флоу». Обсуждение скилла и чтение этого файла не запускают процесс. Начатая задача продолжается без повторного маркера до её завершения, отмены или замены пользователем.

## Основной порядок

1. Прочитайте запрос, проектные инструкции, выбранную задачу или план и относящиеся к ней To Do, Lessons, Implementation Notes. Установите ограничения на правки, команды и внешние действия. Не загружайте всю историю проекта.
2. Выберите минимальный flow из [flows.md](references/flows.md). Для простой консультации достаточно ответа. Для изменения файлов используйте один SQLite-журнал с текущим контрактом из [traceable-runs.md](references/traceable-runs.md).
3. Укажите источник критериев: уникальный раздел задачи и подраздел «Критерии приёмки» с плоским списком. Не создавайте отдельную копию требований или Definition of Done для прогона.
4. Инициализируйте задачу на реальных рабочих каталогах. Записывается опись путей и отпечатков; исходники не копируются. Чужие незакоммиченные правки сохраняйте точечным редактированием.
5. Уточните существенные требования и архитектуру до зависимых правок. Применяйте профильные skills по существу задачи. Для нового или существенно изменённого плана назначьте независимое requirements review существующему `qa-verifier`; оно не заменяет итоговую проверку продукта.
6. Выполните работу самостоятельно либо разделите её по [delegation.md](references/delegation.md). У каждого пути одновременно один исполнитель. Дополнительный агент нужен для независимой проверки или самостоятельного объёма работы.
7. Каждый исполнитель возвращает один отчёт. Writer принимает его из собственного завершённого native-ответа агента. Основной агент подтверждает собственные изменения уже выполненными native-действиями текущего turn.
8. Завершите правки перед QA. Для положительного завершения задачи с изменением файлов нужны реальные независимые `qa-verifier` и `reviewer`: QA проверяет текущий результат, reviewer — результат и принятый QA-отчёт. Их IDs отличаются друг от друга и от авторов.
9. Исправьте подтверждённые замечания. Повторяйте только затронутые проверки; изменение результата делает связанные заключения неактуальными.
10. Завершите журнал через `finalize`. Final появляется только в конце с `completed` либо `failed`. Передайте пользователю итог со ссылками на отчёты, фактическими проверками и оставшимися ограничениями.

## Полномочия и доказательства

Запуск Agent Flow не разрешает автоматически установку зависимостей, контейнеры, commit, push, публикацию или deploy. Соблюдайте ограничения пользователя и действующие правила среды. При уже полученном разрешении не спрашивайте его повторно.

Не считайте текст «всё проверено» доказательством. Отчёт ссылается на реальные действия и результаты команд. Запрещённая, недоступная или невыполненная проверка остаётся неподтверждённой. Если согласованный результат невозможно принять, завершайте `failed` с причиной и перечнем непроверенного.

SQLite хранит единственные текущие записи назначений, отчётов и final. Markdown формируется при чтении. Не поддерживайте параллельно lane-map, summary, timeline, handoff-файлы или матрицы с теми же фактами. Отчёты нужны текущей задаче у текущего провайдера; после обновления Agent Flow начинайте новый чат.

Операции SQLite защищают согласованность записей, но не замораживают исходники и не обеспечивают однократность внешней команды. После прерывания проверяйте её фактический результат до повтора.

## Качество без лишней процедуры

- Архитектор нужен при изменении границ модулей, публичных контрактов, потоков данных или иных существенных технических решений. Решение и ограничения хранятся в его отчёте либо существующем проектном документе.
- Перед QA проверьте простоту основного решения: нет ли ненужной абстракции, дублирования, зависимости, запасного режима или расширения задачи. Исправляйте причину; косметическая правка отчёта не исправляет код.
- Тесты проверяют требования и реальные риски. Не создавайте матрицу редких случаев, не повторяйте неизменённые проверки ради нового receipt.
- Для UI проверяйте реальный пользовательский путь. Скриншот доказывает только видимую на нём часть интерфейса.
- Для текста и артефактов используйте [ai-slop-gate.md](references/ai-slop-gate.md). Отдельного проверяющего комментариев нет: применяйте `development.md` при обычном ревью.
- Не меняйте состав ролей, модель и reasoning без соответствующего поручения. Выбирайте параметры через существующий `agent_config.py`.
